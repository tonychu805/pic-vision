## TrackNetV3 (`qaz812345/TrackNetV3`) fixed, confirmed working, and benchmarked once

- **Diagnosed the hang, don't just restart it.** `predict.py` was run without `--large_video`, so it decoded the entire video into RAM up front (1920×1080 × 1753 frames = 10.9 GB, confirmed against every stuck worker's RSS to the byte) and handed it to a 16-worker `DataLoader`. This venv's Python (3.14) defaults multiprocessing to `forkserver`, not `fork` (confirmed via `mp.get_start_method()`), so each of the 16 workers was getting its own separately-pickled ~11 GB copy over IPC instead of sharing memory — ~175 GB of transfer against a 61 GB box. It could never finish.
- **Fixed with `--large_video`**, which streams frames per-worker (just a file path + lazy `cv2.VideoCapture`) and doesn't even spawn subprocess workers for that path. Verified working this time — showed up in `nvidia-smi`'s process list (the hung one never did), RSS stayed sane, I/O kept climbing — rather than just trusted.
- **Smoke test completed** (~8 min, 1753-frame clip), wrote a real per-frame ball-position CSV. Its column names (`Frame,Visibility,X,Y`) are a subset of the k14 CSV's, so `src.tracknet.load_predictions` parses it directly — no adapter code needed.
- **First real benchmark, on `brickwall_30fps`** (`--eval_mode nonoverlap` for speed, ~15.5 min for the full 25.2-min video), scored through the identical `court_wedge → crossing_times → cluster_crossings → match_intervals` pipeline, same `gap_sec=3.0`/`min_crossings=6`, same labels as k14: **TrackNetV3 0.694 precision / 0.971 recall**, vs. k14 shipped 0.64/0.80 and k14 adaptive-gap 0.76/0.91. Beats the shipped config on both metrics; beats even the adaptive-gap version on recall (missed only 1 of 35 real rallies); precision trails the adaptive-gap version.
- **This is one video, the cleanest one in the project, picked for exactly that reason** — not a decision, a promising first data point. It's also a *detector* result, not a downstream one: it can't touch PIC-31's dominant remaining failure mode (the ball genuinely, correctly crossing the net during dead time), since that's a downstream-logic problem no detector improvement can fix in principle.
- Filed as Linear **PIC-47**, with the brickwall result as a comment. Next: same run on `pb_draft_cup`/`IMG_7744` before this means anything conclusively; before shipping (not before benchmarking), resolve the weight-license gap — the checkpoints are pretrained on badminton data, code is MIT, but the weights' own redistribution/usage terms are undisclosed, same gap already flagged for PIC-46's fine-tuning candidates.

## Segment classifier (PIC-46) — training code added, dev-only leave-one-video-out result

- The orphaned worktree's `segment_classifier.py` had feature extraction done (candidates at `min_crossings=1`, labelled TP/FP by the same IoU≥0.5 match `eval/harness.py` uses, features = duration/crossing_count/crossing_rate plus the frozen `src/events.py` player-position signals) but no model-fitting step. Added it: leave-one-video-out CV across the three `dev` sessions, comparing a trained classifier (logistic regression and gradient-boosted trees) against the shipped `min_crossings≥6` heuristic on the same candidate pool.
- **Result: real ranking ability, miscalibrated default threshold.** Average precision (threshold-independent) is 0.63–0.94 — the classifier genuinely separates TP from FP by score. But at the default 0.5 cutoff, recall collapses specifically on IMG_7744 (0.65→0.20 logreg, →0.05 hgb) while roughly matching the heuristic on brickwall/pb_draft_cup. Consistent with the already-documented finding that IMG_7744's false positives are a structurally different mechanism (real failed exchanges, not background clutter) — one fixed threshold doesn't cover both.
- **Not yet a candidate to ship**: needs a properly cross-validated decision threshold (picked from training folds only, never touching held-out or `eval`) before its precision/recall numbers mean anything comparable to the heuristic's.
- Landed on `main` as `scripts/segment_classifier.py`. Recorded on Linear PIC-46 with the full per-video table.
