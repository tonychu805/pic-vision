# 2026-09-06

**Started from a commercial-venue-readiness question and turned it into two real security fixes, plus two real bugs found along the way (`DECISIONS.md` ADR-082).** Operator asked "is the current design capable of accommodating a commercial sports venue?" -- answered directly (not just reassured), surfacing concrete gaps: plaintext camera/session/agent credentials, no way to revoke a lost device's access, no spend controls, no staff roles, no billing, an unpackaged installer, and unvalidated detection accuracy off the operator's own known cameras. All logged as Linear tickets (PIC-79 through PIC-85) before any code was written, since the operator explicitly wanted docs/Linear updated before exploring further.

**Built and shipped the console's agent Disconnect/revoke control first, since it's cheaper than encryption and covers a scenario encryption alone doesn't (a stolen laptop that's already unlocked).** New `POST /api/agents/[id]/revoke` (cookie-session authenticated, scoped by `brand_id` in the query itself), a "Disconnect" button + confirm dialog on the Overview page. Verified against real production infrastructure, not synthetically: revoked the operator's one real agent, confirmed the old token got a genuine `401` from the live heartbeat endpoint.

**QCing that feature -- deliberately tracing every other reader of the state it changed, not just the happy path -- found two real, separate bugs, both fixed same day:**
1. The Cameras page had no `status != 'unpaired'` filter on its agent lookup (Overview already did). A revoked device's cameras kept showing up normally, and Start/Stop recording on one would queue a command that could never be picked up -- no error, just a silently stuck `pending` row. Fixed in both the page's initial query and its client-side poll (which had no agent filter *at all*, relying purely on RLS).
2. Restoring the revoked connection through the actual app kept failing with a generic `TypeError: fetch failed` on the "Connect to the cloud console" button -- reproduced by the operator too, not just automation, so it was real. Chased it all the way down: `cloud.js`'s `DEFAULT_CONSOLE_URL` defaulted to `http://localhost:3000` (backwards from `auth.js`'s own Supabase URL/key, which correctly default to production). `registerDevice()` -- the function behind that button and the auto-register-at-launch check -- has no stored console URL to fall back on and hit this default directly; every other call site had always had a real one to reuse, which is why this had silently never been exercised since ADR-079 shipped it. Confirmed with plain Node's own `fetch` succeeding against the same hosts at the same moment before finally reading the actual default-parameter value and finding the real cause. One-line fix (default flipped to the real production console URL), verified by actually clicking the real button afterward and watching it succeed for the first time.

**Then closed out the other half: OS-vault encryption for the three plaintext secrets (`electron/secureField.js`, PIC-79).** Wraps Electron's `safeStorage` (OS keychain/credential-manager/Secret-Service), with a real plaintext fallback when no vault is available rather than throwing -- confirmed this sandbox's own vault *is* available by watching real encrypted values (`enc:v1:` prefix) land on disk. Applied to camera password/streamUri, the Supabase session tokens, and the agent's long-lived API token, centralized at one read/save choke point per file rather than scattered across call sites. Legacy plaintext values already on disk keep working (read as "no prefix means already plain") and migrate to encrypted form the next time anything naturally rewrites that store -- proved this by triggering a no-op camera rename and confirming both real cameras (Synology, Tapo C200) still connected fine through the decrypt round-trip afterward.

**Filed two smaller findings rather than fixing them today:** PIC-86 (revoking an agent mid-recording has no remote stop path now that ADR-080 removed the desktop's local controls -- a real design decision, not a quick fix) and PIC-87 (the operator's one real device's local `deviceId` had already drifted from the server's on-file `device_id` before any of today's testing, for reasons still unknown -- caused one harmless duplicate agent row).

Verified: `tsc --noEmit` clean on the console after each change, `node --check` on every touched desktop file, and everything above checked against the operator's real running app and real production Supabase project -- not mocked.

**Two more real usability fixes to Scan settings, both operator-requested and verified live.** Removed the "Previews" panel entirely (accurate but pointed elsewhere, didn't belong on a settings page). Then reduced real friction in the Ranges "Add" flow: it now accepts a single camera IP (e.g. `10.20.5.37`) and auto-expands it to a `/24` around it, since most people know one camera's actual address (its own settings screen, or the vendor's app) but not the CIDR notation for the block it lives in; also added a live "= N addresses" / "too many, narrow this" hint as you type, reusing `networkSweep.js`'s own `MAX_HOSTS` cap so an oversized range is caught before clicking Add rather than after a failed round-trip. Also added a venue network-setup guide (`desktop/README.md`, plus a collapsed pointer in the Scan settings UI itself) for the case where ONVIF discovery needs to cross a VLAN -- explains why that's structurally impossible without a network-side fix (multicast doesn't route), and what to actually ask a network admin for (IGMP proxy/multicast routing, or a relay device).

**Closed with a full security/UX audit of the desktop agent design, at the operator's request, before deciding what to build next.** Went through the whole app-console-database chain looking for what's real progress vs. what still isn't there, verifying claims against actual code rather than general impressions -- two verified true, one verified false along the way (the read-only recording view *does* already explain itself with "start it from the cloud console," better than initially assumed). Filed six new Linear tickets for what's real and not yet fixed: PIC-88 (agent token never expires/rotates), PIC-89 (no rate limiting on bearer-token endpoints), PIC-90 (no audit trail for revoke/register actions), PIC-91 (no size cap on `agent_commands`' JSONB columns), PIC-92 (the Cloud page's "Connected" status reflects "a connection is stored," not "the last heartbeat actually succeeded" -- found while testing the Disconnect feature, not yet fixed), and PIC-93 (raw thrown error text like `"TypeError: fetch failed"` gets shown straight to the user -- literally what made today's `DEFAULT_CONSOLE_URL` bug confusing to debug live). PIC-92/93 marked High -- of everything found today, these two are the most likely to actually confuse a real operator.

**Later the same day: a full codebase review (structure, security, aesthetics) across all four subprojects, and it found something worse than anything in the morning's audit (`DECISIONS.md` ADR-083).** The review checked the live Supabase RLS policies directly instead of trusting the code comments about them, and the `reels` table's share-link policy turned out to be `USING (true)` for the public anon role -- meaning anyone with the anon key (which is bundled into every browser client on purpose) could list every reel in every venue, share ids and video URLs included. Verified against production: one unfiltered request returned all three rows. The "you have to know the share id" protection the code described never existed. Two neighbours on the same path: the operator's email was being published as the venue name on the public share page (a sign-up fallback that got copied onto reel rows and then went stale when the brand was renamed), and the route the desktop agent uses to report a finished reel accepted whatever ids and object keys it was handed, so one venue's agent could add a slide to another venue's share page. All three fixed in code today: share pages now read through a database function that returns rows for one known share id only, brand names are joined live and never an email, and the report route checks ownership and pins the object key to the reel's own id. The console side is committed; **the production migration and reel-page deploy are waiting on operator approval** (the auto-mode classifier blocked both the DDL and the reel-page commit -- exact steps, in the order that matters, are in PIC-94).

Everything else from the review is filed rather than fixed (PIC-95 through PIC-108), with the desktop's two real problems at the top: yesterday's at-rest encryption is undone the moment the UI loads (decrypted camera passwords and the cloud API token are handed straight to the renderer, and RTSP passwords render on screen with a Copy button -- PIC-97), and Electron 33 is end-of-life, eleven major versions behind (PIC-98). The process boundary itself checked out well (context isolation, sandbox, no shell execution, encrypted at rest, zero npm vulnerabilities), the console's auth model is correctly implemented everywhere except that one policy, and the Python side has no security holes for its scope. One small hygiene fix landed directly: the documented `make test` had been silently aborting before running a single test (it collected `archive/tests/`, which imports retired code) -- a two-line `pytest.ini` fixes it, and the real suite is 132/132 green.

**Operator noticed the Schedule page showing 8 cameras instead of 4.** Cause: the revoked ghost agent from yesterday (PIC-87) still owns four stale camera rows, and the Schedule pages were the one place that never got the `status != 'unpaired'` filter ADR-082 added to Cameras. **Then a design pass over the desktop app's four tabs, prompted by the Cloud console tab being confusing to use.** The specific complaint was that everything on it looked equally editable when only one field actually is -- and the same problem turned out to run through the whole app. Fixed on that tab first (the one thing you can change is up top; the account, device id, and connection facts moved into a plainly read-only block, and the device id stopped being a text box you can click into but not type in), then the other three tabs were reviewed the same way and the whole list worked through.

**Four of the findings were real bugs, not taste.** Scanning the network and finding nothing left a completely blank page -- the illustrated "here's what to do" screen only ever showed *before* the first scan, so the one moment with most to explain showed least. The Stop button during a scan only hid the progress bar; the results still arrived seconds later and repopulated the list. In the log, the detail line -- which is where the reason for a failure lives -- was clipped to one line with no tooltip and no way to expand it. And the sidebar had been claiming "Scanning this network for cameras" ever since automatic scanning was removed on 2026-09-03, which is simply not something the app does any more.

**Several things were saying something other than what was true.** A camera that merely answers a connection test was labelled "Streaming", which invites a venue owner to believe footage is being captured when recording is started from the cloud console entirely -- now "Online". The camera detail page had grown three separate "…from the cloud console" dead ends with no way to actually get there; they're one line now, with a button that opens it (which needed a small, protocol-restricted "open a link in the browser" bridge on the Electron side). Clearing the log -- the only record of what the pipeline did, with no undo -- took one click of a button in the corner, while removing a camera two pages over correctly takes two; it now matches. Removing a camera also sat in the top-right corner in the same styling as the harmless "Live view" button, and has moved to the bottom of the page.

**The palette had no way to say "this failed".** Both of Nocturne's accents are purple, so a failed pipeline job, a finished one, and a camera going offline were drawn in nearly the same colour and the log couldn't be scanned. Added three semantic colours tuned to sit in the existing dusk range, and the log, the camera status tags, the frame-rate warning and every error message now use them.

**Underneath all of it, the app had a design system nobody had written down.** The Nocturne handoff shipped tokens and component classes but nothing page-level, so every page hand-rolled its own shell, cards, section headings and muted text as inline styles -- the same muted grey retyped 23 times across 9 files, page padding that had drifted three different ways, and 17 distinct font sizes, several a half-pixel apart. Those are now five named patterns and a five-step type scale in the stylesheet, and the pages use them. Also folded "Scan settings" out of the sidebar: it existed only to configure the Cameras page's Scan button, which isn't top-level standing, and it now opens from next to that button (renamed "Scan options", one column instead of a two-column grid whose right half was one field beside a void, and it confirms when a setting saves).

**Not verified by eye.** All of this builds clean and the 18 main-process tests pass, but the app hasn't been launched to look at it -- there's no browser-automation tooling on this machine and reaching most of these screens needs a signed-in session and real cameras. A click-through is the obvious next step, and it overlaps with the click-through the cloud-pipeline work already needed.

**Finally, asked whether the desktop agent is ready to be packaged, and the answer was no — for a reason worth fixing on the spot (`DECISIONS.md` ADR-088).** Checked the three known concerns against the code rather than the tickets. The serious one held up: last week's work encrypted camera passwords and the cloud token so a stolen laptop couldn't give up a venue's cameras — and then the app handed all of it back to its own interface, decrypted, on every screen refresh. The encryption was protecting the hard disk and nothing else. Anyone who could open the app could read every camera password. That was survivable while the app only ran on the operator's own machine; it stops being survivable the moment there's an installer going onto machines at venues, around staff and contractors.

**Fixed by keeping secrets in the part of the app that needs them.** Passwords no longer travel to the interface at all, and the stream address — which for some cameras has the username and password written into it — now shows with those starred out. The "Copy" button still puts a working address on the clipboard: it asks for the real one at the moment you click, so the credentials exist for a second rather than for the whole session. Recording, calibration and the cloud sync are untouched; they run in the part of the app that legitimately holds the credentials.

**The test written to lock this down immediately caught a second leak in the fix itself** — a password containing an "@" (allowed, and it happens) left the tail of itself visible on screen. Worth noting because the first version looked right and the app behaved identically either way; that is exactly the kind of fix a later change undoes without anyone noticing, which is why it's pinned by a test that checks the password appears nowhere in the whole record rather than in the fields someone thought to check.

**Still blocking a package, both unchanged:** the app is built on a version of its framework that stopped receiving security updates a long time ago, and none of the interface work from today has been opened in the running app even once — it compiles and its background logic is tested, but nobody has clicked through it. A packaged installer is the worst possible place to discover a screen that doesn't load.

**Then started production packaging of the desktop app, and it turned out not to be a packaging problem at all (`DECISIONS.md` ADR-084).** The operator wants a v1 that pilot venues can install on a Mac. The blocker wasn't code-signing or build config -- it was that the app ran the entire cloud pipeline locally: the "send to cloud" button spawned Python that uploaded to R2 with the operator's own storage keys, created a GPU pod with the operator's RunPod key, and SSH'd into it. **What was built instead: the venue's machine only does what has to happen near the cameras.** It records, manages cameras, grabs a calibration frame, and uploads the raw recording to storage using one-time upload links the cloud console hands out. Processing happens on the operator's own workstation, which polls the console for queued work and runs the existing pipeline completely unchanged. The venue machine now holds no credentials, no Python, and no SSH -- there is nothing on it worth stealing. Calibration moved the same way (the maths needs OpenCV, so it runs on the operator's machine and the result is stored against the camera in the cloud, not as a file on the venue's disk). The progress display the operator already knew was kept exactly as-is, just fed from the cloud instead of from a local process, so nothing in the interface had to change.

**Then the day's most consequential finding, and it started as a throwaway question about camera compatibility.** Asked whether field cameras generally support H.264, which led to checking what the system actually knows about its cameras -- and the answer was nothing. No codec, resolution, frame rate or bitrate was recorded anywhere. Pulling that thread found that `config.yaml` has said `fps: 30 -- confirmed once at setup` since the beginning, but **nothing has ever confirmed it, and no such step exists in venue setup**. Court 1 was then measured at exactly 15 frames per second: 9,000 frames in 600 seconds. Court 2's own camera profile also said 15. Both real cameras were running at half the rate every detection setting was tuned for.

**Measured what that actually costs rather than guessing (`EXPERIMENTS.md`).** Took five minutes of labelled footage, made a 15fps copy by dropping every other frame, and ran both through the full pipeline -- same calibration, same labels, same settings, only the frame rate different. 30fps found 8 rallies of which 6 were right; 15fps found 5 of which 3 were right. **Half the rallies lost.** Then tried to buy them back by loosening the detector, and couldn't: even at the loosest setting recall never reached the 30fps baseline while precision collapsed and false alarms went up six-fold. The information simply isn't there at half the frame rate.

**So 30fps became a requirement rather than advice (`DECISIONS.md` ADR-086/087), enforced in four places.** The app now measures what each camera is really sending -- codec, resolution, frame rate and bitrate, all from a single cheap probe that never decodes a frame -- and refuses to record or calibrate a camera below the floor, naming the camera's own address and the setting to change. Crucially it tells two different faults apart: a camera *set* to 15 gets "change this setting", while a camera set to 30 that only delivers 15 gets "your settings are fine, this is a network problem" -- sending someone to change a correct setting wastes their time and costs trust. The tracker's own distance threshold, which silently assumed 30fps and was throwing away genuine fast-ball movement at lower rates, now derives from the measured rate too.

**And the same check now guards the cloud job itself, which is where the money is.** A camera can start a session fine and degrade partway through -- indoor light falling is the usual cause, since cameras lengthen exposure and drop frame rate to compensate, and evening is exactly when a venue is busiest. Nothing checked the actual recording before spending on it. Now the first thing a job does is profile the recording's frame rate in 30-second windows and refuse it before the conversion, the upload or the GPU machine. It costs a third of a second on a 21-minute file. It reports *where* the problem is rather than one average, because a flat low rate (camera configured wrong, whole session affected) and a mid-session sag (conditions changed, part of the session affected) need opposite responses and average to the same number.

**Several real bugs were caught by building the failing case instead of reasoning about it, which is worth recording as a pattern.** The frame-rate probe originally trusted the video file's own declared rate -- which lies, because recording copies the camera's stream through untouched and inherits whatever the camera claims; it would have returned 30 for exactly the 15fps case it existed to catch. The rate was first averaged across the whole sample, which under-reads an RTSP stream's slow start and would have told a venue their working Wi-Fi was faulty. The job gate first passed or failed on the median, and a synthesised session that ran 30fps for half its length and 15 for the other half sailed straight through. A text-range edit to the recording module silently deleted six exports and broke the app entirely -- `node --check` passed, because a missing export is only an error when something tries to import it. That last one prompted the desktop app's first automated tests, which now number 17 and have since caught two further mistakes of their own.

**Open, and unchanged by today:** the DMG still hasn't been built, and almost none of the new desktop code has been exercised in the running app -- it's been verified at module level and against real storage, but not clicked through. Starting the job runner and putting one real session through the new path would be worth more than any further hardening.
