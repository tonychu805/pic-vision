# 2026-09-06

**Started from a commercial-venue-readiness question and turned it into two real security fixes, plus two real bugs found along the way (`DECISIONS.md` ADR-082).** Operator asked "is the current design capable of accommodating a commercial sports venue?" -- answered directly (not just reassured), surfacing concrete gaps: plaintext camera/session/agent credentials, no way to revoke a lost device's access, no spend controls, no staff roles, no billing, an unpackaged installer, and unvalidated detection accuracy off the operator's own known cameras. All logged as Linear tickets (PIC-79 through PIC-85) before any code was written, since the operator explicitly wanted docs/Linear updated before exploring further.

**Built and shipped the console's agent Disconnect/revoke control first, since it's cheaper than encryption and covers a scenario encryption alone doesn't (a stolen laptop that's already unlocked).** New `POST /api/agents/[id]/revoke` (cookie-session authenticated, scoped by `brand_id` in the query itself), a "Disconnect" button + confirm dialog on the Overview page. Verified against real production infrastructure, not synthetically: revoked the operator's one real agent, confirmed the old token got a genuine `401` from the live heartbeat endpoint.

**QCing that feature -- deliberately tracing every other reader of the state it changed, not just the happy path -- found two real, separate bugs, both fixed same day:**
1. The Cameras page had no `status != 'unpaired'` filter on its agent lookup (Overview already did). A revoked device's cameras kept showing up normally, and Start/Stop recording on one would queue a command that could never be picked up -- no error, just a silently stuck `pending` row. Fixed in both the page's initial query and its client-side poll (which had no agent filter *at all*, relying purely on RLS).
2. Restoring the revoked connection through the actual app kept failing with a generic `TypeError: fetch failed` on the "Connect to the cloud console" button -- reproduced by the operator too, not just automation, so it was real. Chased it all the way down: `cloud.js`'s `DEFAULT_CONSOLE_URL` defaulted to `http://localhost:3000` (backwards from `auth.js`'s own Supabase URL/key, which correctly default to production). `registerDevice()` -- the function behind that button and the auto-register-at-launch check -- has no stored console URL to fall back on and hit this default directly; every other call site had always had a real one to reuse, which is why this had silently never been exercised since ADR-079 shipped it. Confirmed with plain Node's own `fetch` succeeding against the same hosts at the same moment before finally reading the actual default-parameter value and finding the real cause. One-line fix (default flipped to the real production console URL), verified by actually clicking the real button afterward and watching it succeed for the first time.

**Then closed out the other half: OS-vault encryption for the three plaintext secrets (`electron/secureField.js`, PIC-79).** Wraps Electron's `safeStorage` (OS keychain/credential-manager/Secret-Service), with a real plaintext fallback when no vault is available rather than throwing -- confirmed this sandbox's own vault *is* available by watching real encrypted values (`enc:v1:` prefix) land on disk. Applied to camera password/streamUri, the Supabase session tokens, and the agent's long-lived API token, centralized at one read/save choke point per file rather than scattered across call sites. Legacy plaintext values already on disk keep working (read as "no prefix means already plain") and migrate to encrypted form the next time anything naturally rewrites that store -- proved this by triggering a no-op camera rename and confirming both real cameras (Synology, Tapo C200) still connected fine through the decrypt round-trip afterward.

**Filed two smaller findings rather than fixing them today:** PIC-86 (revoking an agent mid-recording has no remote stop path now that ADR-080 removed the desktop's local controls -- a real design decision, not a quick fix) and PIC-87 (the operator's one real device's local `deviceId` had already drifted from the server's on-file `device_id` before any of today's testing, for reasons still unknown -- caused one harmless duplicate agent row).

Verified: `tsc --noEmit` clean on the console after each change, `node --check` on every touched desktop file, and everything above checked against the operator's real running app and real production Supabase project -- not mocked.

**Two more real usability fixes to Scan settings, both operator-requested and verified live.** Removed the "Previews" panel entirely (accurate but pointed elsewhere, didn't belong on a settings page). Then reduced real friction in the Ranges "Add" flow: it now accepts a single camera IP (e.g. `10.20.5.37`) and auto-expands it to a `/24` around it, since most people know one camera's actual address (its own settings screen, or the vendor's app) but not the CIDR notation for the block it lives in; also added a live "= N addresses" / "too many, narrow this" hint as you type, reusing `networkSweep.js`'s own `MAX_HOSTS` cap so an oversized range is caught before clicking Add rather than after a failed round-trip. Also added a venue network-setup guide (`desktop/README.md`, plus a collapsed pointer in the Scan settings UI itself) for the case where ONVIF discovery needs to cross a VLAN -- explains why that's structurally impossible without a network-side fix (multicast doesn't route), and what to actually ask a network admin for (IGMP proxy/multicast routing, or a relay device).

**Closed with a full security/UX audit of the desktop agent design, at the operator's request, before deciding what to build next.** Went through the whole app-console-database chain looking for what's real progress vs. what still isn't there, verifying claims against actual code rather than general impressions -- two verified true, one verified false along the way (the read-only recording view *does* already explain itself with "start it from the cloud console," better than initially assumed). Filed six new Linear tickets for what's real and not yet fixed: PIC-88 (agent token never expires/rotates), PIC-89 (no rate limiting on bearer-token endpoints), PIC-90 (no audit trail for revoke/register actions), PIC-91 (no size cap on `agent_commands`' JSONB columns), PIC-92 (the Cloud page's "Connected" status reflects "a connection is stored," not "the last heartbeat actually succeeded" -- found while testing the Disconnect feature, not yet fixed), and PIC-93 (raw thrown error text like `"TypeError: fetch failed"` gets shown straight to the user -- literally what made today's `DEFAULT_CONSOLE_URL` bug confusing to debug live). PIC-92/93 marked High -- of everything found today, these two are the most likely to actually confuse a real operator.
