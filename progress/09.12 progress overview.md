## Reel share page: top 10 individual rallies, ranked, now lead the page

Operator request: reorder the reel share page to lead with the top 10 individual rallies (ranked by score, not chronological order), then the existing 30-second "quick hits" burst clip, then a full reel — cut down from 5 minutes to 3. Confirmed up front to build this for real rather than behind a flag (this project's usual mode, no staging environment), and to show however many rallies qualify when fewer than 10 clear the bar, rather than padding or hiding the section.

**Most of the hard part already existed.** The full reel has ranked every candidate rally by score since ADR-063, and already cut each one to its own file before concatenating them into one reel — the individual clips existed for a moment on every single run and were thrown away. The new piece (`scripts/top_rallies_reel.py`) reuses that exact ranking and cutting logic, just skips the concatenation step and hands back the top 10 clips in score order instead of one file.

**Wired into both places a reel gets cut** — the live SSH-driven path (`cloud_pipeline/pod_cut.py` / `run_cloud_job.py`) and the newer self-driving pod path from last week's ADR-093 work (`pod_driver.py`), which isn't live for real venue sessions yet but would have silently drifted out of sync with the live path if only one got this. The two differ on one real detail: full and burst are always exactly one file (or zero), so their upload IDs get minted before the pod even starts; the top-10 clips are a variable count depending on the session, so each one mints its own ID only once cutting is done and the real count is known.

**Touched the live production database.** A new `kind='rally'` reel type, a `rally_rank` column, and the share page's lookup function rewritten to order rally clips (by rank) first, then burst, then full — replacing an ordering that only worked by accident (it happened to always report "full" first). Applied directly via migration, checked against the live schema afterward rather than assumed.

**Verified rather than trusted:** full test suite (158 passing, 3 new), `tsc --noEmit` clean on both the cloud console and the public share page app, and a real run of the new cutting logic against real cached footage (`brickwall_30fps`) — 10 real, playable video clips came out, confirmed with `ffprobe`, in the right score-descending order.

**What's still open:** no real venue session has actually gone through either pipeline path with this change yet — everything above is built and directly verified, not yet confirmed on a live booking. Full writeup: `DECISIONS.md` ADR-102.

## Two real bugs, found by actually trying "Send to cloud" live

Operator tried the console's "Send to cloud" button (sample-clip camera, PIC-136 follow-up from 09-10) and hit a real, immediate failure.

**Bug 1: the button never worked at all.** The Sep 10 commit that added `send_to_cloud` to the app's own list of valid command types never widened the database's matching check constraint — every click failed with a bare Postgres constraint-violation message. Fixed with a migration (`agent_commands_type_check` now includes `send_to_cloud`), applied to the live database and verified.

**Bug 2, surfaced right after: the "3-minute reel" change from earlier today wasn't actually live for this path.** The real trigger for both a scheduled auto-send and this manual button never goes through the Python call sites fixed earlier — it's `desktop/electron/cloud.js` posting a literal `targetSec: 300` straight to the console API, which lands in the job row before `job_runner.py`'s already-fixed fallback ever gets a say. Three more sites corrected (`cloud.js`'s literal, `pipeline.js`'s own fallback, the API route's fallback) — this is exactly the kind of claim that needed checking against the real, live path rather than trusted from the Python side alone, and it's now recorded as a correction in `DECISIONS.md` ADR-102, not a silent edit.

**Bug 3: the console let the same camera be sent to the cloud twice.** With the job now actually running, the operator noticed the desktop app showed "waiting for processing" while the console's own button was still clickable — nothing stopped a second click from queuing a second, separately-billed job for the same recording. Fixed: the button now polls for any in-flight job for that camera and disables itself while one exists, plus a short local guard for the few seconds between clicking and the desktop agent actually picking the command up. See `DECISIONS.md`, "PIC-141".

All three verified against the real, live database and running job for the actual camera involved (Sample 1), not just against local tests.
