# 2026-09-18

## A pass over the desktop app found two real bugs, both now fixed

Ran the desktop agent (1.3.0) the way an operator would, on this workstation, and checked what the console's own database said at each step rather than trusting the screen. Deliberately left out: anything that would pull video from the two real cameras (they're still not pointed at a court), and "Send to cloud", which starts a billed GPU job. 87 of 87 automated tests passed before any of this.

**A mistyped camera address froze the Add dialog for about 15 minutes.** Typed an address with nothing on it. "Connecting…" for ~2 minutes, then "Looking for a video stream…" — a step with no Cancel button — for ~13 more, ending with advice to check the camera's ONVIF setting, which is the wrong advice for a typo. Two separate causes, both measured rather than guessed:

- `rtspProbe.js`'s 2.5s timeout never applied while connecting. The timeout listener only settled an in-flight request, and during connect there isn't one, so the wait fell through to the OS's own limit — **134 seconds, timed directly** — and the path ladder does that seven times. Confirmed the timeout event does fire on schedule (2.505s) and was simply being dropped.
- The `onvif` library defaults to **120 seconds** per request, which is the ~2 minutes before the ladder even started. Now 10s, which is generous for a camera on the venue's own LAN.

The same input now fails in **30 seconds**, end to end, checked in the running app. Three new tests cover it, including one that pins the connect-phase case the old code missed.

**A calibrated camera showed "Not calibrated" right after launch.** Court 3 read "Not calibrated" on screen while the console's database (checked directly) said it had been calibrated since 2026-09-06 — and the app's own background process agreed it was calibrated. The camera list is read before the first heartbeat answers, and nothing on the detail page re-read it afterwards; the Refresh button sitting right beside the calibration line only refreshed recordings. For a real camera this also disables "Send to cloud" and relabels it "Calibrate first".

Verified properly rather than by eye: pointed the agent at a local relay that held its first heartbeat back by 20 seconds, which reproduces the launch window on demand. **With the fix** the page showed "Not calibrated" and then corrected itself to "Calibrated — 0.55 ft" with no navigation. **With the fix stashed, same conditions**, it stayed wrong through two heartbeats and a Refresh click. Local state (console URL, cameras) restored afterwards.

**Filed, not fixed:** renaming a camera hides every recording it already has (`PIC-149` — label-keyed folders, the same keying that already caused one bug; Court 1 has 2 recordings that would vanish); Court 2 measures 52 fps while the camera reports 30, and the 30fps gate trusts the measured number (`PIC-150`, mechanism suspected but not confirmed); internal "Error invoking remote method…" text reaching operators plus the wrong ONVIF advice (`PIC-151`); a scan that finds nothing giving no feedback, and four wording fixes (`PIC-152`). The desktop renderer's missing CSP went as a comment on `PIC-146`, which already covers the same gap in the web apps.

**Not tested, and worth knowing:** everything involving real-camera video (live view, recording, calibration, re-entering a password), "Send to cloud" and Retry, the destructive actions (sign out, remove machine, remove camera), and all the macOS-only behaviour — this was the dev build on Linux, not the 1.3.0 DMG.

## PIC-150: the frame-rate estimator itself was the bug, not which reading wins

Operator asked whether frame-rate reading should move off the local device (it can't -- the venue machine is the only thing that can reach the camera, by design; ADR-071 is outbound-only, nothing dials in). Looked at whether the cloud-side check should be trusted instead, and the more useful answer turned out to be that the local number itself was wrong.

**Confirmed the estimator, not the camera, was misbehaving.** The live-stream frame-rate probe estimated fps from the *median* gap between consecutive packet timestamps -- chosen specifically to stop a slow RTSP start from under-reading a real 30fps camera as ~24.9. But a median only tells you the *typical* gap, not the *average* one: a camera whose packet spacing genuinely alternates short and long -- 20ms, 47ms, 20ms, 47ms, averaging 33.5ms per frame, a true ~29.85fps -- has its median sitting on the 20ms side, reading ~50fps. Reproduced exactly with synthetic packet times (no live camera touched): the same alternating pattern that measured 51.55fps and 49fps on Court 2 this week reads 29.92fps under the fix.

**The fix keeps the slow-start correction without the median's blind spot.** `estimateFpsFromPacketTimes` (new, pure, in `capture.js`) discards packets within the first second of the sample, then computes frames over the remaining span -- immune to the *order* gaps arrive in, since frames-over-span only cares about count and span, not which gap is more common. Verified against the shape that mattered: steady 30fps reads 30.00; a slow RTSP start (sparse first second, steady 30fps after) still correctly reads 30.00, not the naive 24.9; a real mid-stream stall correctly reads *down*, which is honest rather than a regression -- a median would have hidden it. 9 new tests, all synthetic data per the project's standing rule against pulling live frames or streams from real cameras to verify code.

**Deliberately did not also change which measurement source the recording gate trusts.** The original plan was to prefer the post-recording file measurement over the live probe, on the theory that "which source wins" was the problem. It wasn't -- the estimator was wrong regardless of source, and a correct estimator should make live and file-based readings converge on their own. Re-architecting the source-preference logic on top of that would have been solving a problem with no remaining evidence behind it; left alone unless a live camera, after this fix, still shows real instability.

Also checked the cloud-side check (`src/video_quality.py`) for the same bug: it doesn't have it. It already buckets frames by time window rather than taking a median gap, and its own comments record it already learned a related lesson (a median hid a bad 2-minute stretch inside an otherwise-good session) and moved off medians before this session started.

115 desktop tests passing (9 new).

## Two more fixes off the same list: the rename bug, and a finished reel that could be lost

**Renaming a camera no longer hides its recordings (`PIC-149`).** Recording directories were named after the camera's label, so a rename pointed both `startRecording` and `listRecordings` at a directory that did not exist: the files stayed on disk under the old name and vanished from the camera's page, taking the "Send to cloud" row with them. Two cameras sharing a label also shared a directory, which had already caused one real bug.

Directories are now keyed by camera id, which a rename cannot touch. The awkward part is the machines that already recorded under the old layout — a fix that only changed new writes would strand those permanently, so there is a one-time move at startup, written as a pure function (`planRecordingDirMigration`) precisely because its edge cases need testing: already migrated, two cameras sharing one label (first in list order takes it; their recordings were commingled and attributing them afterwards would be invention), and a sample clip whose absolute stored path points inside the directory being moved.

Ran for real on this workstation: `Court_1`, `Court_3` and `Court_4` moved to their id-named directories, both sample clips' stored paths rewritten, and Court 1's 2 recordings survived a rename and a rename back — 2, 2, 2. The pre-fix behaviour (2 → 0) is from reading `capture.js:378`, not from re-running it.

**A finished reel can no longer be lost to a console hiccup (pipeline).** `pod_driver.py`'s `patch_job` swallows every failure on purpose, so a running GPU job isn't abandoned over a network blip. That was also true of the *final* report — and by the time that one is sent, the reels are already uploaded to R2 and the console is the only thing that will ever know they exist. One 500 at that moment meant: pod self-terminates, `job_runner.py` marks the job errored ("pod disappeared without reporting"), its cleanup deletes the venue's uploaded segments, and the operator is asked to re-upload a session and pay for a second GPU job whose output is already sitting complete in the bucket.

Terminal reports (done / error / cancelled) now go through `report_final_job_status`, which retries ~63s with backoff and treats 409 as delivered rather than retrying a row that has already moved on. Progress reports stay best-effort, and a test pins that half of the contract too, since collapsing the two would be the obvious wrong simplification.

165 Python tests and 98 desktop tests pass.

**Still open from the same list:** `PIC-150` (the 52 fps reading — needs a live-stream check on a real camera, so it needs the operator's say-so first), `PIC-151` (wrong ONVIF advice and raw IPC error text), `PIC-152` (silent scan plus wording). And one that isn't a code change: push a byte-identical backup tag of `tf215-cuda118` to Docker Hub, the only image RunPod reliably starts — attempted here and correctly blocked as an outward-facing action, so it's an operator command.

## PIC-93: the cloud console's own connection errors were the last raw-text screen left

Closed a nine-day-old ticket (filed 2026-09-05) rather than opening a new one. Camera errors were already fixed back then (probeResult.js's classification); CloudPage's own "Connect to the cloud console" flow was the one place that never got the same treatment, and today's error-cleanup work touched this exact file, so it was the natural next thing.

**Why a message-text guess wasn't good enough here**, unlike the camera fixes and today's earlier PIC-151 work: a server error from the console API is very often a raw, unmarked Postgres error string (PIC-144, still open on the console side) with nothing in the wording to tell it apart from a real, addressable 4xx. Guessing from text alone would get exactly the case that matters most wrong. The classification has to happen where the HTTP status still exists -- in `cloud.js`'s `registerAgentOnce`, on the main-process side -- which throws one of three short, deliberate words (`network`/`auth`/`server`) instead of the real message, and puts the real message in the Log tab via `logEvent`, the same split `probeResult.js` already established for camera failures. `ipcError.js`'s new `describeRegisterError` maps each word to a real sentence; anything unclassified still shows something real rather than being guessed at or swallowed.

**Found and fixed a second, real gap while building this:** the fetch itself had no timeout at all. A console that accepts a connection and never answers would have left "Connecting…" on the button with no ceiling -- same shape of bug as this morning's `rtspProbe.js` fix, in a different call. Now bounded at 20 seconds, and a timeout is classified the same as any other network failure.

**Found the same way the bug was found** -- by actually running it, not by only reading the code: the first version of the fix's own happy-path test hung past the test harness's full budget, twice, for two different real reasons rather than a flaky test. First, a completed HTTP response leaves its keep-alive socket open on both ends, which `server.close()` alone doesn't touch (`closeAllConnections()` is the fix). Second, and the more interesting one: a successful registration starts the heartbeat loop as a real, permanent side effect of `registerAgentOnce` itself -- true before today, just never exercised by a test until this one, since no test for this file existed. The test now stops the loop it starts.

Considered and deliberately left alone: `saveAgentName`, `disconnect`, and `signOut`'s own error handling. Checked each against what can actually fail there -- a local store write, a local-only disconnect, and a sign-out whose own network call already swallows its failure -- and none of them can genuinely throw a network-shaped error in practice. Building classified messages for failures that don't occur would be inventing scenarios, not fixing a real one.

13 new tests (7 for the classification, against a real local server; 6 for the plain-language mapping). 126 desktop tests passing.

## Sample-clip cameras can no longer be booked for a recording

Operator's observation, and it was right: a sample clip is an uploaded file standing in for a camera, so there is nothing for a booked start time to capture. The whole stack allowed it anyway — the console's schedule page listed every camera, `dispatch_due_schedule_bookings` queued `start_recording` at the booked hour, and only the venue agent refused it (`desktop/electron/cloud.js`'s `runCommand`, which has always had that guard). So an impossible booking looked accepted and then failed silently, at the hour, where nobody was watching.

Fixed in three layers, because the first two are screens rather than rules: the overview still lists the camera (so it doesn't just disappear) but says "Sample clip — no live stream to record" in place of the Manage bookings button; its editor page explains instead of rendering a calendar; and a trigger on `schedule_sessions` refuses the row outright, since `lib/schedule.ts` inserts straight from the browser under RLS by design and a stale tab would otherwise still get through. The trigger fails open when no camera row matches — a booking can legally exist for a camera the database hasn't heard about yet.

Checked against the live database, not assumed: Court 3 (sample clip) is refused with the trigger's own message, Court 1 (rtsp) is still accepted, and the test row was deleted afterwards. `tsc --noEmit` and a production build are both clean. Console commit `43f7763`; the migration is already applied to production, so the UI wants deploying to match.

## PIC-153: raw venue footage was publicly readable -- split into a private bucket, every key now brand-prefixed

Found while doing the routine "check the R2 bucket ACL" item under PIC-146. It wasn't routine: `cdn.picvisionai.com` was an active custom domain on `test-ingest-runpod`, the same bucket holding raw, unprocessed venue camera footage (`ingest/<agent_id>/<job_id>/<name>`) -- and R2 custom domains expose the entire bucket, with no per-path scoping (confirmed against Cloudflare's own current docs, not assumed). Confirmed live with a content-free probe (a made-up key, no real footage touched): a clean 404, no auth challenge of any kind. Filed separately as PIC-153 rather than folded into PIC-146's routine closure.

**Structural fix, not a naming convention.** A private bucket (`pic-vision-ingest-private`, created via the Cloudflare API, confirmed private by default) now holds raw segments; the existing bucket keeps its custom domain and only ever holds what was always meant to be public -- reels, brand logos, calibration snapshots. `lib/r2Presign.ts`'s new `privateIngestBucket()` throws rather than silently falling back to the public bucket if its env var is unset -- a config mistake fails loudly instead of quietly reopening the hole.

**Every key now leads with the venue's brand id** (`lib/r2Keys.ts`, one module, one naming scheme, fully tested -- 10 new tests, since a typo here either breaks uploads or misfiles one venue's data into another's-looking path). Worth being honest about what this buys and what it doesn't: it is **not** the security fix -- R2 has no per-prefix access control, so a brand-prefixed key in the public bucket is exactly as guessable-or-not as before, and reels/logos/snapshots still rely on an unguessable id, unchanged from ADR-075. What it buys is operational: per-venue storage accounting, a clean single-prefix delete when a venue churns, lifecycle rules scoped per venue -- none of which existed before, since `jobs`/`reels` only carry `agent_id`, brand only reachable by a join.

**On the pipeline side**, `pod_driver.py` was reusing one bucket for both downloading raw segments and uploading the finished reel -- had to split into `BUCKET` (private, input) and a new `OUTPUT_BUCKET` (public, output), or the finished reel would have landed in the wrong bucket. Caught a second real bug making that change: the final status report's `reel_bucket` field still said `BUCKET`, which would have told the console the wrong bucket for every reel from here on -- fixed in the same edit, before it ever shipped. `job_runner.py` now refuses to create a pod at all for a job with no `brand_id` rather than guessing.

**Deliberately not touched:** `run_cloud_job.py`, the older SSH-driven path -- per its own docstring it was never run end-to-end with real inference and was never a live multi-tenant ingest path (an operator-invoked CLI uploading footage already on their own disk), so doubling this change's size to thread brand_id through a second, effectively-dead dispatch path wasn't worth it. A clear comment marks the gap if it's ever revived.

**Two things outside my reach, reported rather than worked around:** the WAF block rule meant as a stopgap for stray objects failed with a real Cloudflare permission error (this session's API token can read/create R2 resources but apparently can't write WAF rulesets) -- not the approval system this time, a genuine credential-scope gap. And checking what's actually exposed right now: **zero objects** currently sit under `ingest/` in the old bucket -- good news, not something to take as reducing the need for the fix, since the window it was exposed for was still real.

**One real consequence of shipping this:** the console repo auto-deploys to Netlify on push, and `privateIngestBucket()` requires `R2_PRIVATE_INGEST_BUCKET` to be set there -- which nothing in this session can do. Production "Send to cloud" is broken (loudly, safely -- a clear failure, not silent data exposure) until that one env var is set. Should have sequenced this before pushing rather than after; flagged prominently rather than buried.

Confirmed the workstation's own `pic-vision-runner.service` picked up the pipeline-side changes for real: the `pic-vision-runner.path` watcher built 2026-09-12 restarted it within moments of the edit landing on disk -- the exact safety net that same day's incident was built to prevent recurring.

37 console lib tests (10 new), 169 Python tests (4 new). Commits: `pic-vision-cloud-console` 75899d4, `pic-vision` (desktop/pipeline) 6348519.

## A stuck pod now retries itself once, on a spare copy of the image

Operator asked whether the pipeline falls back automatically if the image doesn't work. It didn't: the image was a hardcoded default, and the only automatic fallback in that file is for GPU type. A missing tag would have meant every job failing at container start, ~8 minutes of rented GPU at a time, until someone edited the line by hand.

Two failures turned out to share one remedy. The unexplained container-start hang (ADR-101, twice last week) looks identical from outside to a broken image — pod created, nothing ever checks in — and both times a human clicking Retry cleared it. So a stuck attempt is now retried once automatically, and the retry uses `tf215-cuda118-known-good-20260918`, a byte-identical copy of the only image RunPod has ever reliably started (same digest, confirmed on Docker Hub after the operator pushed it).

Kept tight on purpose: one retry rather than a loop; the 3-hour deadline is captured once and shared across both attempts, so a retry can't double what a venue waits or what a GPU bills; every attempt's pod is still terminated; and the failure reaches the console only once both attempts are spent, so a job rescued by the retry never flashes an error at the venue. This reverses the explicit "does not auto-retry" call in ADR-101 — recorded there as a dated update rather than changed quietly, since the original reasoning was deliberate and is now only half right.

Three tests cover the shapes that matter: stuck twice (two pods, two different images, one error), stuck then rescued (no stuck-container error reported at all), and checked in normally (exactly one pod — getting that wrong would double the GPU bill on every successful run). 167 Python tests, 106 desktop.

## A VLM doing tennis analytics — reviewed, and both halves recorded

Operator shared a Roboflow write-up using a pose model per frame plus a general-purpose vision-language model reasoning over 20-second chunks (serve / hit / point / fault, with timestamps). Same split this pipeline already has: cheap per-frame detector, expensive reasoning only on shortlisted material.

The arithmetic is what settles it: ~$1 per 20-second chunk is **~$180 per court-hour, ~$1,440 for a 2-hour 4-court session**. Only affordable after our detector has already picked the clips (~$10 per camera-session for the top 10 rallies). And the published result is one clip checked by eye — the same two gaps (unscored, unchecked for stability) that got our own Gemini verifier retired in ADR-085.

## One more single point of failure closed: ffmpeg was being apt-get installed on every pod job (PIC-154)

Leftover from the original single-point-of-failure pass that opened today: every reel job's pod bootstrap ran `apt-get update && apt-get install ffmpeg` against Ubuntu's package mirrors before doing anything else. Same two problems as everything else fixed today — an external dependency with no fallback (a mirror blip fails the whole job), and it installs whatever version Ubuntu 22.04 currently ships, which already caused one real bug earlier this week (`-fps_mode cfr` not recognized, worked around with the older `-vsync cfr`).

Fixed by reusing something already proven in this project instead of sourcing anything new: `desktop/electron/binaries.js` already ships static `ffmpeg`/`ffprobe` binaries (the `ffmpeg-static`/`ffprobe-static` npm packages) to every venue's desktop app. Pulled the Linux x64 binaries straight out of `desktop/node_modules/`, uploaded them to R2 once (not per job — same caching pattern the 130MB TrackNet weights already use, not `_upload_pod_deps()`'s fresh-every-job pattern, which is right for source code but wrong for a large binary that never changes), and had `pod_driver.py` download and chmod them to `/usr/local/bin` as its first action. `/usr/local/bin` beats `/usr/bin` on PATH by Debian convention, so every existing bare `"ffmpeg"`/`"ffprobe"` call in the pod-side code picked them up with no call-site changes. Removed the `apt-get` line from the bootstrap entirely.

Worth a note: the npm package's own version tag (`b6.1.1`) turned out stale — the real binaries report `ffmpeg 7.0.2` and `ffprobe 4.0.2` (a real version gap between the two, not a mistake here, confirmed against the actual `-version` output before trusting it and naming the R2 keys after it instead of the misleading tag).

Verified with a real upload → download → chmod → execute round-trip through R2 (both binaries run standalone, no missing shared libs). 169 Python tests still pass; this class of change isn't meaningfully unit-testable without a real pod, same standing as the weights-fetch code it mirrors. Filed and closed as PIC-154. Not yet exercised by a real live pod job — same as every other ADR-093 change to date.

The genuinely useful half is the pose model: RF-DETR Keypoint is Apache 2.0 on code *and* weights, and running it would answer the far-court pose question `PRD.md` has carried as an untested risk since it was written — on the GPU we already rent, with no API spend. Written up in `STRATEGY.md` §8; tracked as `PIC-147` (pose) and `PIC-148` (VLM tagging, with the ADR-085 preconditions spelled out). Neither is scheduled — movement analytics stays deferred until venue rollout.
