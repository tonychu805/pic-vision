# 2026-09-18

## A pass over the desktop app found two real bugs, both now fixed

Ran the desktop agent (1.3.0) the way an operator would, on this workstation, and checked what the console's own database said at each step rather than trusting the screen. Deliberately left out: anything that would pull video from the two real cameras (they're still not pointed at a court), and "Send to cloud", which starts a billed GPU job. 87 of 87 automated tests passed before any of this.

**A mistyped camera address froze the Add dialog for about 15 minutes.** Typed an address with nothing on it. "Connecting…" for ~2 minutes, then "Looking for a video stream…" — a step with no Cancel button — for ~13 more, ending with advice to check the camera's ONVIF setting, which is the wrong advice for a typo. Two separate causes, both measured rather than guessed:

- `rtspProbe.js`'s 2.5s timeout never applied while connecting. The timeout listener only settled an in-flight request, and during connect there isn't one, so the wait fell through to the OS's own limit — **134 seconds, timed directly** — and the path ladder does that seven times. Confirmed the timeout event does fire on schedule (2.505s) and was simply being dropped.
- The `onvif` library defaults to **120 seconds** per request, which is the ~2 minutes before the ladder even started. Now 10s, which is generous for a camera on the venue's own LAN.

The same input now fails in **30 seconds**, end to end, checked in the running app. Three new tests cover it, including one that pins the connect-phase case the old code missed.

**A calibrated camera showed "Not calibrated" right after launch.** Court 3 read "Not calibrated" on screen while the console's database (checked directly) said it had been calibrated since 2026-09-06 — and the app's own background process agreed it was calibrated. The camera list is read before the first heartbeat answers, and nothing on the detail page re-read it afterwards; the Refresh button sitting right beside the calibration line only refreshed recordings. For a real camera this also disables "Send to cloud" and relabels it "Calibrate first".

Verified properly rather than by eye: pointed the agent at a local relay that held its first heartbeat back by 20 seconds, which reproduces the launch window on demand. **With the fix** the page showed "Not calibrated" and then corrected itself to "Calibrated — 0.55 ft" with no navigation. **With the fix stashed, same conditions**, it stayed wrong through two heartbeats and a Refresh click. Local state (console URL, cameras) restored afterwards.

**Filed, not fixed:** renaming a camera hides every recording it already has (`PIC-149` — label-keyed folders, the same keying that already caused one bug; Court 1 has 2 recordings that would vanish); Court 2 measures 52 fps while the camera reports 30, and the 30fps gate trusts the measured number (`PIC-150`, mechanism suspected but not confirmed); internal "Error invoking remote method…" text reaching operators plus the wrong ONVIF advice (`PIC-151`); a scan that finds nothing giving no feedback, and four wording fixes (`PIC-152`). The desktop renderer's missing CSP went as a comment on `PIC-146`, which already covers the same gap in the web apps.

**Not tested, and worth knowing:** everything involving real-camera video (live view, recording, calibration, re-entering a password), "Send to cloud" and Retry, the destructive actions (sign out, remove machine, remove camera), and all the macOS-only behaviour — this was the dev build on Linux, not the 1.3.0 DMG.

## Two more fixes off the same list: the rename bug, and a finished reel that could be lost

**Renaming a camera no longer hides its recordings (`PIC-149`).** Recording directories were named after the camera's label, so a rename pointed both `startRecording` and `listRecordings` at a directory that did not exist: the files stayed on disk under the old name and vanished from the camera's page, taking the "Send to cloud" row with them. Two cameras sharing a label also shared a directory, which had already caused one real bug.

Directories are now keyed by camera id, which a rename cannot touch. The awkward part is the machines that already recorded under the old layout — a fix that only changed new writes would strand those permanently, so there is a one-time move at startup, written as a pure function (`planRecordingDirMigration`) precisely because its edge cases need testing: already migrated, two cameras sharing one label (first in list order takes it; their recordings were commingled and attributing them afterwards would be invention), and a sample clip whose absolute stored path points inside the directory being moved.

Ran for real on this workstation: `Court_1`, `Court_3` and `Court_4` moved to their id-named directories, both sample clips' stored paths rewritten, and Court 1's 2 recordings survived a rename and a rename back — 2, 2, 2. The pre-fix behaviour (2 → 0) is from reading `capture.js:378`, not from re-running it.

**A finished reel can no longer be lost to a console hiccup (pipeline).** `pod_driver.py`'s `patch_job` swallows every failure on purpose, so a running GPU job isn't abandoned over a network blip. That was also true of the *final* report — and by the time that one is sent, the reels are already uploaded to R2 and the console is the only thing that will ever know they exist. One 500 at that moment meant: pod self-terminates, `job_runner.py` marks the job errored ("pod disappeared without reporting"), its cleanup deletes the venue's uploaded segments, and the operator is asked to re-upload a session and pay for a second GPU job whose output is already sitting complete in the bucket.

Terminal reports (done / error / cancelled) now go through `report_final_job_status`, which retries ~63s with backoff and treats 409 as delivered rather than retrying a row that has already moved on. Progress reports stay best-effort, and a test pins that half of the contract too, since collapsing the two would be the obvious wrong simplification.

165 Python tests and 98 desktop tests pass.

**Still open from the same list:** `PIC-150` (the 52 fps reading — needs a live-stream check on a real camera, so it needs the operator's say-so first), `PIC-151` (wrong ONVIF advice and raw IPC error text), `PIC-152` (silent scan plus wording). And one that isn't a code change: push a byte-identical backup tag of `tf215-cuda118` to Docker Hub, the only image RunPod reliably starts — attempted here and correctly blocked as an outward-facing action, so it's an operator command.

## A VLM doing tennis analytics — reviewed, and both halves recorded

Operator shared a Roboflow write-up using a pose model per frame plus a general-purpose vision-language model reasoning over 20-second chunks (serve / hit / point / fault, with timestamps). Same split this pipeline already has: cheap per-frame detector, expensive reasoning only on shortlisted material.

The arithmetic is what settles it: ~$1 per 20-second chunk is **~$180 per court-hour, ~$1,440 for a 2-hour 4-court session**. Only affordable after our detector has already picked the clips (~$10 per camera-session for the top 10 rallies). And the published result is one clip checked by eye — the same two gaps (unscored, unchecked for stability) that got our own Gemini verifier retired in ADR-085.

The genuinely useful half is the pose model: RF-DETR Keypoint is Apache 2.0 on code *and* weights, and running it would answer the far-court pose question `PRD.md` has carried as an untested risk since it was written — on the GPU we already rent, with no API spend. Written up in `STRATEGY.md` §8; tracked as `PIC-147` (pose) and `PIC-148` (VLM tagging, with the ADR-085 preconditions spelled out). Neither is scheduled — movement analytics stays deferred until venue rollout.
