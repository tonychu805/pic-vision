# 2026-09-01

## Desktop client: camera discovery/management started for real (`STRATEGY.md` §5)

**Stack decided: Electron, not Tauri, for the POC** — a real trade-off
discussion, not a default pick. Tauri is the better-engineered long-term
choice (smaller footprint, secure-by-default credential handling — relevant
since this client will eventually need scoped, non-`.env` RunPod/R2
creds), but Electron won for v1 because the actual first feature (ONVIF
discovery, RTSP handling) is Node's ecosystem, not Rust's, and it gives
full UI+backend code reuse with a future web app rather than just the UI
layer. Migrating to Tauri later is a partial move, not a rewrite, if the
Node/OS-touching code stays behind a clean IPC boundary now (documented in
`desktop/electron/main.js`'s comments) — either rewrite that backend logic
in Rust, or keep it as a Node "sidecar" process Tauri spawns.

**Built: `desktop/` — Electron + React, ONVIF camera discovery/management.**
`electron/cameras/discovery.js` (WS-Discovery probe via the `onvif` npm
package) + `store.js` (persisted camera list, connect/test via
`electron-store`) behind exactly 5 `ipcMain.handle` calls, matched by
`preload.cjs`'s `contextBridge` surface — the renderer never touches
Node/OS directly. `desktop/README.md` has the full picture.

**Two real bugs found and fixed while getting it running, neither
guessed — both confirmed via Chrome DevTools Protocol against the actual
running app, which turned out to be the load-bearing debugging technique
all session** (this is a remote/no-display dev box; screenshots of the
real X11 display come back solid black — locked/asleep, not an app
problem — but CDP's `Page.captureScreenshot` renders from inside Chromium
itself, so it works regardless of the OS display state):
1. Linux sandbox: `chrome-sandbox` isn't root-owned+4755 in this dev
   container → `--no-sandbox` on the dev launch only.
2. **`preload.js`'s `import` syntax silently failed to run** — Electron's
   preload loader resolves module type by file extension, not by
   `package.json`'s `"type": "module"` the way normal Node/Vite resolution
   does. No thrown error, no console warning — `contextBridge` just never
   ran, `window.cameraAPI` stayed `undefined`. First surfaced when the
   user's own screenshot showed "Cannot read properties of undefined
   (reading 'list')" through the Tailscale dev-server link — which
   initially looked like it might just be "browser tab has no preload
   injection" (a real, separate, expected limitation of that viewing
   method) until re-checking the *actual* Electron renderer via CDP showed
   the same undefined `cameraAPI` there too. Fixed: renamed to
   `preload.cjs`, switched to `require()`.

**Real bug found and fixed: ONVIF discovery wasn't camera-only, and the
first explanation for that was wrong.** WS-Discovery against this network
returned 2 Synology NAS boxes (`tony_nas`, `tony_ds1525`, port 5357) as
if they were cameras. First guess -- Synology Surveillance Station's own
ONVIF/NVT bridge answering on the NAS's behalf -- was never actually
checked and turned out to be wrong; the user pushed back ("i dont think
you're supposed to be able to detect NAS?"), which prompted actually
capturing the raw WS-Discovery XML (`Discovery.on('device', (cam, rinfo,
xml) => ...)`, not exposed by the library's promise-resolved result at
all). **Root cause: the `onvif` npm package's `Discovery.probe()` sends a
Probe scoped to `<Types>dn:NetworkVideoTransmitter</Types>` but never
checks a responder's own declared `<wsd:Types>` before returning it as a
camera.** Both NAS boxes' raw responses self-reported
`wsd:Types = "wsdp:Device pub:Computer"` -- the generic Windows-network-
browsing/WSD type, unrelated to ONVIF, nothing to do with Surveillance
Station. Fixed in `electron/cameras/discovery.js`: listens for the raw XML
via the event API and filters by the responder's actual declared type
before returning anything, cross-referenced against the promise API's
resolved list for timeout/completion handling. Verified fixed against the
same real network both directly (`discoverCameras()` now returns `[]`
instead of the 2 NAS boxes) and through the running app (CDP click-through
of a real "Scan again").

**Real find, corrected once: the target camera (a Synology BC510) does run
ONVIF — just not where the default path or WS-Discovery would find it.**
Found the device by IP/MAC/port fingerprinting first — MAC OUI `90:09:D0`
(a different Synology block than their NAS line), RTSP port 554 open, no
DSM/webman ports, distinct minimal embedded web UI. Direct ONVIF SOAP
request to `/onvif/device_service` (lowercase, the `onvif` library's
default) came back a plain `404`, which first read as "ONVIF disabled by
default on this model" — **wrong, corrected same session**: probing
`/Onvif/device_service` (capital O) instead returned `401 Unauthorized`
with `WWW-Authenticate: Digest ... realm="IPCam"` — a real ONVIF/HTTP-
Digest endpoint, not disabled at all, just cased differently than the
library assumes. It also never answered the WS-Discovery probe at all
(unrelated to the type-filter bug above — this device simply doesn't
respond to WS-Discovery), so auto-scan can't find it either way. Didn't
attempt login/credential guessing — real credentials needed from the
operator to finish confirming it end-to-end. Real consequence: the app
needed both a manual-add path *and* an optional ONVIF-path override
(neither in the original Claude Design mockup, which has no manual-add
affordance at all) — added because the gap was real, not hypothetical.
`electron/cameras/store.js`'s `testConnection`/`addCamera` and the manual-
add dialog now take an optional `path`.

## Follow-up same day: credentials tried, real path confirmed missing, network sweep built

**Operator gave real BC510 credentials; tried them directly against every
ONVIF path candidate found so far — none work, but confirmed *why* rather
than left ambiguous.** A raw digest-auth control test (deliberately wrong
password → `401` again; the real password → `404`) proved the credentials
themselves are valid — the server accepts the auth and moves on to
routing, where nothing is registered at `/Onvif/device_service` (or
`/onvif/device_service`, `/onvif/Device`, `/onvif/services`,
`/ISAPI/System/deviceInfo`, tried on both HTTP and HTTPS). **This corrects
the same-day "ONVIF exists at a different-cased path" finding above —
that was also wrong.** Current best understanding: `/Onvif/device_service`
is a route that demands auth but has no real ONVIF handler behind it,
possibly a generic proxy rule rather than an actual ONVIF implementation.
Didn't keep guessing paths past this point — diminishing returns on blind
probing; the operator's own path to a real answer is the camera's admin
UI, now log-in-able with confirmed-valid credentials.

**Real gap surfaced by this whole exchange: the app had no discovery
method that doesn't depend on the camera cooperating.** Operator asked
directly ("is WS-Discovery the only option for scanning?") — no, but it
was the only one *built*. Added `electron/cameras/networkSweep.js`: TCP-
probes port 554 (RTSP) against every host in the real local subnet
(`system.js`'s `getNetworkInfo()`), in parallel (concurrency-capped host
pool, no external deps). RTSP-open was the exact signal that separated the
real camera from the two NAS false-positives earlier in the day, by hand
— this automates that. Verified against the real network: found the
BC510 at `192.168.1.121` in ~4s, correctly flagged neither NAS box (RTSP
closed on both). Wired into "Scan again" alongside WS-Discovery
(`Promise.allSettled`, independent failure handling); sweep hits render as
a new "Possible camera" card state (distinct from WS-Discovery's "Sign-in
needed" -- a sweep hit doesn't know ONVIF is even present, only that port
554 answered) and clicking one opens the manual-add dialog pre-filled with
its IP, since there's no known ONVIF path yet. `SettingsPage.jsx`'s
protocol list updated to mark ONVIF WS-Discovery and RTSP port sweep as
`REAL`, the rest still illustrative.

## Later same day: BC510 root cause actually found, RTSP sweep upgraded to a real protocol check

**The BC510 mystery is solved, for real this time — read its own client
code instead of guessing more paths.** Fetched `main.bundle.js` (2.7MB,
the camera's own web UI, `curl`'d directly) and grepped it rather than
trying more URL guesses. Found the real API prefix
(`/syno-api/maintenance/operation_mode`, not `/webapi/` or `/onvif/` —
every earlier guess was wrong) and, more importantly, the actual
mechanism: **this camera has three mutually exclusive "Operation Mode"
settings — `svs` (Synology Surveillance Station's own protocol), `onvif`,
and `c2` (Synology cloud) — and defaults to `svs`.** A real authenticated
`GET` against that endpoint (credentials from the operator, a digest-auth
control test first confirmed they're genuinely valid) returned `"svs"`
directly from the camera. That's *why* every ONVIF path 404'd all day —
there was never a wrong path to find; the ONVIF subsystem simply isn't
running while the camera's in `svs` mode. Did not flip the setting via API
— the camera's own UI wraps that switch in a confirm dialog (likely
disconnects it from Surveillance Station), a real consequence for the
operator to decide, not something to do silently through a raw API call.

**Operator set explicit product direction from this: stay ONVIF-generic,
never let the UX feel vendor-specific (Synology especially)** — declined
building the obvious follow-on feature (read/switch Operation Mode from
inside the app) for exactly that reason. Recorded as a durable project
memory (`project_desktop_client_scope.md`) so it doesn't need re-litigating
next session. Prompted a real copy cleanup too: two places in the actual
UI (not just code comments) had drifted into narrating this session's own
debugging history ("the real case that added this field", "a real camera
on this network needed the sweep") — fixed to read like normal product
copy, since a real user has no reason to see that.

**RTSP sweep upgraded from "port is open" to a real protocol check.**
Operator asked directly why a sweep hit could only ever say "possible"
rather than being confirmed. Fair question — the sweep was doing a bare
TCP connect, the weakest signal possible (proves nothing about what's
actually listening). Added a real RTSP `OPTIONS` handshake
(`networkSweep.js`'s `probeRtsp`) once the TCP port answers — `OPTIONS`
needs no credentials per the RTSP spec (RFC 2326 §10.1), so this is a
genuine protocol-level confirmation, not a guess, and it's vendor-neutral
(any RTSP camera, any brand, answers the same way). Two confidence levels
now: **"RTSP confirmed"** (a real RTSP response came back) vs. **"Possible
camera"** (port open, no valid RTSP reply — could be anything). Verified
against the real network: the BC510 now reports "RTSP confirmed"
(upgraded from the earlier "Possible camera"), still correctly excludes
both NAS boxes (neither speaks RTSP at all).

## Later still: brand identification from MAC address, generically

**Operator asked whether brand/model could be identified for cameras that
show up before ONVIF works at all** (i.e. sweep hits, which today only
carry an IP). Answered honestly: brand yes via a generic mechanism, model
no. Model needs the device to say so itself, which only happens through
ONVIF's `GetDeviceInformation()` once a camera actually connects — no
protocol-generic substitute exists for that.

**Brand: MAC address (via ARP, ports already contacted it during
discovery) → manufacturer (IEEE OUI registry).** Flagged the real
trade-off before building — live vendor-lookup APIs (used manually earlier
today, `api.macvendors.com`) leak every scanned device's MAC to a third
party on every scan and rate-limit fast (hit that limit at 9 lookups
earlier); chose to bundle the registry instead (`oui-data` npm package,
BSD-2-Clause, ~5.6MB, published by automated CI 3 days before this
session — actively maintained, not stale). Verified the package's data
directly against every MAC already confirmed by hand today before trusting
it (`9009D0`/`001132` → Synology, matching the manual lookups; `BCAD28` →
Hikvision, matching the original mockup's own fixture data).

Two real things caught and fixed before landing this, not assumed correct:
1. **WS-Discovery hits can report a symbolic hostname, not an IP**, in
   their XAddr URL (that's exactly how the two now-filtered NAS boxes
   showed up, as `Tony_NAS`/`Tony_DS1525`) — ARP only indexes IPs. Fixed
   by using the UDP reply's actual source address (`rinfo.address`,
   always a real IP, can't be spoofed by a hostname string) for the
   vendor lookup instead of trusting the device's own claimed hostname.
2. **IEEE registrants are legal-entity names**, not brand names
   ("Hangzhou Hikvision Digital Technology Co.,Ltd." from an initial test
   lookup, not "Hikvision") — added a blanket corporate-suffix-stripping
   rule (Inc./Ltd./Co.,Ltd./Corp./etc.), same rule for every registrant,
   not a per-brand name-mapping table (would have been exactly the kind of
   vendor-specific curation the operator asked to avoid). First version of
   this rule had its own bug — pre-splitting on comma severed the compound
   "Co.,Ltd." suffix in half, leaving a dangling "Co." — caught by testing
   against the real Hikvision entry before trusting it, not assumed
   correct from reading the regex.

Verified against the real network: the BC510 card now reads "Synology —
RTSP confirmed (port 554)" instead of a bare IP.
