# 2026-09-01

## Desktop client: camera discovery/management started for real (`STRATEGY.md` §5)

**Stack decided: Electron, not Tauri, for the POC** — a real trade-off
discussion, not a default pick. Tauri is the better-engineered long-term
choice (smaller footprint, secure-by-default credential handling — relevant
since this client will eventually need scoped, non-`.env` RunPod/R2
creds), but Electron won for v1 because the actual first feature (ONVIF
discovery, RTSP handling) is Node's ecosystem, not Rust's, and it gives
full UI+backend code reuse with a future web app rather than just the UI
layer. Migrating to Tauri later is a partial move, not a rewrite, if the
Node/OS-touching code stays behind a clean IPC boundary now (documented in
`desktop/electron/main.js`'s comments) — either rewrite that backend logic
in Rust, or keep it as a Node "sidecar" process Tauri spawns.

**Built: `desktop/` — Electron + React, ONVIF camera discovery/management.**
`electron/cameras/discovery.js` (WS-Discovery probe via the `onvif` npm
package) + `store.js` (persisted camera list, connect/test via
`electron-store`) behind exactly 5 `ipcMain.handle` calls, matched by
`preload.cjs`'s `contextBridge` surface — the renderer never touches
Node/OS directly. `desktop/README.md` has the full picture.

**Two real bugs found and fixed while getting it running, neither
guessed — both confirmed via Chrome DevTools Protocol against the actual
running app, which turned out to be the load-bearing debugging technique
all session** (this is a remote/no-display dev box; screenshots of the
real X11 display come back solid black — locked/asleep, not an app
problem — but CDP's `Page.captureScreenshot` renders from inside Chromium
itself, so it works regardless of the OS display state):
1. Linux sandbox: `chrome-sandbox` isn't root-owned+4755 in this dev
   container → `--no-sandbox` on the dev launch only.
2. **`preload.js`'s `import` syntax silently failed to run** — Electron's
   preload loader resolves module type by file extension, not by
   `package.json`'s `"type": "module"` the way normal Node/Vite resolution
   does. No thrown error, no console warning — `contextBridge` just never
   ran, `window.cameraAPI` stayed `undefined`. First surfaced when the
   user's own screenshot showed "Cannot read properties of undefined
   (reading 'list')" through the Tailscale dev-server link — which
   initially looked like it might just be "browser tab has no preload
   injection" (a real, separate, expected limitation of that viewing
   method) until re-checking the *actual* Electron renderer via CDP showed
   the same undefined `cameraAPI` there too. Fixed: renamed to
   `preload.cjs`, switched to `require()`.

**Real bug found and fixed: ONVIF discovery wasn't camera-only, and the
first explanation for that was wrong.** WS-Discovery against this network
returned 2 Synology NAS boxes (`tony_nas`, `tony_ds1525`, port 5357) as
if they were cameras. First guess -- Synology Surveillance Station's own
ONVIF/NVT bridge answering on the NAS's behalf -- was never actually
checked and turned out to be wrong; the user pushed back ("i dont think
you're supposed to be able to detect NAS?"), which prompted actually
capturing the raw WS-Discovery XML (`Discovery.on('device', (cam, rinfo,
xml) => ...)`, not exposed by the library's promise-resolved result at
all). **Root cause: the `onvif` npm package's `Discovery.probe()` sends a
Probe scoped to `<Types>dn:NetworkVideoTransmitter</Types>` but never
checks a responder's own declared `<wsd:Types>` before returning it as a
camera.** Both NAS boxes' raw responses self-reported
`wsd:Types = "wsdp:Device pub:Computer"` -- the generic Windows-network-
browsing/WSD type, unrelated to ONVIF, nothing to do with Surveillance
Station. Fixed in `electron/cameras/discovery.js`: listens for the raw XML
via the event API and filters by the responder's actual declared type
before returning anything, cross-referenced against the promise API's
resolved list for timeout/completion handling. Verified fixed against the
same real network both directly (`discoverCameras()` now returns `[]`
instead of the 2 NAS boxes) and through the running app (CDP click-through
of a real "Scan again").

**Real find, corrected once: the target camera (a Synology BC510) does run
ONVIF — just not where the default path or WS-Discovery would find it.**
Found the device by IP/MAC/port fingerprinting first — MAC OUI `90:09:D0`
(a different Synology block than their NAS line), RTSP port 554 open, no
DSM/webman ports, distinct minimal embedded web UI. Direct ONVIF SOAP
request to `/onvif/device_service` (lowercase, the `onvif` library's
default) came back a plain `404`, which first read as "ONVIF disabled by
default on this model" — **wrong, corrected same session**: probing
`/Onvif/device_service` (capital O) instead returned `401 Unauthorized`
with `WWW-Authenticate: Digest ... realm="IPCam"` — a real ONVIF/HTTP-
Digest endpoint, not disabled at all, just cased differently than the
library assumes. It also never answered the WS-Discovery probe at all
(unrelated to the type-filter bug above — this device simply doesn't
respond to WS-Discovery), so auto-scan can't find it either way. Didn't
attempt login/credential guessing — real credentials needed from the
operator to finish confirming it end-to-end. Real consequence: the app
needed both a manual-add path *and* an optional ONVIF-path override
(neither in the original Claude Design mockup, which has no manual-add
affordance at all) — added because the gap was real, not hypothetical.
`electron/cameras/store.js`'s `testConnection`/`addCamera` and the manual-
add dialog now take an optional `path`.

## Later same day: BC510 root cause actually found, RTSP sweep upgraded to a real protocol check

**The BC510 mystery is solved, for real this time — read its own client
code instead of guessing more paths.** Fetched `main.bundle.js` (2.7MB,
the camera's own web UI, `curl`'d directly) and grepped it rather than
trying more URL guesses. Found the real API prefix
(`/syno-api/maintenance/operation_mode`, not `/webapi/` or `/onvif/` —
every earlier guess was wrong) and, more importantly, the actual
mechanism: **this camera has three mutually exclusive "Operation Mode"
settings — `svs` (Synology Surveillance Station's own protocol), `onvif`,
and `c2` (Synology cloud) — and defaults to `svs`.** A real authenticated
`GET` against that endpoint (credentials from the operator, a digest-auth
control test first confirmed they're genuinely valid) returned `"svs"`
directly from the camera. That's *why* every ONVIF path 404'd all day —
there was never a wrong path to find; the ONVIF subsystem simply isn't
running while the camera's in `svs` mode. Did not flip the setting via API
— the camera's own UI wraps that switch in a confirm dialog (likely
disconnects it from Surveillance Station), a real consequence for the
operator to decide, not something to do silently through a raw API call.

**Operator set explicit product direction from this: stay ONVIF-generic,
never let the UX feel vendor-specific (Synology especially)** — declined
building the obvious follow-on feature (read/switch Operation Mode from
inside the app) for exactly that reason. Recorded as a durable project
memory (`project_desktop_client_scope.md`) so it doesn't need re-litigating
next session. Prompted a real copy cleanup too: two places in the actual
UI (not just code comments) had drifted into narrating this session's own
debugging history ("the real case that added this field", "a real camera
on this network needed the sweep") — fixed to read like normal product
copy, since a real user has no reason to see that.

**RTSP sweep upgraded from "port is open" to a real protocol check.**
Operator asked directly why a sweep hit could only ever say "possible"
rather than being confirmed. Fair question — the sweep was doing a bare
TCP connect, the weakest signal possible (proves nothing about what's
actually listening). Added a real RTSP `OPTIONS` handshake
(`networkSweep.js`'s `probeRtsp`) once the TCP port answers — `OPTIONS`
needs no credentials per the RTSP spec (RFC 2326 §10.1), so this is a
genuine protocol-level confirmation, not a guess, and it's vendor-neutral
(any RTSP camera, any brand, answers the same way). Two confidence levels
now: **"RTSP confirmed"** (a real RTSP response came back) vs. **"Possible
camera"** (port open, no valid RTSP reply — could be anything). Verified
against the real network: the BC510 now reports "RTSP confirmed"
(upgraded from the earlier "Possible camera"), still correctly excludes
both NAS boxes (neither speaks RTSP at all).

## Later still: brand identification from MAC address, generically

**Operator asked whether brand/model could be identified for cameras that
show up before ONVIF works at all** (i.e. sweep hits, which today only
carry an IP). Answered honestly: brand yes via a generic mechanism, model
no. Model needs the device to say so itself, which only happens through
ONVIF's `GetDeviceInformation()` once a camera actually connects — no
protocol-generic substitute exists for that.

**Brand: MAC address (via ARP, ports already contacted it during
discovery) → manufacturer (IEEE OUI registry).** Flagged the real
trade-off before building — live vendor-lookup APIs (used manually earlier
today, `api.macvendors.com`) leak every scanned device's MAC to a third
party on every scan and rate-limit fast (hit that limit at 9 lookups
earlier); chose to bundle the registry instead (`oui-data` npm package,
BSD-2-Clause, ~5.6MB, published by automated CI 3 days before this
session — actively maintained, not stale). Verified the package's data
directly against every MAC already confirmed by hand today before trusting
it (`9009D0`/`001132` → Synology, matching the manual lookups; `BCAD28` →
Hikvision, matching the original mockup's own fixture data).

Two real things caught and fixed before landing this, not assumed correct:
1. **WS-Discovery hits can report a symbolic hostname, not an IP**, in
   their XAddr URL (that's exactly how the two now-filtered NAS boxes
   showed up, as `Tony_NAS`/`Tony_DS1525`) — ARP only indexes IPs. Fixed
   by using the UDP reply's actual source address (`rinfo.address`,
   always a real IP, can't be spoofed by a hostname string) for the
   vendor lookup instead of trusting the device's own claimed hostname.
2. **IEEE registrants are legal-entity names**, not brand names
   ("Hangzhou Hikvision Digital Technology Co.,Ltd." from an initial test
   lookup, not "Hikvision") — added a blanket corporate-suffix-stripping
   rule (Inc./Ltd./Co.,Ltd./Corp./etc.), same rule for every registrant,
   not a per-brand name-mapping table (would have been exactly the kind of
   vendor-specific curation the operator asked to avoid). First version of
   this rule had its own bug — pre-splitting on comma severed the compound
   "Co.,Ltd." suffix in half, leaving a dangling "Co." — caught by testing
   against the real Hikvision entry before trusting it, not assumed
   correct from reading the regex.

Verified against the real network: the BC510 card now reads "Synology —
RTSP confirmed (port 554)" instead of a bare IP.

## Very end of day: the BC510 actually gets added — an RTSP fallback ladder, not a bypass

Operator asked whether the app could bypass the ONVIF requirement, or at
least instruct users. Investigated the "bypass" half properly first,
before answering: fetched the camera's own client JS again and found the
actual RTSP path-building logic — `rtsp://host:port/1` normally, only
gaining a `/onvif` prefix when Operation Mode is actually ONVIF. Confirmed
for real with `ffprobe` (not assumed): `rtsp://tonychu:***@192.168.1.121:554/1`
and `/2` both played, real H.264 video (2880×1620 and 1920×1080), audio
included. The camera's stream was reachable the entire day, completely
independent of the ONVIF question that consumed most of it.

Operator reframed the ask once presented with this: not "bypass ONVIF",
but "what's the most frictionless path, and what fallback mechanisms
cover the most real cameras" — a coverage-ladder question, not a single
trick. Landed on a real insight before building anything: ONVIF metadata
(model/serial/firmware) was never actually load-bearing for this product
— it cuts highlights from footage, which needs a stream, not a model
name. That reframes ONVIF as the *fastest* path when it works, not a
*required* one.

**Built the next two rungs of the discovery ladder, both deliberately
generic (no per-vendor branching):**

4. **Automatic RTSP-path fallback** when a manual ONVIF attempt fails —
   tries a short, generic list of common stream paths (`/1`, `/2`,
   `/live`, `/live.sdp`, `/stream1`, `/video1`, and root) with the same
   credentials already entered, verified by a real RTSP `DESCRIBE`
   exchange, not just a protocol handshake. New `electron/cameras/
   rtspProbe.js` implements RTSP Digest auth from scratch — `DESCRIBE`,
   unlike `OPTIONS` (discovery.js/networkSweep.js), isn't credential-free
   under RFC 2326.
5. **Raw-RTSP-URL paste** as the true last resort, offered only if the
   generic list also fails — covers whatever the generic list can't guess,
   since it doesn't depend on guessing anything; the user finds it in
   their camera's own app. Plus a generic, brand-neutral instruction
   ("check your camera's settings for an ONVIF option") shown at the same
   point, deliberately not naming Synology's "Operation Mode" wording.

**A real bug caught before trusting the Digest implementation, not
assumed correct:** the first version tested against the real camera and
failed even with verified-correct credentials. Root cause, found by
capturing the raw exchange rather than re-reading the auth math: each
`DESCRIBE` attempt opened a *fresh* TCP connection, but this server
(LIVE555) issues a new nonce per connection — the authenticated retry was
presenting a nonce from a connection that no longer existed. Fixed by
holding one connection across the initial challenge and the authenticated
retry. Re-verified against the real camera afterward: correct path +
credentials succeeds, wrong path gets a real `404 Stream Not Found` (not
another 401 — proof auth itself was accepted), wrong password gets
rejected, and the generic path-list search finds `/1` correctly on its
own.

## Postscript: N100 capacity question researched, benchmark script prepared (no N100 in hand)

Operator asked whether N100 would hold up for 4 cameras with live view.
Recapped from documentation first (`STRATEGY.md` §5, `DECISIONS.md`
ADR-043): N100's actual designed job is capture → 720p proxy encode →
upload for cloud detection → cut full-res locally from returned
timestamps — and the architecture was explicitly scoped **one camera per
box** ("one box per court") and **batch, not live** (§5's own opening
line). Both "4 cameras" and "live view" are new requirements outside what
was ever designed, not just untested within it. Also caught real doc
drift while in there: `TECH_SPEC.md`'s N100 diagram still says "yolov8x
detection," predating the TrackNet pivot, never updated.

Researched real N100/Quick Sync capacity (web search + primary-source
fetch attempts) rather than reason from memory: Intel's own spec confirms
4K@60fps hardware decode/encode per stream, no software-enforced
concurrent-session cap (unlike NVIDIA NVENC). Real-world numbers vary by
workload type — full 4K transcode benchmarks land at 1–3 concurrent
streams; Jellyfin/Plex mixed-resolution testing reaches 5 concurrent at
~35% CPU; Frigate NVR's own hardware docs (the closest real analog —
a home NVR that decodes multiple camera streams) recommend N100 for
1–6 cameras at low-medium activity, running local ML detection
*at the same time* as decode. That last point matters: this project's
detection already runs on RunPod's cloud GPU, not locally, so the actual
N100 workload (decode-only for live view, stream-copy record, periodic
proxy encode) is lighter than every benchmark found, none of which
apply directly without local inference competing for the same resources.

**No N100 physically available to verify against, so a real benchmark
script was written instead of guessing further** — `desktop/scripts/
benchmark-decode.sh`, parameterized on the operator's own real camera
stream. Grounded in real measured numbers, not assumed: probed the
BC510's actual sub-stream via `ffprobe` packet sampling (not just
`ffprobe -show_streams`, which returned no bitrate/fps for this RTSP
source) — 1920×1080, ~13fps, ~744kbps H.264.

**Real bug caught before shipping the script, not assumed safe:** the
obvious hardware check ("does `/dev/dri/renderD128` exist") would have
silently passed on *this very dev workstation* — it has a render node,
but it belongs to the discrete NVIDIA card (PCI vendor `0x10de`), not an
Intel iGPU (this machine's actual CPU, a Core i7-7820X HEDT chip, has no
integrated GPU at all). Fixed to check the real PCI vendor ID
(`0x8086` = Intel) on every render node found, not just node presence.
Verified the fix by actually running the script here: it correctly
detected no Intel GPU and refused to run, rather than producing a
meaningless result on the wrong hardware.

## Same feature, reworked same day: flat hour-set replaced with real sessions

Operator caught a real gap in what was just shipped: the flat "which
hours are active" cell set can't represent a booking boundary -- a 1-2pm
booking and a back-to-back 2-4pm booking for someone else look identical

be able to create highlights per session") needs each booking to stay a
distinct, identifiable thing.

**Reworked the data model, not just the UI.** `electron/schedule.js`
replaced entirely: a session is now `{id, day, start, end, label}` (day

any existing session it overlaps rather than allowing silent double-
booking -- a session fully inside the new range is dropped, one only
partly overlapped is trimmed from whichever side overlaps, and a session
that fully contains the new range splits into two independent
remainders (verified directly via `scheduleAPI`, not just eyeballed:
booking Tue 9-11 into an existing Tue 8-12 session correctly produced
8-9 and 11-12 as two separate objects, not one session with a hole).

**`WeekGrid.jsx` interaction model changed to match:** drag across empty
cells books a new session spanning exactly the dragged range; clicking a
cell that's already part of a session deletes that whole session (not
just the one hour). A thin inset divider renders at the start of every
session so two sessions that touch with zero gap stay visually distinct,
not just structurally distinct. Dropped "Activate all" (a 168-hour
"session" spanning the whole week doesn't fit the booking model) and
added a session list next to the grid (`ScheduleEditorPage.jsx`) --
sorted by day/time, each row showing the time range with an editable
label and a delete button, since the grid alone can't fit readable
labels into 16px cells.

**Verified for real again, same CDP techniques as the first version**

results and the on-disk `schedules.json` directly): booked Mon 1-2pm and

## Same day, third pass: borders replaced with an actual gap merge

Operator's reaction to the two-sided-border version, with a screenshot:
still not it -- preferred the opposite fix. Instead of adding a border to
*separate* touching-but-distinct sessions, close the gap entirely for a
*genuinely continuous* one, leaving the normal gap as the thing that
signals "these are different" (its absence, not an added line).

**Rebuilt `WeekGrid.jsx` on CSS Grid instead of nested flex rows**, which
was necessary, not just a style choice: with a shared flex row per hour,
there's no way to remove spacing for one day's column without also
shifting every other day's row height, breaking the hour-label gutter's
alignment. A CSS Grid's row/column tracks are fixed by the grid
definition regardless of a child's content, so each cell can carry an
absolutely-positioned "bridge" rect (`position:absolute`, out of layout
flow) that visually paints over the gap strip below it when -- and only
when -- the cell directly below shares the *same* session id. Two
sessions that merely touch (different ids) get no bridge, so the row-gap
between them stays exactly as visible as it always was.

Verified geometrically, not just by eye: for a real continuous 11am-1pm
session, the bridge rect's top/bottom edges landed exactly flush against
the two real cells' edges (`cell.bottom === bridge.top` and
`bridge.bottom === cell.top`, zero px gap) via `getBoundingClientRect`;
for two separate touching 1-hour sessions (2-3pm, 3-4pm) the real gap
measured the expected 2px, no bridge present. Also spot-checked that the
hour-label gutter still lines up with its row after the rewrite (a
label's vertical center landed inside its row's cell bounds). Test data
cleared afterward.

## Same day, fourth pass: still two visible pieces, not one -- rounded corners were the actual problem

Operator's reaction to the gap-bridge version, with another screenshot:
"i can obviously see whats in between" -- still reads as two shapes.
Real cause, not the same bug as before: each per-hour cell had its own
`border-radius`, so even with the gap fully bridged, the *rounded
corners* of each individual cell still created a visible notch/seam at

the existing create/delete logic is untouched.

Verified geometrically again: queried the overlay's rendered elements
directly and confirmed exactly one rectangle per session, not one per
hour -- a real continuous 2-hour booking measured a single 34px-tall

## Same day, a real latent bug found: the NAS false-positive filter never actually worked per-device

Operator activated a real TP-Link Tapo C200 and ran "Scan again" --
saw 4 cameras total (1 configured + 3 "found"), two of which were
labeled `tony_nas:5357` / `tony_ds1525:5357` -- the exact two Synology
NAS boxes a filter earlier today (`electron/cameras/discovery.js`) was
supposed to have excluded from scans entirely.

**Investigated with real data, not a guess** -- added temporary raw-XML
logging to `discovery.js`'s `device` event handler, restarted Electron,
ran a real "Scan again," and read back the actual SOAP responses. The
two NAS boxes' XML confirmed they still correctly self-report
`<wsd:Types>wsdp:Device pub:Computer</wsd:Types>` (no
`NetworkVideoTransmitter`, exactly as found the first time) -- the type
check itself was never the problem. The real camera's XML (the Tapo
C200, `192.168.1.115:2020/onvif/device_service`, Scopes literally
naming `hardware/C200`) correctly declared
`<wsdd:Types>tdn:NetworkVideoTransmitter</wsdd:Types>` and should pass.

**Root cause: `cam.urn` is `undefined` on this version of `onvif`'s Cam
objects, at both the event and the promise-resolved stage** -- confirmed
directly in the debug log (`urn=undefined` on every single event, C200
included). The filter kept a `Set` of "confirmed" URNs from devices that
passed the type check, then filtered `Discovery.probe()`'s resolved list
by `confirmedUrns.has(cam.urn)`. With every device's `.urn` equally
`undefined`, that check degenerates into "is *any* device confirmed at
all" -- as soon as one real camera (the C200) passed, `confirmedUrns`
held `{undefined}`, which then matched every other device's equally-
undefined `.urn`, silently re-admitting the NAS boxes. **This filter
never actually filtered per-device -- it only ever appeared to work
earlier today because that test had zero real cameras respond, so
`confirmedUrns` stayed empty and nothing could pass regardless.** A
coincidental pass, not a working fix, only exposed now that a real
camera finally answered a scan alongside the false positives.

**Fixed by removing the cross-referencing step entirely** -- confirmed
devices are now accumulated directly inside the `device` event handler
(same object shape as the resolved list, verified via the debug log:
hostname/xaddrs are populated at event time), and `Discovery.probe()`'s
own return value is no longer used at all, only awaited for its
completion/timeout behavior. Nothing left to silently degrade if `.urn`
is ever unpopulated again.

**Verified against the real network, twice:** scan now returns exactly
2 cameras (the configured Synology + the real Tapo C200,
`192.168.1.115:2020`), both NAS boxes gone, repeated on a second "Scan
again" to rule out a one-off. Debug logging removed before committing.
