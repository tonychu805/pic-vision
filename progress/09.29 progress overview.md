# 09.29 progress overview

## Design review: how the venue machine talks to the console

The basic shape holds up: the machine only ever connects out, a push is only a "go check" signal, the 60s poll is always underneath it, and every wait has a time limit. Seven findings, two fixed today:

- **Fixed — the instant command channel after a first sign-in.** A fresh install registers as part of signing in, and nothing started the fast command channel there, so a new venue's first Calibrate waited on the 60s poll until the app was restarted. Sign-in and sign-out now both rebind it. Tested; not yet watched on a real sign-in.
- **Fixed — three console routes checked the machine's token their own way** (heartbeat and both command routes), skipping the "this machine was removed" check. Safe today only because removing a machine also clears its token. They now use the shared check, and a new test fails if any route goes back to doing it by hand.

**Still open, in priority order:**

1. ~~**Anyone can take over another venue's machine if they know its device ID.**~~ **Fixed, not yet live (ADR-134).** The console now only looks for a machine inside the signed-in account. A machine signed into a second account gets its own separate record there, and the first account's record is left alone. The cost: **camera calibrations don't follow an account switch**, so set up a venue's machine signed in as the venue. **Database change applied 2026-09-29.** Waiting on: the console push.
2. ~~**A booked recording only stops if the internet is up, and old commands never expire.**~~ **Fixed, not yet live (ADR-135).** Checking first found it worse than thought: **if the app crashes, the recording keeps running on its own** and nothing can stop it (measured). Now the machine knows when each booking ends and stops on time without the internet. It picks a booking back up after a restart, stops anything a crash left running, ignores a start that arrives after its booking, and keeps retrying the send until the console has it. Tested end to end against a stand-in console and a real database engine; not yet on a real Mac or camera. **Database change applied 2026-09-29.** Waiting on: a desktop release and the console push (either order works).
3. ~~**A command can run twice**~~ **Fixed, not yet live (ADR-136).** Production showed no command actually running twice; what it did show was **Start clicked twice**, reported as a failure while the camera was recording. Now a repeated Start just succeeds, and the machine remembers what it has already done, so a command whose "done" got lost is answered again rather than run again (the costly case: a sample clip sent to the GPU twice).
4. ~~**A machine the console has rejected just says "Connection lost"**~~ **Fixed, not yet live (ADR-137).** After three refusals in a row the page now says **"Removed from <venue>"**, stops knocking, and offers a Reconnect button; it never reconnects by itself, since the venue may have removed it on purpose. Along the way: the console used to answer "not allowed" when its own database lookup failed, which would have made a database blip look like a removal. That now answers as a server error instead.
5. **Removing and re-adding a camera deletes its calibration.** **Main cause fixed, not yet live (ADR-138).** Production showed 6 of 15 calibrated cameras later deleted, including a real loss at the PGC field test. The likely reason people re-add: there was **no way to change a camera's address**, so a new IP meant remove and re-add. Now a camera that isn't answering offers "Did this camera get a new address?". It stays the same camera, so its calibration is kept. Still open, if re-adds keep happening: keep removed cameras on the console and offer to reuse their calibration.

**Not pushed:** the desktop change is in `pic-vision`, the route change in `pic-vision-cloud-console`. Both are committed only.

Item 5's follow-up is Linear **PIC-189**: re-check in 1–2 weeks after the release; build calibration reuse only if calibrated cameras are still being deleted.

## Code review of today's console changes (ADR-139)

A review of the console's unpushed commits found **a real bug in the booking change already applied to production.** A command stays "pending" until the machine reports back, so a machine that started recording and then lost the internet had its start treated as never run, **and got no stop at all**. Machines on the current desktop version ignore the end time, so they would have kept recording with no stop ever coming, even after reconnecting. **Fixed** by always sending the booking's stop again and only cancelling the start. Tested on a real database engine: the fix passes 10/10; the flawed version failed 4. **Correction applied to production the same afternoon**, with no booking near. No booking ran while the flawed version was live.

Also fixed:
- A machine switching accounts now releases its old record, but only when it proves it was that record. It sends the password it was using, which a stranger doesn't have.
- The check that guards against the takeover now covers more code.

Two findings turned out not to be problems. One was accepted as is: an error format.
