# 2026-10-25 progress overview

## Headline: the far-ball / 2nd-shot problem is self-inflicted downscaling, not the detector or the camera

Spent the day running the hit/serve overlay down to its root. The overlay kept
missing the **serve return (2nd shot)** and misplacing far hits. Chased why, and
it bottoms out somewhere useful.

**What's actually wrong.** At the serve-return moment the ball track blacks out
for ~0.5s — exactly when the ball is deepest and fastest. Two things cause it, and
the pipeline causes both itself:
- We **downsample 60fps → 30fps** (`CFR_FPS=30`) before TrackNet ever runs. On the
  fast shots, 30fps goes blind where 60fps holds the track (2–4× better per frame).
- We feed the **full 1920-wide frame into TrackNet's 512 input** (3.75× shrink), so
  the far ball goes from ~9px native to ~2.4px — below detectability.

**The key number:** the far ball is **~9px at native 1080p** (measured). That's
*not* an optics wall (I'd called 2–3px hopeless) — the signal is at the sensor, the
pipeline throws it away. So it's a **software/pipeline fix, not a camera change**, for
the median far ball. Only the sub-5px fastest balls are a true floor.

**We have 60fps footage** — the PGC Sept field test is all 1080p@60 (5 sessions,
~1hr), the real production camera. We'd just never tested detection on it at 60fps
because the pipeline downsamples first.

## Decision recorded
- **ADR-159**: keep TrackNet (the motion model is what works; TrackNetV3 and single-frame
  YOLO are both worse). The bottleneck is input downscaling — temporal (CFR 30fps) +
  spatial (1920→512). Fix the input, not the detector.
- Full detail + numbers: EXPERIMENTS.md 2026-10-25 (four scored runs).

## What to do next (not built)

   non-16:9 crop *hurt* (5% vs 18%) — aspect matters.
2. Longer-term alternative: **retrain TrackNet at higher input resolution** (keeps 9px
   as 9px, no tiling merge).
