# 2026-09-08

**Built a Diagnostics tab in the desktop app: the venue-survey screen someone can run standing in a gym with a laptop, before committing to a pilot.** It answers four questions — can this building upload fast enough, is the cloud console reachable, are the cameras online and recording at a usable frame rate, and is there disk space — and it answers the first one by actually measuring, not by asking the operator to install a speed-test app.

## Why upload speed became the question worth building a tool for

This started as a plain question about whether a venue needs any dedicated equipment beyond a laptop. Working through it produced a clear answer (no: nothing listens for incoming connections, the laptop only records and uploads, and all the video conversion happens back on the operator's own machine) — and one real cost hiding behind that answer.

Because the venue machine no longer converts anything, the whole session leaves the building at full camera bitrate. Measuring the real recordings already on disk: a court camera produces between 1.6 and 2.8 megabits per second, so a two-hour session is about 2.5 gigabytes going out over the venue's internet connection. On a 25 Mbps upload that's about 13 minutes. On 5 Mbps it's over an hour. Below about 3 Mbps per camera it never finishes at all in the sense that matters — the next session starts before the last one has finished uploading, and the venue falls permanently behind.

That's a per-venue fact nobody could look up. Now it takes one button.

## What makes the measurement trustworthy

Three decisions, each of which was the difference between a number and a *correct* number:

- **It uploads to the same place recordings go, the same way.** The code that sends a recording segment was split so the speed test uses it directly rather than a similar-looking copy written next to it. A test that talks to a nearby speed-test server over many parallel connections routinely reports several times what a single upload to our actual storage achieves — and the second number is the one that decides when a venue's highlights arrive.
- **It ignores the first two seconds.** Handing data to the network is not the same as it arriving; the operating system accepts the first few megabytes almost instantly into its own buffer, and connection setup sits in the same window. Counting those makes a slow link look fast.
- **It grows the test until the answer settles.** Measured on the workstation here, against real storage: an 8 MB test reported 27 Mbps, and a 64 MB test on the same connection over the same minute reported 38. The short test was wrong by 30%, low. So the test starts small (so a genuinely slow venue isn't stuck waiting) and steps up only while runs finish too quickly to trust.
- **It repeats the measurement three times and reports the middle one**, which was not the original plan — see the next section for why.

Nothing from the venue's cameras is uploaded for this — the test data is generated on the spot, and deleted from storage afterwards.

## The finding that changed the design, and a wrong first explanation

Running the same test repeatedly against real storage produced: 28.8, then 3.4, then 29.0, then 32.3 megabits per second. Same machine, same storage bucket, minutes apart. Not a slow drift — two distinct modes, roughly 3.5 or roughly 30, with no obvious pattern to which one a given connection lands in.

The first explanation was that the slow ones were going out over the newer internet addressing scheme and the fast ones over the older one. That was **checked and turned out to be wrong**: forcing each in turn produced both modes on both. So the question got chased properly, and the answer is now reasonably well established — **it is outside our system entirely**.

What was ruled out, each by measurement rather than argument:

- **The laptop, the app, and encryption.** Uploading to a server on the same machine ran at roughly 18 gigabits per second from inside the app; with encryption, 1.5–4.6 gigabits.
- **Packet loss.** This was the informative one. The slow connections show *no* lost packets at all, while the fast ones do lose a few — which is backwards from what a congested network looks like. A fast connection pushes hard enough that something eventually drops; a slow one never pushes hard enough to find out.
- **A "burst allowance" from the provider.** A single 128 MB upload held 30–38 Mbps for its whole 37 seconds, with no step down to a slower sustained rate.
- **The storage provider.** Alternating identical uploads between our storage and a completely different endpoint on the same network, in the same minute, showed both fast and slow on both — and not at the same times as each other. An effect that follows the connection rather than the destination isn't the destination's fault.

What that leaves is the building's own internet connection, where an individual upload lands in a roughly 4 Mbps regime and stays there for its whole life, while another one opened seconds later gets 30. **Opening several uploads at once does not rescue it** — four at a time totalled 15–23 Mbps, less than one good connection on its own, so the line itself tops out around 30.

Two consequences. First, the tool now takes three samples and reports the median, and when fastest and slowest differ by more than double it says so plainly, showing both estimates instead of one confident-looking number. Second, and more important: **real session uploads take exactly the same route**, so this affects them too. A session that uploads in 11 minutes on a good connection takes an hour and a half on a bad one. This is one building's line, so the number to trust is the one measured at the venue — which is the whole reason the tab exists.

## The rest of the tab

The other three checks each read something the app already knew and had never shown in one place: a round trip to the cloud console over the same connection the app's regular check-in uses; each camera's reachability alongside the resolution, frame rate and bitrate measured the last time it connected, flagged against the 30 fps floor that a previous session established halves detection quality when missed; and free disk space, expressed as hours of recording rather than gigabytes.

Every row is written to answer in the terms of what would go wrong. Not "8.4 Mbps" but "a two-hour session would take 40 minutes to upload — reels arrive after everyone has left".

## Verified

The whole thing was run end to end, against real infrastructure rather than stand-ins: the desktop app talking to a locally running copy of the cloud console, authenticating with its real device credential, uploading to real cloud storage, and rendering the result. Two complete runs — one where the connection was in its slow mode, which produced exactly the "inconsistent" warning it should have, and one where it wasn't, which produced a tight, unwarned result. Rejections were checked separately: no credential and a wrong credential are both refused.

The other three rows were checked against this machine's real cameras, and one earned its place immediately — a camera streaming at 17 frames per second was correctly flagged as below the 30 the pipeline needs, while the other three passed.

That camera (Court 2) is on wifi, which the operator pointed out and which matters: it's very likely the frame loss over wifi that an earlier session already measured and wrote up, not a camera setting anyone can change. The check reports what the stream actually delivers, which is the right thing to gate on, but a camera *set* to 15fps and a wifi camera *losing* frames produce an identical row and need different fixes. The row's wording should say so — noted below.

Eleven automated tests cover the arithmetic, including both cases where it deliberately falls back to a more pessimistic reading, and prove the shared upload code still sends what our storage requires — a speed test that quietly broke real recording uploads would be a bad trade.

One real bug surfaced from testing and was fixed rather than noted: a test whose cleanup didn't run left an 8 MB object behind in storage, because the cleanup step can only be best-effort (the console can be unreachable at exactly the moment a test finishes — which is one of the things a venue survey is looking for). The cloud side now sweeps up an agent's own stale test objects whenever a new test starts. Confirmed afterwards: storage is empty.

**Not verified:** the cloud-side route has never run on the deployed site, only locally, and no venue machine has run the tab. The speeds above are the operator's own workstation, which is not a venue.
