## Desktop client: real manual recording built (PIC-66)

Operator asked directly whether the app could pull a live stream yet
("are we able to pull live stream?"), got an honest no (confirmed by
grepping the repo, not recalling from memory -- the only place
`-rtsp_transport` appeared was the standalone decode-capacity benchmark
script, not anything the app calls itself), then asked whether ffmpeg
could be built into the desktop client. Yes, and `TECH_SPEC.md` §1.2
already spec'd the exact command -- scoped one real fork before
building: manual Start/Stop button vs. tied to the Schedule sessions
built the day before. Operator picked manual, "simpler to get right
first."

**Built:** `electron/capture.js` -- `startRecording`/`stopRecording`/
`recordingStatus`, module-level state (survives navigating away from a
camera's detail page, since it's a background process, not page state).
Command shape exactly `TECH_SPEC.md` §1.2: RTSP pull via `ffmpeg
-rtsp_transport tcp`, `-c copy` (no re-encode, sidesteps `PIC-67`'s
GPU-encoder question entirely), `-f segment -segment_time 600` (a crash
or Wi-Fi drop costs one segment, not the session, per the real frame-
drop testing in `DECISIONS.md` ADR-030/032), `-use_wallclock_as_timestamps
1` (same ADR -- camera RTP timestamps are unreliable). Stop is always
`SIGINT`, never a hard kill (ADR-031: that corrupts the container),
including on app quit via a new `before-quit` handler that awaits any
active recording actually finishing its clean stop first.

**Real bug #1, found by actually running this against a real camera, not
by trusting the spec:** `TECH_SPEC.md`'s own example command names its
output `session-%03d.mp4` -- but its own prose two lines later says
`pcm_alaw` audio requires MKV, since MP4 has no codec tag for it. The
Tapo C200 streams exactly that codec. Copying the example literally
produced a real, quiet-looking failure the first time this ran for real:
0-byte output file, `ffmpeg` exited almost immediately (`Could not find
tag for codec pcm_alaw in stream #1... Could not write header`).
Diagnosed by running the exact command by hand outside the app (not
guessing from the error text alone) -- first with `-f null -` to confirm
the RTSP connection and credentials were fine (they were), then with the
real segment muxer to reproduce the actual failure, then swapping to
`.mkv` and confirming a real, valid, ffprobe-clean file came out.

**Real bug #2, found the same way:** the first version of `startRecording`
returned success the instant `ffmpeg` was spawned, so bug #1's fast
failure reported "recording started" and then silently reverted to
"Start recording" seconds later with zero explanation -- looked exactly
like a UI bug, not a diagnosable `ffmpeg` error. Fixed with a 2-second
startup grace period: a fast exit within that window now rejects with
the real last line of `ffmpeg`'s stderr instead of a false success.

**Verified end-to-end against both real cameras, not just one:**
- **Tapo C200** (ONVIF-added, streamUri has no embedded credentials --
  exercises `authenticatedStreamUri()`'s credential-injection path):
  started via the real UI button, confirmed a real `ffmpeg` process and
  a genuinely growing file (1MB -> 3.4MB over 5s), stopped via the real
  Stop button, confirmed clean process exit and a valid 28.47s
  1920x1080 h264+pcm_alaw file via `ffprobe`.
- **Synology BC510** (RTSP-fallback-added, streamUri already has
  embedded credentials -- exercises the other branch of that same
  function): same full cycle, confirmed the recording survived
  navigating away to the C200's page and back (module-level state, not
  page state, working as designed) and picked up the correct real
  elapsed time (0:45) on return. Clean stop, valid 54.3s h264+pcm_mulaw
  file. Different audio codec than the C200 -- confirms the `.mkv` fix
  isn't overfit to one specific codec.
- **Double-start guard:** called `captureAPI.start` twice for the same
  camera back to back -- second call correctly rejected
  ("Already recording this camera"), confirming error propagation
  through the IPC boundary works, not just the happy path.

All test recordings deleted afterward -- verification data, not
something the operator asked to actually keep. `desktop/README.md` (new
"Recording" section, "Known gaps" corrected) and `TECH_SPEC.md` §12
(new `capture.js` entry, corrected `desktop/` header and `pages/`
description) updated in the same change.

**Not done:** tying this to the Schedule page's booked sessions (the
Schedule page's own copy already promises "each booking becomes its own
highlight reel once automatic capture is built" -- this is the piece
that makes that literally true, deliberately deferred, not forgotten).
Also still open: CFR conversion (`PIC-67`, NVIDIA-only), upload to
cloud, receiving cloud output back and cutting from local full-res, CDN
delivery -- the rest of `STRATEGY.md` §5's shape.

## Architecture split locked in: thin local agent vs. cloud web app (`DECISIONS.md` ADR-071)

Right after the recording work above, operator pushed back on where the
system's weight should sit: "I was actually expecting heavy lifting on
the web app (including camera management, etc)." Real, substantive
architecture conversation, not a feature request -- worked through it in
three passes rather than jumping to an answer: first the forcing
constraint (ONVIF discovery is UDP multicast, cameras sit on a private
LAN with no port-forwarding, so *something* has to run at the venue no
matter what), then three candidate shapes (local-only web UI / cloud-
hosted-with-relay / hybrid) with their real tradeoffs, then the
operator's own concrete proposal for the split: local agent keeps camera
management, calibration, transcoding, and uploading; scheduling and
other court-management tasks move to a cloud web app.

**Checked against the real repo before agreeing to anything** -- `webapp/`
(Flask) is not a hosted, multi-venue, venue-facing web app at all; it's
a single-operator local tool (upload footage, calibrate, run the
pipeline, download a reel). So "the web app" the operator is picturing
is close to entirely unbuilt, the same place `desktop/` itself was a
few days ago -- worth saying plainly rather than letting the
conversation proceed on an assumption.

**Locked in as `DECISIONS.md` ADR-071** (architecture only, nothing
built): local agent keeps everything LAN-bound or needing the local
file on disk (camera discovery/management, recording, calibration,
transcode, upload, and -- per ADR-043's own privacy reasoning -- cutting
the final reel from local full-res footage, since that file never
leaves the venue regardless of how the rest splits). Cloud web app
takes everything that's just data (scheduling, court/venue management,
footage review, multi-venue admin, delivery to players). Connectivity
is outbound-only from the local agent (polls or maintains a lightweight
connection for commands, never an inbound port on the venue's router) --
decided, not defaulted to, since the operator explicitly located the
web app "on the cloud," which rules out a local-only web UI. Existing
Python (`r2_storage.py`, calibration, ffmpeg CFR calls) gets invoked as
subprocesses from the local agent rather than reimplemented in JS --
confirms `PIC-68`'s already-scoped plan rather than changing it.

One real nuance made explicit rather than left implicit: scheduling
*data and UI* move to the cloud, but *triggering a recording on time*
still has to execute locally -- closed by having the local agent
poll/cache the relevant schedule over the same outbound channel, not a
separate mechanism. Today's `desktop/` Schedule feature (built
2026-09-01) is explicitly interim -- real, useful now, and the reference
design to port, but not its permanent home; a future migration should
remove it from `desktop/` once the web app exists rather than
maintaining the feature in two places.

`STRATEGY.md` §5 updated in the same change -- its desktop-client
section still described the old, undivided scope (everything from
camera discovery through CDN delivery as one client's job); rewritten to
describe the local agent's now-narrower scope plus a new subsection for
the cloud web app, both pointing back to ADR-071.

## PIC-68: desktop client wired to `cloud_pipeline` (first real ADR-071 build)

Operator: "let's proceed with the architecture, starting with making the
desktop utility thin." The most concrete, already-scoped piece of that --
Linear `PIC-68`, explicitly cited in ADR-071's consequences -- is the local
agent invoking the existing, working Python (`cloud_pipeline`/`webapp`)
as a subprocess instead of reimplementing R2 upload, RunPod dispatch, or
reel-cutting in JS. Built end to end:

- **`cloud_pipeline/run_desktop_job.py`** (new) -- writes `job.json`, then
  calls `webapp/pipeline.py`'s `run_cloud_job(job_dir)` on a background
  thread. A SIGINT/SIGTERM from the Electron parent runs
  `webapp.pipeline.cancel_job(job_dir)` from the (now-unblocked) main
  thread -- the same mechanism the Flask dashboard's own cancel button
  already relies on, which terminates any RunPod pod already created, not
  just the local process. Chose to reuse `webapp/pipeline.py`'s
  `job_dir`/`status.json`/`log.txt` contract wholesale rather than invent
  a second one, per PIC-68's own suggestion.
- **`desktop/electron/pipeline.js`** (new) -- spawns the script above,
  first concatenating `capture.js`'s 10-minute segments into one file
  (stream-copy `ffmpeg concat`, same `-c copy` capture already uses,
  since the cloud pipeline needs one continuous video and nothing
  produced that before). Module-level state, same as `capture.js`, so a
  job survives navigating away from the camera page.
- **`capture.js`**: added `listRecordings` -- nothing tracked past
  recordings anywhere before this, only the filesystem itself.
- **`store.js`/`system.js`**: a per-camera `calibPath` field + a native
  file picker, deliberately not a calibration flow -- PIC-68's own scope
  stops at "pass an existing `calib.json` path in."
- **`CameraDetailPage.jsx`**: a new "Cloud pipeline" panel -- calib file
  picker, one row per recording, "Send to cloud," live stage/progress by
  polling `status.json` every 2s (same cadence `RecordingControl` already
  uses for `capture:status`), Cancel while running.

**Real bug found and fixed by actually running the failure path, not by
reading the code and trusting it:** `webapp/pipeline.py`'s
`run_cloud_job(job_dir)` only caught `Exception`, but
`cloud_pipeline/run_cloud_job.py`'s missing-calibration guard raises
`SystemExit` -- not an `Exception` subclass. A job with no calibration
silently escaped that `except` block uncaught; `status.json` stayed stuck
at `stage="drift_check"` forever, never reaching `stage="error"`. Caught
by actually spawning the new wrapper against a missing calib path (a
scratch venv with the repo's Python deps, since `desktop/`'s Node process
needs a real `python3` on `PATH` with `boto3`/`opencv-python`/etc.
installed, same pre-existing environment assumption `run_cloud_job.py`'s
own CLI already had -- not something this change altered) and watching
`status.json` never move past `drift_check` with exit code 0 (should have
been 1). This was a live bug in the Flask dashboard's cloud-job route
too, not something new introduced here -- fixed at the shared
`except (Exception, SystemExit)` in `webapp/pipeline.py`, one line, not
worked around in the new file.

**Verified:** the fix, re-run the same way -- `status.json` now reaches
`stage="error"` with the real guard message, exit code 1, `log.txt`
carries the traceback. `vite build` clean. Full `pytest` suite: 128
passed (2 pre-existing collection errors, `google-genai`/retired
`archive/` module, unrelated to this change).

**Deliberately not run:** a real end-to-end job against R2/RunPod --
that uploads real data and creates a real billed GPU pod, so it needs the
operator's own explicit go-ahead and real per-venue credentials, not
something to trigger incidentally while verifying plumbing. `PIC-71`
(per-venue scoped credentials) is still a hard prerequisite before this
can point at anything but the operator's own `.env`; cancellation's own
pod-termination path is therefore also unverified against a real pod, only
reviewed against `cancel_job()`'s existing, already-proven logic.

`desktop/`, `cloud_pipeline/`, `capture.js`, `store.js`, `system.js`,
