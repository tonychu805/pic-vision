# 2026-09-02

## Desktop client: real manual recording built (PIC-66)

Operator asked directly whether the app could pull a live stream yet
("are we able to pull live stream?"), got an honest no (confirmed by
grepping the repo, not recalling from memory -- the only place
`-rtsp_transport` appeared was the standalone decode-capacity benchmark
script, not anything the app calls itself), then asked whether ffmpeg
could be built into the desktop client. Yes, and `TECH_SPEC.md` §1.2
already spec'd the exact command -- scoped one real fork before
building: manual Start/Stop button vs. tied to the Schedule sessions
built the day before. Operator picked manual, "simpler to get right
first."

**Built:** `electron/capture.js` -- `startRecording`/`stopRecording`/
`recordingStatus`, module-level state (survives navigating away from a
camera's detail page, since it's a background process, not page state).
Command shape exactly `TECH_SPEC.md` §1.2: RTSP pull via `ffmpeg
-rtsp_transport tcp`, `-c copy` (no re-encode, sidesteps `PIC-67`'s
GPU-encoder question entirely), `-f segment -segment_time 600` (a crash
or Wi-Fi drop costs one segment, not the session, per the real frame-
drop testing in `DECISIONS.md` ADR-030/032), `-use_wallclock_as_timestamps
1` (same ADR -- camera RTP timestamps are unreliable). Stop is always
`SIGINT`, never a hard kill (ADR-031: that corrupts the container),
including on app quit via a new `before-quit` handler that awaits any
active recording actually finishing its clean stop first.

**Real bug #1, found by actually running this against a real camera, not
by trusting the spec:** `TECH_SPEC.md`'s own example command names its
output `session-%03d.mp4` -- but its own prose two lines later says
`pcm_alaw` audio requires MKV, since MP4 has no codec tag for it. The
Tapo C200 streams exactly that codec. Copying the example literally
produced a real, quiet-looking failure the first time this ran for real:
0-byte output file, `ffmpeg` exited almost immediately (`Could not find
tag for codec pcm_alaw in stream #1... Could not write header`).
Diagnosed by running the exact command by hand outside the app (not
guessing from the error text alone) -- first with `-f null -` to confirm
the RTSP connection and credentials were fine (they were), then with the
real segment muxer to reproduce the actual failure, then swapping to
`.mkv` and confirming a real, valid, ffprobe-clean file came out.

**Real bug #2, found the same way:** the first version of `startRecording`
returned success the instant `ffmpeg` was spawned, so bug #1's fast
failure reported "recording started" and then silently reverted to
"Start recording" seconds later with zero explanation -- looked exactly
like a UI bug, not a diagnosable `ffmpeg` error. Fixed with a 2-second
startup grace period: a fast exit within that window now rejects with
the real last line of `ffmpeg`'s stderr instead of a false success.

**Verified end-to-end against both real cameras, not just one:**
- **Tapo C200** (ONVIF-added, streamUri has no embedded credentials --
  exercises `authenticatedStreamUri()`'s credential-injection path):
  started via the real UI button, confirmed a real `ffmpeg` process and
  a genuinely growing file (1MB -> 3.4MB over 5s), stopped via the real
  Stop button, confirmed clean process exit and a valid 28.47s
  1920x1080 h264+pcm_alaw file via `ffprobe`.
- **Synology BC510** (RTSP-fallback-added, streamUri already has
  embedded credentials -- exercises the other branch of that same
  function): same full cycle, confirmed the recording survived
  navigating away to the C200's page and back (module-level state, not
  page state, working as designed) and picked up the correct real
  elapsed time (0:45) on return. Clean stop, valid 54.3s h264+pcm_mulaw
  file. Different audio codec than the C200 -- confirms the `.mkv` fix
  isn't overfit to one specific codec.
- **Double-start guard:** called `captureAPI.start` twice for the same
  camera back to back -- second call correctly rejected
  ("Already recording this camera"), confirming error propagation
  through the IPC boundary works, not just the happy path.
