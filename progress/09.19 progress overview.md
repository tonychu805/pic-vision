# 2026-09-19

## Yesterday's bucket split broke every upload; found by asking whether anything was running

Answering a plain question — "are any jobs running right now" — turned up one job parked in `uploading` for 11 minutes, and behind it a bug that had broken **every** "Send to cloud" from the moment yesterday's PIC-153 fix deployed.

**The upload had actually worked.** Job `e6a9f2af` ("Sample 1", agent Montenegro) was created 01:41:08 UTC and never advanced. But checking R2 directly rather than trusting the row: the file was there, 271,472,517 bytes, written at 01:42:15 — 67 seconds after the job started — matching the size the agent declared byte for byte, with no half-finished multipart upload behind it. The footage was complete the whole time. Nothing was billing; no pod was ever created.

**Only the write half of yesterday's change had moved.** After uploading, the agent calls `complete` on the job, and that handler verifies each segment really is in R2 at the declared size before letting the job queue — a good check, and the thing that caught this. But it looked in the **public** bucket, while yesterday's split sent the upload to the **private** one. Confirmed in both directions against live R2 with the job's own key:

```
PUBLIC  test-ingest-runpod        -> NOT FOUND   (what the check looked at)
PRIVATE pic-vision-ingest-private -> FOUND, 271472517 bytes  (where it was)
```

So `complete` answered "some segments are missing or incomplete in storage", the agent's call threw, and the row stayed at a status the runner never claims. This was not one unlucky job: of the 13 jobs on record, 1 used the private bucket (this one, failed) and 12 used the public one, all from before the split. This was simply the first upload to exercise the path.

**A second one in the same file, not yet fired, and worse in kind.** The retry path for an expired upload URL also defaulted to the public bucket — so a venue slow enough to outlive the URL's life would have been handed a fresh upload slot **into the public bucket**, quietly reopening the exposure PIC-153 existed to close. This upload finished in 67 seconds, far inside that window, so it never happened; found by reading the file, not by it going wrong.

**The fix reads the bucket off the job's own row** rather than recomputing it. That column records where the upload URLs were minted, and a job's bytes never move afterwards, so the 12 old jobs keep resolving to the public bucket and everything new resolves private — no migration, no cutover date to get right. `jobSegmentBucket` is a pure function with four tests, one of which deliberately pins the *legacy* direction so a later change can't break the old jobs the mirror-image way.

41 console tests (4 new), typecheck and production build clean. Console commit `e0cf057`, deployed and live. Filed as `PIC-155`.

**This is the failure `CLAUDE.md` already describes**, under "remove the secret, then prove it still works". Yesterday's change added tests asserting the new private-bucket key shape; they passed, and the feature was broken. Removal is not correctness — and the paired assertion that would have caught this (prove an upload can still *finish*) is exactly what the rule asks for and exactly what was missing.

**Worth fixing separately: a stuck job is invisible.** The agent logged a local failure, the console showed the row as in-progress indefinitely, and nothing raised it — it was found by chance, 11 minutes in, because someone asked. A staleness check (`uploading` with no movement for N minutes while its segments are all present in its own bucket) would have caught it immediately. Same shape of gap as `PIC-109`'s "single point of failure with no alerting", noted on `PIC-155` rather than filed on its own yet.

**Still to do on this:** job `e6a9f2af` can be recovered rather than re-uploaded — its footage is intact in R2 and the check it failed now passes — but flipping it to `queued` starts a real billed GPU job, so it is waiting on an explicit go-ahead. That will also be the first end-to-end confirmation of the fix, and of every other ADR-093 pipeline change from yesterday, none of which has met a live pod yet.
