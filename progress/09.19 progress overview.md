# 2026-09-19

## Yesterday's bucket split broke every upload; found by asking whether anything was running

Answering a plain question — "are any jobs running right now" — turned up one job parked in `uploading` for 11 minutes, and behind it a bug that had broken **every** "Send to cloud" from the moment yesterday's PIC-153 fix deployed.

**The upload had actually worked.** Job `e6a9f2af` ("Sample 1", agent Montenegro) was created 01:41:08 UTC and never advanced. But checking R2 directly rather than trusting the row: the file was there, 271,472,517 bytes, written at 01:42:15 — 67 seconds after the job started — matching the size the agent declared byte for byte, with no half-finished multipart upload behind it. The footage was complete the whole time. Nothing was billing; no pod was ever created.

**Only the write half of yesterday's change had moved.** After uploading, the agent calls `complete` on the job, and that handler verifies each segment really is in R2 at the declared size before letting the job queue — a good check, and the thing that caught this. But it looked in the **public** bucket, while yesterday's split sent the upload to the **private** one. Confirmed in both directions against live R2 with the job's own key:

```
PUBLIC  test-ingest-runpod        -> NOT FOUND   (what the check looked at)
PRIVATE pic-vision-ingest-private -> FOUND, 271472517 bytes  (where it was)
```

So `complete` answered "some segments are missing or incomplete in storage", the agent's call threw, and the row stayed at a status the runner never claims. This was not one unlucky job: of the 13 jobs on record, 1 used the private bucket (this one, failed) and 12 used the public one, all from before the split. This was simply the first upload to exercise the path.

**A second one in the same file, not yet fired, and worse in kind.** The retry path for an expired upload URL also defaulted to the public bucket — so a venue slow enough to outlive the URL's life would have been handed a fresh upload slot **into the public bucket**, quietly reopening the exposure PIC-153 existed to close. This upload finished in 67 seconds, far inside that window, so it never happened; found by reading the file, not by it going wrong.

**The fix reads the bucket off the job's own row** rather than recomputing it. That column records where the upload URLs were minted, and a job's bytes never move afterwards, so the 12 old jobs keep resolving to the public bucket and everything new resolves private — no migration, no cutover date to get right. `jobSegmentBucket` is a pure function with four tests, one of which deliberately pins the *legacy* direction so a later change can't break the old jobs the mirror-image way.

41 console tests (4 new), typecheck and production build clean. Console commit `e0cf057`, deployed and live. Filed as `PIC-155`.

**This is the failure `CLAUDE.md` already describes**, under "remove the secret, then prove it still works". Yesterday's change added tests asserting the new private-bucket key shape; they passed, and the feature was broken. Removal is not correctness — and the paired assertion that would have caught this (prove an upload can still *finish*) is exactly what the rule asks for and exactly what was missing.

**Worth fixing separately: a stuck job is invisible.** The agent logged a local failure, the console showed the row as in-progress indefinitely, and nothing raised it — it was found by chance, 11 minutes in, because someone asked. A staleness check (`uploading` with no movement for N minutes while its segments are all present in its own bucket) would have caught it immediately. Same shape of gap as `PIC-109`'s "single point of failure with no alerting", noted on `PIC-155` rather than filed on its own yet.

**Still to do on this:** job `e6a9f2af` can be recovered rather than re-uploaded — its footage is intact in R2 and the check it failed now passes — but flipping it to `queued` starts a real billed GPU job, so it is waiting on an explicit go-ahead. That will also be the first end-to-end confirmation of the fix, and of every other ADR-093 pipeline change from yesterday, none of which has met a live pod yet.

## The first real pod job found two more things, one of them self-inflicted

With uploads working again, the stalled job was released to run — the first time any of yesterday's pipeline changes met a live pod. It failed twice, and both failures were worth having.

**Four things did work, first time on real hardware.** The pod was created in 2 seconds and checked in immediately (no stuck container). It pulled its segments from the *private* bucket, which is the pod-side half of yesterday's PIC-153 split finally confirmed. Exactly one pod was created on the primary image, so the new one-shot retry correctly stayed dormant — the case most worth getting right, since a misfire doubles the GPU bill on every successful run. And the pod terminated itself; zero pods left on the account.

**Failure one: yesterday's ffmpeg change couldn't encode at all (`PIC-156`).** The convert step died on `Unrecognized option 'cq'`. `-cq` is NVIDIA-encoder-only, and the static binary PIC-154 adopted — the one the desktop app ships — turns out to contain **no NVIDIA encoder whatsoever**. Checked against the binary itself, not guessed: `7.0.2-static` from johnvansickle.com, nothing matching nvenc in its encoder list, no `--enable-cuda/nvenc/nonfree` in its build flags.

The delivery machinery PIC-154 built was never the problem — the binary downloaded from R2, landed in `/usr/local/bin`, won the PATH race and ran. Only the *choice* of binary was wrong, and it looked free because the desktop app never encodes anything (recording is a stream copy, live view an MJPEG remux), so the pod is the one consumer needing an encoder the desktop never touches. Two consumers, different requirements, one of them checked.

Replaced with a BtbN `linux64-gpl` build, cached in R2 the same way, so every actual benefit of PIC-154 survives: no package mirror in the per-job path, a version that can't drift, no per-job install. **Verified on this workstation's RTX 2000 Ada — the same GPU model RunPod rents us — rather than by a version string**, since a passing version string is exactly what hid the defect: the encoder is present, a real encode completes, no missing libraries, and both the old and new CFR flag spellings are accepted (so the existing one needed no change, and the code comment justifying it by reference to a now-deleted apt ffmpeg says so instead).

Worth recording for its own sake: **the first download of that build was byte-perfect on size and still corrupt.** Caught only against BtbN's published checksums, after which the uploaded R2 copies were re-verified by downloading them back and comparing hashes rather than content-length. Same shape as trusting a version string — the cheap check passed and the real one hadn't run.

**Failure two, caused by the first, and mine: the failed run deleted its own input (now fixed).** The retry 404'd on its own segments, because cleanup deleted the venue's uploaded footage from a `finally` block — on every outcome, success or failure. So the 271MB that had been sitting intact in R2 was gone, and the only way to retry became re-uploading it. This behaviour is described in yesterday's entry, was read this morning, and was quoted back before the run was started anyway; a server-side copy to a safe key first would have cost nothing.

Segments are now kept unless the job actually reached `done`. The subtle part: success can't be inferred from whether an exception was raised, because the pod reports its own terminal status and self-terminates — a job that fails *on the pod* returns through the success path, and both of today's failures logged "finished", not "FAILED". So cleanup reads the status back from the console (whose runner endpoint already returned it — verified against the live console, which answers `error` for this very job). An unreadable status counts as not-done: keeping wrongly costs storage, deleting wrongly costs a venue their session.

Six tests, paired on purpose: three that segments survive error/cancelled/unknown, **one that a successful job still deletes them** — without which "never delete anything" would pass everything else while leaking every session ever uploaded — one that cleanup really asks the console, and one that local scratch still goes either way.

On a two-hour session this was ~2.5GB back over a venue's uplink, on a link already measured as bimodal, spent because a pod hit a transient error. Yesterday made the reverse case safe — a finished reel can't be lost to a console hiccup; the input side had nothing.

175 Python tests (6 new), 41 console tests. Commits `245e26c` (PIC-156), `5bd2d99` (cleanup).

**Still unproven on a real pod, unchanged by any of this:** the convert with the new ffmpeg, inference, reel cutting, the upload to the public output bucket, and the final-report retry. The next run is still the first look at all five, and it needs a fresh "Send to cloud" from the desktop app since the previous upload is gone.

**Follow-up this creates:** nothing reclaims the segments of a job that never succeeds. An R2 lifecycle rule on the `ingest/` prefix is the intended tool and does not exist yet — worth doing before storage accumulates, and deliberately preferred over a `finally` block because it does not have to be right on the first try to avoid costing a venue an upload.

## The venue visit: why the app couldn't find their cameras, and what it now says instead

A venue visit, and a different kind of problem from the pod work above. On the venue's guest WiFi, no cameras were findable. They belong to the venue owner and turned out to be Tapo — TP-Link cloud cameras, watched through the vendor's app rather than over the local network.

**Nothing was broken.** The cameras are almost certainly on a different network from the one the laptop was on, or on guest WiFi that deliberately hides devices from each other, or both. That is the intended behaviour of a guest network, not a fault.

**What was wrong is that the app had no way to say so.** Its detection side is actually complete — it already does everything that was done by hand at the venue: ONVIF discovery, SSDP, an RTSP port sweep across the whole subnet with extra ranges you can configure, manufacturer lookup from the MAC address, and adding a camera by IP or by pasting an RTSP URL. All of it would have come back with the same result, because the obstacle is enforced by the venue's access point and nothing on the laptop can cross it. And then the screen said **"Nothing found on this network"** — one sentence covering four situations that need four different responses: no cameras here, cameras on another network, a network that hides its devices, or a camera whose streaming was never switched on. Only the second is something the operator can fix alone.

**So the empty screen now works out which one it is** (`desktop/electron/cameras/networkPresence.js`, ADR-103). When a scan finishes and finds nothing, it spends about three seconds on three questions — and, importantly, none of them touch anyone else's device:

- What does this computer's own address table know? After a sweep has asked about all 254 addresses, this is the telling one. A network that hides its devices still lets you talk to the router, so the table ends up holding the router and nothing else.
- Did anything answer the general "is anyone there?" question the app already broadcasts on every scan?
- Listening quietly for a few seconds, does anything announce itself unprompted?

If nothing at all is visible, the screen now says so plainly, and says the only thing that actually helps: *ask the venue to put this computer on the same network as their cameras — their main or camera network, not the guest one.* If devices **are** visible but none is a camera, it says that instead, and points at the two real causes. Underneath either one it prints the numbers it based that on, so the reading can be checked rather than believed.

**A measurement that changed the design.** On a real network with 11 live devices, one three-second listening window heard two of them and the next heard none. So silence over a few seconds proves nothing, and that signal is only ever allowed to *rule out* the "this network hides its devices" conclusion, never to support it. More generally the code is tuned to avoid claiming isolation wrongly — a false accusation there sends someone to argue with a venue owner about their WiFi, which is worse than being vague.

**What was deliberately not built.** Scanning harder — more ports, vendor fingerprinting, reaching into neighbouring subnets. None of it crosses the obstacle, and it would turn the agent into a network scanner running on someone else's infrastructure.

**Which raises something worth deciding on purpose.** The Scan button already port-scans the entire local subnet. On a venue where the agent was installed as part of a deal, that is plainly fine. On an exploratory visit over a venue's guest WiFi, before any agreement exists, it is not. Today those are the same button, with nothing distinguishing them.

**Two follow-ups this suggests, neither built:** a per-vendor card telling the operator exactly what to ask the owner for (for Tapo: the RTSP account behind Settings → Advanced → Camera Account), and an exportable venue-readiness sheet from the Diagnostics tab so a first visit ends with a document rather than an awkward conversation. Also worth knowing before that second visit: Tapo main streams are commonly 15fps, and 15fps halves recall (ADR-086/087) — a camera can connect, authenticate and still be useless.

**Verified:** 140 desktop tests (9 new), renderer builds clean, and the module run for real against this machine's network, where it correctly reported "devices here, none of them a camera". **Not verified:** the new empty-state panel as rendered — the remote-debugging connection was unreachable this session on two fresh launches, so that part rests on a clean build and the logic tests, not on having seen it.

## Cancel during "Send to cloud" didn't stop anything

Reported from actually using it: Cancel appeared to do nothing, and then — on a second look — "it stops after a while, just not immediately."

**Both observations were the same bug.** The click did reach the cloud console, and the console did the right thing: it marked the job cancelled straight away. The desktop app then ignored its own cancellation completely and **kept uploading every remaining segment**. On a two-hour session that's gigabytes going over the venue's connection after you asked it to stop, on a link we already know swings between about 3 and 30 Mbps. The "stop after a while" was the upload finally reaching the end.

And what it said when it got there was wrong too. Having uploaded everything, the app asked the console to queue the job, the console answered "that job is already cancelled", and the app reported **"upload failed"**. So a cancellation you asked for came back as a failure you didn't, several minutes late.

**Why it was built that way.** The code kept a note of each in-flight job whose own comment described it as holding a "cancelled" flag. Nothing ever set that flag, and the upload loop never checked it. The flag was designed and then not wired up, so cancelling only ever told the console — the one participant that wasn't doing the uploading.

**What it does now.** The local upload stops first, before anything is sent to the console, because that's the half spending the venue's bandwidth. The segment currently in flight is torn down mid-transfer rather than allowed to finish — segments are hundreds of megabytes, so waiting for a tidy boundary isn't stopping — and the loop refuses to start the next one. The app no longer tells the console to queue a job it already cancelled, so the "upload failed" message is gone.

The screen now changes the moment you click. It says **"Stopping…"**, not "Cancelled", because those are different things: a job already running on a GPU hasn't actually stopped until the pod says so. It settles to "Cancelled" once that's actually true. And while a pod is winding down, the row keeps saying "Stopping…" instead of flipping back to "Running TrackNet inference" on the next refresh — which would have looked like the button was ignored all over again.

**Two smaller things fixed alongside.** Cancel used to do nothing at all if the app had been restarted since the job started, because the job's id was only held in memory — it's written to disk too, and is now read back from there. And that path now follows the job to completion, so the row reaches a real end state instead of sitting on "Stopping…" indefinitely.

**Verified:** 143 tests (3 new), and the new ones were checked the important way round — with the fix removed they fail, with it in place they pass, and the test that a normal upload still works passes either way. They run against a real server that stalls mid-transfer, and the assertion that matters is that the server never receives the whole segment.

**Not verified:** nobody has pressed Cancel on a real in-flight upload since the change. The next "Send to cloud" is the first chance — the same run that will also be the first look at the five pod stages that have never succeeded.

## The 1.5.0 build crashed on launch

Cut a desktop release (1.5.0) carrying five changes that had never been in an installed build, and it didn't open. Opening it gave "A JavaScript error occurred in the main process" and stopped there, for anyone with a camera set up.

**The cause was a single missing variable, a day old.** Yesterday's frame-rate fix moved that calculation out into its own small function and deleted a leftover value along with the old code. The line that measures a camera's bitrate was still using that value. It sits three lines below, in the same block. Every attempt to check a camera's stream threw — and because that check runs when the app opens, the app never opened.

**The uncomfortable part is why nothing caught it.** Yesterday's change came with nine new tests, all passing, all of them about the frame-rate maths — which was genuinely fixed. But those tests exercise the small extracted function, and *nothing in the suite has ever run the larger function it lives inside.* The test file even says so, as a deliberate choice: keep the maths pure so it can be tested without a real camera or a real ffprobe. That is the right instinct about cameras, and it quietly became "never run the real thing at all". So a refactor could break everything around the part being tested and still report nine green ticks.

It's the same lesson already written into the project's own conventions from an earlier incident — a test proving the new thing works has to sit beside one proving the feature still works — arriving from the opposite direction. Last time we proved a secret was gone without proving the app still functioned. This time we proved the extracted maths were right without proving anything still called them.

**And I shipped it.** The release bundled five commits nobody had run, and I cut it without opening the app against any of them. A short launch earlier in the day only confirmed the process started; it never got as far as looking at a camera.

**Fixed, and now covered properly.** The missing value is restored (deliberately the full measurement window, not the trimmed one the frame-rate estimate uses, since the byte count covers everything). There's a new test that runs the whole measurement for real against a clip generated from a synthetic test pattern — no camera involved, which was always what the rule was about. It fails with the fix removed, reproducing the exact error from the crash dialog, and passes with it.

**Scope:** 1.5.0 only. Yesterday's change landed after 1.4.0 was tagged, so 1.4.0 is unaffected and is the last good build.
