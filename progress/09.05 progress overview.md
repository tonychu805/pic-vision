**Along the way, "Court 3 doesn't have a Send to cloud button" turned out to be a real, findable bug, not user error.** A sample-clip camera's recording folder is derived only from its **label** (`Court_3/`), not the camera's own id -- and that same folder had been used months earlier (2026-09-03) by a local-GPU dev-testing session (`scripts/burst_moment_reel.py` experiments) that left a completed `cloud_job/status.json` sitting there. `pipelineStatusForRecording()` reads status purely by directory path, so the brand-new Court 3 camera inherited that old "done" status the instant it was created, hiding the Start button (`CloudJobRow` never renders it once `hasRun` is true). Fixed by deleting the stale `cloud_job/` folder (~4.2GB) -- confirmed the camera's own data (`sampleClipPath`, `calibPath`) was correct the whole time. Flagged, not fixed: the underlying label-not-id folder-keying bug can recur any time a sample-clip camera is removed and re-added under the same name -- deferred, operator's call.

**Burst reel's target duration shortened from 60s to 30s** (`cloud_pipeline/pod_cut.py`'s `BURST_TARGET_SEC`) -- operator request after seeing real output from the Court 3 run, "reads as a tighter quick-hits clip." One-line change, `DECISIONS.md`/`TECH_SPEC.md` updated to match, takes effect automatically on the next job (the pod gets a fresh copy of `pod_cut.py` via tarball every run, nothing to deploy).

**A real architecture conversation about where cloud-side orchestration code should actually run, working through several real options with verified numbers, not assumptions.** Started from "does full production mean hosting all the code in the cloud" -- clarified the actual split: camera-facing work (ONVIF/RTSP) has a hard LAN constraint and stays local no matter what; everything else (console, storage, GPU inference itself) is already cloud-hosted. The live question became: `run_cloud_job.py`'s RunPod-orchestration half (create pod, SSH, poll, cut, terminate) currently runs as one bundled local script alongside the parts that genuinely need local disk (CFR convert, proxy encode) -- but the orchestration half has no such dependency once the proxy is uploaded, so it's a real, moveable seam. Evaluated where to host it: **Fly.io** (no free tier since Oct 2024, ~$2-5/mo minimum) and **Railway** (real free tier is effectively $1/mo credit, practical minimum $5/mo Hobby) both ruled out -- wrong pricing shape for bursty, few-minutes-per-job work, since both bill for allocated/idle time. **RunPod itself** ruled out too: its Serverless product is GPU-priced ($0.58-$10/hr equivalent) with no real CPU-only tier for a job that needs zero GPU, and running the controller on the same platform as the pods it manages/terminates is a real coupling risk (an outage could kill the one thing responsible for cleaning up a billed pod). **Landed on Cloudflare Containers** (reached GA earlier this year, checked live) -- same vendor already used for R2/CDN, $5/mo Workers Paid plan flat, billed per-10ms-of-*active*-use (not idle/provisioned), $0 when no job is running -- the right pricing shape for this workload, verified against Cloudflare's own pricing page rather than assumed. GCP Cloud Run Jobs / AWS Fargate flagged as the equivalent pattern on other clouds, not needed here since Cloudflare already covers it. Not built -- this was scoping/research only.

**Then the real build of the day: the cloud->agent command channel `ADR-071`/`ADR-073` had both flagged as missing, actually built (`DECISIONS.md` ADR-077).** Operator: "the desktop client only allows to add/remove cameras/sample clip, everything else (calibrate, recording, etc) should be on the console" -- a partial, deliberate reversal of `ADR-071`'s "local agent keeps... recording... calibration, can't move" list, worth noting precisely why: `ADR-071`'s calibration reasoning ("needs a live/local frame to click points on") was already stale by the time `PIC-75` shipped the next day with a snapshot-first flow -- only the snapshot *grab* is LAN-bound, not the point-clicking UI. Recording is a genuine split either way: the ffmpeg capture itself can never leave the venue machine, but the start/stop *trigger* has no such constraint.

Built the recording half (calibration's two-round-trip command flow is designed, not built -- see ADR-077 for the full design). New `agent_commands` table (RLS: venue owners get select+insert through the same agents->venues chain every other table uses; agent side always via the admin client). Three new console routes: `POST /api/commands` (venue-owner session, creates a command), `GET /api/agents/commands` (bearer token, agent's own pending rows), `POST /api/agents/commands/[id]` (bearer token, reports done/error). No new connection or timer anywhere -- `desktop/electron/cloud.js`'s existing 30s heartbeat loop also polls for commands on the same tick and executes them by calling the exact same `capture.js` `startRecording`/`stopRecording` functions the desktop app's own button already calls -- only the trigger moved, not the action, consistent with `ADR-071`'s explicit "polling is fine, nothing here is latency-sensitive" call. Cameras page's detail sheet gets a Start/Stop button (disabled for sample-clip cameras), which just posts a command and waits for `is_recording` to flip on the camera's own next heartbeat sync -- no separate faster poll invented just for this.

Verified: `python3 -m pytest -q` (132 passed, untouched by this), both Next.js apps' `tsc --noEmit`/`next build` clean, desktop renderer build clean.

**Scoped down same day, operator's call: calibration stays on the desktop app, not migrated -- the "everything else on the console" framing only ever meant recording.** `DECISIONS.md` ADR-077 updated to say this is decided, not deferred -- the two-round-trip calibration command design documented there is scoped out permanently, not a TODO.

**Found and fixed a real id-mismatch bug (`camera not found`) on first real click.** The Start/Stop button was sending `camera.id` (this row's own Postgres primary key) instead of `camera.camera_id` (the desktop agent's own id, what `/api/commands` actually looks cameras up by) -- neither `page.tsx` nor `cameras-client.tsx` even selected `camera_id` from Supabase, so it wasn't available to send correctly until fixed.

**Then verified against a REAL camera, live, end to end -- the first real proof of ADR-077.** Clicked Start on Court 1 (a real Synology RTSP camera, not a sample clip) from the console. Confirmed on disk: a real `ffmpeg` process pulling `rtsp://...@192.168.1.121:554/1` started ~28s after the command was created, writing real segments to `Court_1/2026-09-04T19-11-18-289Z/`. **Operator feedback from that same test: the buttons took a confusingly long time to reflect a new state.** Root-caused to two separate things, both fixed: (1) a real bug -- `cloud.js`'s heartbeat tick ran `sendHeartbeat()` *before* `processCommands()`, so a command's effect (e.g. `is_recording` flipping) was reported stale by a full extra ~30s cycle; reordered. (2) a pure UI gap -- the button's "pending" state cleared the instant the POST that queues the command resolved (well under a second), so it flipped back to looking idle long before anything real happened; now tracks a separate `awaiting` state that shows "Starting…"/"Stopping…" until `is_recording` actually matches, with a 60s timeout that surfaces an error instead of spinning forever.
