**Found and fixed a real double-tap bug, root-caused rather than patched blind.** Operator: "i have to click twice for the panel to show." The video was cached as a *promise* (`blobPromiseRef`), and a tap landing while that promise was still pending meant `navigator.share()` got called only after a real network wait -- long enough for Safari to have already expired the tap's user-activation window, so `share()` failed silently (caught, no visible error); the fetch itself running in the background read as "downloading." A second tap, after the blob had already resolved, worked because the `await` on an already-resolved promise costs only a microtask, staying inside the activation window. Fix: keep the fetched video as a plain `Blob` in state (not a promise), and don't let the Instagram/TikTok/Download tiles be tapped at all until that blob actually exists -- the spinner now shows proactively from page load, not just mid-share, so a tap only ever fires once `navigator.share()` can run with nothing awaited first.

**Three smaller fixes same pass, all operator-requested from live testing.** Added Threads as a fifth "Repost it" tile -- unlike Instagram/TikTok it has a real documented web share intent (`threads.net/intent/post?text=`), so it's a plain link tile like Facebook/X, not another `navigator.share()` case. Download button switched from a plain `<a href download>` to routing through the same `navigator.share()` path as the app tiles, so it opens the OS action panel too instead of silently saving -- consistent behavior across all four buttons. Naming scheme implemented: `<camera_label>_<venue_name>_<date>.mp4`, sanitized to safe filename characters, used for both the share-sheet attachment and the Download link; `page.tsx` now selects `camera_label`/`created_at` to build it.

**Speed investigation, done with real measurements rather than assumed fixes.** Timed a direct fetch of the real reel from R2's origin: TTFB ~318ms, ~1.06s total for 8.35MB (~7.9MB/s from this dev machine). Landed three real speedups: a server-rendered `<link rel="preload" as="fetch">`/`<link rel="preconnect">` in `page.tsx` (starts the download before client JS even loads, not just before its `useEffect` runs), `priority: 'high'` on the client fetch, and `preload="metadata"` on the preview `<video>` (stops it competing for bandwidth with the share-blob fetch). Calculated, not guessed, how much a CDN edge cache would help beyond that: the ~285ms TTFB origin round-trip a warm cache removes is small next to real mobile transfer time for an 8MB file (bandwidth-bound, not latency-bound) -- worked out to roughly 2-8% faster on typical cellular, up to ~20%+ only on fast wifi, and 0% on the venue-goer's own first (cold-cache) load of their freshly-produced reel, which is the actual scenario being tested. Flagged file-size reduction (a lower-bitrate share-specific proxy) as the higher-leverage lever if speed still isn't enough, not pursued today.

**Talked through the architecture question directly, not just the speed number: does a presigned URL even make sense here?** Concluded no -- the share page's real security boundary is already "know the reelId" (the public RLS policy), so a presigned URL's expiry/signing was protecting something the page doesn't need protected, while its unique-per-request signature defeated the exact caching this page's resharing use case wants. Implemented as `ADR-075`: `run_cloud_job.py` now mints the reel's UUID before upload and keys the R2 object `reels/<id>.mp4` with it (that id is now the entire access boundary, so it has to be as unguessable as the reelId already gating the page -- the old job/session-based key wasn't), threaded through `webapp/pipeline.py` -> `run_desktop_job.py` -> the console's `/api/agents/reels` route (accepts an optional client-supplied `id`, used as the row's own primary key). `cdn.picvisionai.com` set up as a Cloudflare custom domain on the `test-ingest-runpod` bucket with a cache rule; both `lib/r2.ts` copies (`reel-page`, console) replaced `presignedReelUrl()` with a plain unsigned `reelVideoUrl()`. Verified end to end: `cf-cache-status` MISS->HIT confirmed on repeat fetch, CORS carried over to the custom domain with no extra config, both the public share page and the console's video-redirect route serve real reels through it.
