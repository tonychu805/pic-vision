## LINE Login found broken for any returning player — still unresolved (ADR-148)

While testing the new `/account` page on a real phone, LINE Login kept failing with "sign-in did not go through" — but only sometimes, which made it worth actually chasing down rather than shrugging off as flaky Wi-Fi. Several wrong guesses ruled out one at a time using real Supabase logs, not assumptions: not a double-tap (added a guard, still failed clean), not LINE's in-app browser (failed the same in plain Safari), not a general login-mechanism problem (Google, same code path, works every time). The real pattern: Supabase's own logs show a *successful* LINE login completing a whole sequence (callback → login event → token exchange); a *failing* one stops halfway — Supabase received and processed LINE's response, updated the player's record, and then silently never finished creating the actual login session. Proved it decisively by deleting the test account's LINE link and logging in fresh — instant success, because a first-ever link always works; it's only the second and every later login that breaks.

Web search turned up a matching, known bug pattern in Supabase's own issue tracker (a custom login provider returning a different identity shape for someone already linked breaks their matching logic) — but no fix on our side to go with it. The operator then found what looked like the trigger — LINE Developers Console's "2FA requirement" setting on the login channel itself (not each player's own account) — and turning it off made one repeat-login test succeed.

**That "fix" was wrong and got retracted the same day.** It was written up as resolved on that one test, without a clean re-test. About an hour later, the exact same failure recurred three times in a row on the same account with the setting still off. Real lesson, not just about this bug: one ambiguous "seems to work" is not confirmation, especially for something that already looked intermittent — always re-test cleanly, more than once, before calling something fixed. Status is back to: real, reproducible, root cause still inside Supabase's own login service, no fix found yet on our side. Google and email remain unaffected and reliable.

## Check-in page redesigned: independent end times per court, plus an early-end button

The operator flagged a real design gap: every court shared one end-time picker, when different courts could reasonably end at different times, and there was no way to fix a check-in after the fact. Traced where "let a player change their end time" would actually have to reach: the venue machine caches the end time locally the moment recording starts, and never looks back at the database — so editing the database alone would make the console *lie* to the venue about when a camera will actually stop, worse than not offering the feature at all. Properly supporting an arbitrary time change means teaching the venue machine to listen for an update, which means a new desktop release — real scope, not decided today.

What the operator actually needed, though, was narrower: stop a *falsely over-long* booking from blocking the next group at an unattended venue. That doesn't need the venue machine to learn anything new — it already knows how to act on a stop command immediately (the same one the console's own manual stop button uses). Revived a "結束" (end early) button that was built and then removed just yesterday for a different reason, without realizing it also would have closed this exact gap. Sends a real stop command and marks the booking ended at the exact moment pressed (not rounded to the nearest hour — rounding up would recreate the very problem this fixes). Only the player who checked themselves in sees the button, not someone who joined. Verified directly against production: ending a session really frees the camera for the very next check-in request, a stranger can't end someone else's session.

Also built the other half the same session: each court now gets its own end-time picker instead of one shared for the whole page — picking 3pm for one court no longer touches a different court booked to 4pm.

**Not done yet:** the bigger "change to any already-picked time" feature (needs the venue machine changed, a new desktop release, not started); real-device confirmation of both the new "結束" button and the per-court pickers — the operator was about to test on their phone when the session ended for the day.

## Check-in owners can now extend (or shorten) their end time, not just end early

Verified thoroughly against production before touching the frontend: a real extension (successfully moved an active session's end time forward an hour, confirmed both the database row and a real queued command), and three ways it should fail all correctly rejected — picking a time in the past, picking a time beyond the venue's own duration cap, and a non-owner trying to change someone else's session. Desktop side verified via the full test suite (306/306, includes lint) before any of this touched real hardware.

**The one thing this can't do yet: change a real camera's behavior.** The RPC and the desktop handler are both built and verified, but nothing pushes a new desktop build to any venue machine automatically — until that release goes out, a player using this on the live site will see the database and console agree on a new end time, while the actual camera keeps recording (or stops) on the old schedule. ## A second, separate login-persistence gap found and fixed (not the LINE bug)

Answering an unrelated "does login keep you logged in" question turned up a real gap in `pic-vision-reel`: the player-login system had no `proxy.ts` (this Next.js version's renamed `middleware.ts`) to refresh and re-persist a session on the server. Without it, a returning player's expired access token could be refreshed in memory just well enough to serve that one page load, but the new cookie could never be written back from a Server Component render — leaving the browser holding an already-rotated refresh token, a plausible source of a later silent logout. Standard fix: added `proxy.ts`, scoped to the routes that actually read auth state, so public reel-share viewers don't pay for an extra auth round trip.

**This is a different bug from the still-unresolved LINE Login issue above.** LINE fails earlier and harder — GoTrue never finishes minting a session at all on a repeat login, before any cookie or refresh logic is even reached. The new `proxy.ts` fixes an orthogonal risk on top of sessions that *do* get created (Google, email, and LINE's own first-ever login), and has no bearing on why LINE's repeat logins fail.

Caught one real thing while building it: this Next.js version (16) has renamed `middleware.ts` to `proxy.ts` (function name too) — a first pass using the old convention built and ran, but with a deprecation warning; the dev server's own build error on the renamed-but-not-fully-updated file is what caught it before it shipped. Verified: `tsc`, `next build` (warning gone), `npm test` (14/14), and a live request against the running dev server showing `proxy.ts` actually executing with no errors. Committed, not pushed.

## LINE login moved off Supabase's own auth onto Auth0

Rather than keep chasing GoTrue's unresolved repeat-login bug (above), the operator signed up for Auth0 and asked to move LINE login there specifically — Auth0 has a real, officially-maintained LINE social connection, unlike the custom OIDC config GoTrue was using. Google and email stay exactly as they are; only LINE moves.

The one real technical landmine, found before writing any code: Supabase's `auth.uid()` hard-casts the JWT's `sub` claim to a `uuid`, and Auth0's `sub` for any social login is always `<connection>|<id>` (e.g. `line|1234567`) — never a uuid. Wiring up Auth0 the standard way would have made `auth.uid()` throw a real error, not silently fail, on every request from every Auth0-authenticated player. Confirmed directly against the live production function definition before building anything, rather than assuming Supabase's own docs example would just work here.

Fixed with a new `current_player_id()` function that replaces `auth.uid()` everywhere in the player system: returns the same value as before for a Google/email session, and for a LINE session looks the player up by a new `auth0_sub` mapping column instead. Every player-facing RLS policy and RPC (`player_check_in`, the consent functions, all of it) got rewritten to use it. `players.id` lost its foreign key to `auth.users`, since a LINE player authenticated through Auth0 never gets a row there.

Verified against production: the Google/email path is provably unchanged (a player still reads and updates only their own row, a stranger sees nothing), and the new LINE path correctly returns "not signed in" before a player exists (not an error) and correctly creates/resolves/round-trips consent once one does, using a simulated LINE identity. Four of the ten rewritten functions (the ones that queue real commands to actual camera hardware) weren't re-run live this round — same proven substitution pattern as the ones that were, but not itself proven end-to-end yet.

Built the actual login path once the database side was solid: a new route exchanges Auth0's authorization code server-side (the client secret never reaches the browser, same handling as the existing Google callback), the LINE button now redirects straight to Auth0 instead of Supabase, and every place that used to ask Supabase "who's signed in" now asks the same new database function instead — which works for both providers, so none of those call sites need to know which one is actually active. Sign-out is now one shared action that clears whichever of the two sessions exists. `proxy.ts` (built this same day, see above) got extended to keep a LINE session's tokens fresh too, for the identical reason it already does that for Google/email.

Walked the operator through the real Auth0 dashboard setup live — hit two real, well-documented Auth0 quirks along the way (their docs still say "Flows", the dashboard now calls it "Triggers"; a stale-session bug threw a false "no permissions" error on saving the custom Action) — both resolved by checking Auth0's own support material rather than guessing.

**Real-device test found two more real bugs, both fixed, LINE login now confirmed working — including the exact repeat-login case that was broken before.** First: LINE itself rejected the callback with "Invalid redirect_uri" — Auth0's own callback URL wasn't yet registered in the LINE Developers Console (an easy add once identified). Second, trickier one: after LINE's own consent screen succeeded, Auth0 showed "we couldn't find your session." Auth0's real-time logs showed the failed request had no connection or client info at all — not a lost cookie, a request Auth0 never recognized as belonging to any login attempt. Traced to LINE's own iOS behavior: tapping the LINE login link hands off to the native LINE app regardless of which browser started it (confirmed — forcing Safari didn't stop it), and the LINE app's own browser then finishes the round-trip back to Auth0 from a completely different cookie jar than wherever the flow began, so Auth0's own "remember who's logging in" cookie is never there when it needs it.

Fixed with LINE's own documented parameter for exactly this failure mode (`disable_auto_login=true`), which keeps the whole login inside one browser the whole time. Since Auth0 builds LINE's login URL internally rather than us calling LINE directly, applying this required Auth0's Management API rather than a settings toggle — a small, single-purpose Machine-to-Machine application, one scope short on the first attempt (`update:connections_options` is separate from the general `update:connections`), then a successful `PATCH`. Talked through the real trade-off with the operator first: this permanently drops LINE's native-app handoff, the more familiar flow for LINE-heavy users — but it was failing *every* time here, not occasionally, and LINE's own recommended "try native first, fall back on failure" pattern would just mean every login visibly flashes the LINE app open before bouncing back anyway.

**Confirmed working end to end**, not just on LINE's own screen: a real `players` row now exists in production with `auth0_sub` set to the LINE identity, and the operator logged out and back in successfully — the specific thing that was 100% broken under the old GoTrue setup. One cleanup item left: the one-time Management Script application still holds privileged Auth0 API access and should be deleted now that its job is done.

## Architectural/functional gap review, and the biggest one fixed same session

Asked directly what's lacking for the app's actual purpose. Named several real gaps (no personal reel history, no account deletion despite the privacy policy promising it, no way to un-join a mis-joined session, the still-pending desktop release for camera-side extend-time) — but the one picked to fix now: **check-in had zero feedback loop back from the actual camera.** A player checking in only ever saw their own click succeed; whether the venue machine actually started recording was invisible, silently trusted.

Turned out to be straightforward to close: `desktop/electron/cloud.js` already reports real success or failure back onto the same `agent_commands` row (pushed over realtime when the machine's online, not slow polling) — this just had never been read back out to the player. `get_check_in_options()` now surfaces it, and the check-in page shows "Confirming recording…" (polling every 2.5s, giving up gracefully after ~60s with a "this is taking a while" message rather than spinning forever), then either "Recording confirmed" or the real failure reason straight from the camera. Verified against production for all three states (pending/done/error), including passing a real error message all the way through.
