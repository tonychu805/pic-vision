# 2026-09-09

**Settled how the system should handle several courts at once, and wrote it down as a decision rather than leaving it as research.** `DECISIONS.md` ADR-093. Nothing built today — this is direction.

## The question

With the Diagnostics tab finished (see yesterday), the natural next question was what happens when a venue runs four courts at the same time. Working through it honestly:

- **Recording four courts is fine.** Each camera's video is copied straight to disk with no conversion, so it costs almost nothing. Four courts for two hours is about 10 GB, against 157 GB free.
- **Uploading four at once already works** — there's no limit in the code preventing it, and each court uploads its own chunks one after another while the four courts overlap. But it doesn't make anything faster: the building's line is the ceiling, and four streams share it.
- **The processing queue is where it falls over.** Today one program on the operator's own machine takes one job at a time, start to finish. Four courts means the fourth one's highlights arrive around five hours after play ends.

The operator's response was the right one: each camera should get its own cloud worker.

## Why that isn't already true, and what it takes

That target was already half-decided — research in early September picked a Cloudflare product to host the cloud-side coordination. What that research didn't ask is *why* the coordination needs a machine with a command line at all. Two reasons, both removable:

1. **The video is converted using the operator's own graphics card before the cloud ever sees it.** Cloud coordination machines have no graphics card, so as long as that step stays where it is, the whole process is chained to one desk. It also sends the video on an absurd journey — from the venue up to storage, down to the operator's machine, back up to storage, then out to the rented machine. That's a full session travelling *up* the operator's own connection twice.
2. **The rented machine is driven over a remote shell.** Create it, log in, install everything from scratch, copy scripts across, run them, read progress off the terminal output. Cloud coordination services can't do that; a container can, which is most of why containers looked like the answer.

The fix is to make the rented machine self-sufficient: do the conversion there (it has a graphics card and already runs video tools for cutting the reels), ship it a prepared image instead of installing from scratch every single time, and have it report progress and completion back to the console the same way a venue's own app already does. Once nothing needs a command line, coordination is just a few web requests — and one per camera becomes trivial.

Checked against Cloudflare's current documentation rather than assumed: for a job that spends forty minutes *waiting*, their Workflows product is a better fit than containers — a waiting instance doesn't count against concurrency limits at all, whereas containers cap at 20 by default and go to sleep after ten minutes idle. Either way the coordinator must be able to resume from where it left off, because the platform can stop an instance whenever it needs the machine back.

## What it's worth

Four courts stop queueing. Four rented machines run at once for the same total rental time, so **the same cost** — the difference is four reels within the hour instead of the last one arriving at 2am. And the operator's workstation leaves the production path entirely, which is what the thin-agent split was supposed to achieve in the first place.

**Available today, no code:** start two or three copies of the existing job runner. The queue was already built to hand work out safely to several workers, so this cuts the wait proportionally while the real change is built.

## Flagged, not solved

- **Who shuts down an abandoned rented machine?** Today the runner does it on its way out. A self-sufficient machine needs its own deadline plus an outside sweep, or a crash leaves a GPU quietly billing.
- **Four machines at once has never been tried**, and there are still no spend controls on any of it.
- **Credentials.** The rented machine currently gets storage keys handed to it on a command line; a self-driving one needs them in its own environment, and a token scoped to its single job rather than the operator's blanket one.

## Later the same day: a real bug, reported from the packaged Mac app

**Signed in on the Mac as one account, and the app said it was connected as a venue belonging to a different account.** Confirmed against the live database rather than inferred: that machine was genuinely attached to the other venue.

**What causes it.** The app keeps two separate things: who is signed in, and which venue this machine is registered to (with the credential it uses to report in). They were never tied together. Signing out cleared only the first. Signing in only registered the machine if it wasn't registered at all. Each rule made sense on its own; together they meant **the first account to set a machine up owned it forever** — sign out, sign in as anyone else, and the machine kept reporting as the original venue.

The wrong name on screen was the harmless part. The credential in that record is what the machine uses for everything, so its cameras and every reel they produce would have been filed under the other venue, invisible to the person actually using it. Nothing had been misfiled yet — that machine had no cameras, jobs or reels attached when checked.

**The fix, and a correction to it.** The machine now records which account it was set up as, and notices when that changes. My first version quietly re-registered it to whoever was signed in. The operator rejected that immediately and was right to: **moving a machine isn't a correction, it's a transfer.** Its cameras go with it, along with everything they record, and the venue that had it loses it without being told.

So it asks instead. A dialog blocks the app and states the consequence plainly, with two ways out: move the machine to the venue you're signed in as, or sign out and sign back in as the venue that actually owns it. There's deliberately no "remind me later" — a machine in this state is reporting to the wrong venue every thirty seconds.

One case is still handled silently, on purpose: a machine set up by an older build has no account recorded, so if its venue still matches the person signing in, nothing changed hands and it's simply stamped. Upgrading shouldn't interrogate everyone.

**Verified** by six tests covering every branch, and by driving the dialog in the real app: it renders, it blocks, and its failure path was exercised live. That last check caught something small but real — the error shown to the user was leaking internal wiring ("Error invoking remote method...") instead of the actual message. Fixed here; the same class of leak is filed elsewhere in the app.

**Also found, filed rather than fixed:** anyone signed in can claim any machine whose ID they know, and the app prints that ID on screen. That's what makes legitimately moving a machine possible, and it's also a way to take one — along with its cameras. Refusing it outright would break the flow this fix depends on, so the trade is written down for a decision rather than changed in passing.
