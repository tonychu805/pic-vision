**Where things stood.** The latest installer, 1.7.3 (2026-10-06), is missing ten desktop commits that are already on `main`: dual-stream recording, ONVIF multi-profile support, high-res clip trim and re-upload, scanning every local subnet, end-of-day footage expiry, and several fixes to those. Nobody has a build with them. There was also no Windows build at all.

**What changed (branch `feature/windows-desktop-build`, not yet merged).**

- One real Windows bug fixed: stopping a recording used a signal that Windows turns into a hard kill, which is the corruption case from ADR-031. Windows now asks ffmpeg to finish its file by writing `q` to it.
- Install instructions for Windows are in `desktop/README.md`.

**Not verified yet.** Nothing has been run on a Windows machine. The Linux test suite passes (336 tests); the Windows CI job is the first real Windows run, and a camera test on a real Windows PC is still needed before handing it to a venue.

**Next.** Merge this, cut 1.8.0 from the merged commit (picks up the ten commits above), and test the installer on a Windows PC with a real camera.

## Seeing which venues are behind (PIC-222, step 1 of remote updates)

**Why.** With unsigned builds every update is manual, and the console could not tell which venue runs which app version — its heartbeat only carried camera firmware.

**What.** The desktop heartbeat now also reports the app's own version and platform; the console shows both in Overview > Connected agents and marks agents behind the newest published release. An older app that reports nothing shows "Not reported", and an unreachable GitHub shows no marker — never "up to date".

**Status.** Built and tested, not shipped: console change is on a branch awaiting review on staging (and the migration must be applied before it reaches production); the desktop half rides the next desktop release. Remote/automatic update itself is parked as PIC-223 — Windows could do it unsigned, macOS cannot until signing (PIC-117).

## Detection mechanics: concept plan agreed, tickets filed

**What was decided.** After the desktop catch-up we revisited which *detection mechanics* could unlock more highlight types. Concept: three layers — per-rally **signals** (plain facts, "unknown" allowed), small readable **moment rules** over them, and a **selection** step that mixes types and normalises across cameras. Every new signal must beat the existing ranking against the human grades before it is kept (the same gate PIC-196 already sets).

**Order, and where each lives in Linear.**
1. **Ball-only tempo features** (pace profile, kitchen score, escalation, finish speed) — added to PIC-207 under PIC-196.
2. **Person boxes + anonymous tracks, not pose** — PIC-197 (probe), PIC-198 (tracks). Pose stays separate (PIC-147), only for falls / ball-hits-head.
3. **Audio feasibility** — new PIC-225.
4. **Cross-camera normalisation of the hard-shot signal** — new PIC-224; a prerequisite for any second venue.

**Facts found while doing it.**
- The desktop recorder uses `-c copy` with no `-an`, so any audio a camera sends is kept in the segments.
- The pilot source footage **does carry audio** (iPhone `.MOV`: AAC stereo plus a 4-channel track; the brickwall source: AAC stereo, ~21.6 min). The PRD's audio usability gate (Phase 2.5, never built) can therefore be run offline with no new capture.
- **Not known:** whether the real venue cameras (Court 1, Court 2) or the uploaded sub-stream carry audio. No recorded venue segment exists on this machine.
- Audio captures speech, so it waits on the consent decisions (PIC-60/61/62, PIC-190) before anything is stored or processed in the pipeline.

**A caution kept on the record.** "Boxes should hold up better than pose at the far court" is a **hypothesis**. The August yolov8 pose check found only 2 of 4 players (PIC-197). PIC-197's gate stands: agree the far-team coverage threshold *before* looking at numbers, and stop player work if it isn't met — then fall back to ball-only features.

**Demand check: dropped (operator, 2026-10-12).** There is no way to measure what players or venues want to share until the operator has actually spoken to venue owners, so it cannot be quantified from here and is not a step. The order above therefore rests on feasibility and the decisions already on file (2026-10-11), **not** on demand. Revisit the category order after those conversations; until then nothing in this plan claims to know what players most want.

**Not built.** No code was written.
