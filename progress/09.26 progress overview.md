# 09.26 progress overview

## Frame rate: 30 is now a target, not a hard requirement (not yet released)

At PGC on 09.25, a camera set to 30fps read 28 at 20:00, and the desktop refused to start that hour's scheduled recording, so the hour was lost. Changed at the operator's request (ADR-131):
- **29fps or above:** records as before.
- **25–28fps:** **records anyway**, with a warning in the desktop Log and the console's camera panel saying to set the camera back to 30.
- **Below 25fps:** refused, as before.

Only 30fps and 15fps (half the rallies) have ever been measured. How much 25–28 costs is unknown.

Tested: desktop 252, Python 245, console typecheck.

**Status:** cloud processing is live (pod code e2bd390 uploaded). **Desktop 1.6.10 is released** (DMG on GitHub) but only takes effect once installed on the venue Mac. **Console change is committed but not pushed**, so its Record/Calibrate buttons stay greyed out for a 25–28fps camera until the next console deploy. Scheduled recordings aren't affected.

## A booking now takes over a camera that was started by hand (live)

At 14:00 today both PGC courts' bookings failed to start ("Already recording this camera"), because they had been started by hand at 13:38. The hand-started recording kept going, the booking got nothing, and at the booking's end its stop would have been skipped, leaving the recording running until someone noticed. Someone stopped both by hand at 14:02.

Now every booking's start is preceded by a stop for that camera. A recording started by hand ends when the booking begins, keeping its own share link, and the booking records under its own. The earlier footage isn't merged into the booking's link, because it may show other players. Back-to-back bookings are unchanged: the finished booking's own stop still runs first, so it's still sent automatically.

A database change only, no app release. Tested in a rolled-back transaction on production (back-to-back, a lone booking, a later booking left alone) before applying.
