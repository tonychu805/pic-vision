## First end-to-end pipeline run on brand-new footage, and a real "is this broadcast footage" scare that turned out fine

Operator handed over a genuinely new video — `Brick-Wall--Mid-Atlantic.mp4` — and asked for the full pipeline run start to finish, ending in a highlight reel. Different from yesterday's `brickwall-SEMI` work: no hand labels exist for this one, so this tested the *operational* pipeline (does it run cleanly, does the output look right), not detection accuracy.

**Real scare, resolved carefully rather than assumed away.** The file's provenance (a matching download in `~/Downloads` named `YTDown.com_YouTube_Brick-Wall-Pickleball-Mid-Atlantic...`) pointed straight at YouTube — and this project already archived two YouTube broadcast videos as unusable (19–25 hard scene cuts per 3 minutes, `progress/08.18 progress overview.md`). `check_drift.py` alone wasn't trusted as sufficient to clear it (its averaging could plausibly mask many cuts that happen to cancel out) — pulled frames at four points spread across the 21-minute video and confirmed identical framing throughout, including the same tripod-mounted phone visible in every shot. Genuinely a single fixed-camera recording someone uploaded to YouTube, not an edited broadcast. Worth remembering: **file origin (YouTube, an unusual filename) is a legitimate reason to double-check even when the automated drift tool says stable** — it wasn't built with hard-cut detection specifically in mind.

**Pipeline ran clean end to end:** decode integrity checks (before and after), 25→30fps CFR conversion, operator-clicked calibration (0.283ft RMSE — calibration stayed a human-in-the-loop step, per `STRATEGY.md`'s explicit "never blind auto" stance), local-GPU TrackNet inference (~24 min), detection (56 candidates), ranking (`src/select.py`'s locked ADR-063 formula), and a 12-clip, ~4:58 reel — both chronological and rank-ordered versions.

**One real bug, caught by checking rather than assuming:** generalizing `scripts/rank_and_reel.py` for reuse (previously had `brickwall-SEMI` hardcoded) silently dropped the call that builds the chronological `highlight.mp4` — only the ranked version was actually written. Found by verifying both output files exist before calling it done, not by trusting the script ran correctly. Fixed and reverified.

**Reviewed by frame sample, not yet full playback.** Pulled one mid-clip frame per clip (all 12) plus both boundaries of the top-ranked clip — every clip shows genuine active rally play, boundaries land on natural pre-serve/post-point moments. Explicitly **not** a final verdict — this project's own rule is that stills-based verdicts have been wrong before (`IMG_7744` FP review). Full playback review, especially of the shortest/lowest-ranked clip that made the cut (#12, 7.1s), is the next thing to actually do, not done yet.

**Session ended here — operator going offline.** Nothing scored, nothing labeled for this video yet. Uncommitted: `calib/brickwall_mid_atlantic_calib.json` (should be committed per this project's convention — calibrations are expensive to redo) and the `rank_and_reel.py` bugfix. ## Update — a real coordinate bug, found by building a diagnostic for an unrelated reason

Asked to visualize every signal the pipeline uses "on a video" — built an actual annotated clip (court-wedge boundary, net line, tracked ball, crossing flashes, spike rings burned into the footage), not just a static-frame chart. Watching it, the operator caught something real: the tracked marker sat next to the ball, not on it.

**Root cause, confirmed with exact-match math before trusting the fix:** `scripts/pod_infer.py` scales TrackNet's predictions back to source pixels using one height-derived ratio for both x and y, but the frame preprocessing squashes to a fixed 512×288 without preserving aspect ratio. Only correct on exactly-16:9 video — every prior video in this project happens to be 16:9; `brickwall_mid_atlantic` (1280×640, 2:1) is the first that isn't, which is exactly why this had never surfaced before. Fixed (separate x/y ratios), re-ran inference, and *measured* the actual shift rather than trusting the math alone: 142px max, correlating 1.000 with the old x-position — a clean, fully-confirmed linear scale error.

**Re-ran detection and the reel on the corrected data, comparing candidate-for-candidate rather than just counts.** 51 of 56 candidates and 10 of 12 reel clips unchanged; the handful that differ all trace cleanly back to crossings near the court-wedge's x-boundary flipping in/out — one false candidate that only existed because of the bug disappeared, one real one split after losing two bug-only crossings. Both replacement reel clips frame-verified as genuine before accepting the swap. Full detail: `EXPERIMENTS.md` and `DECISIONS.md` ADR-064.

**Worth remembering:** this bug would have silently corrupted `court_wedge` gating on any future non-16:9 footage indefinitely — found through ordinary use of a diagnostic built for a different purpose, not a targeted audit. Net-crossing detection itself was never affected (y-only), so no prior video's results need re-checking.

## Update — the signal-overlay tool got saved for real this time, and watchable as a Claude Artifact

The diagnostic clip that caught the coordinate bug above was thrown together once and never kept — gone by the time this conversation started fresh. Rebuilt it as an actual reusable script, `scripts/visualize_signals.py` (still uncommitted), that burns the court gate, net line, tracked ball, velocity spikes, net crossings, and rally-segment membership into real footage on request, instead of a one-off inline job. Ran it on the same top-ranked `brickwall_mid_atlantic` clip and published it as a Claude Artifact ("Rally Signal Viewer") so it's directly watchable in a browser with a legend, not just a local file to hunt down.

**Also added the PIC-31 pre-serve stillness signal (`scripts/pose_stillness.py`) to the same viewer, clearly marked as experimental/not-shipped** — an ankle-speed meter plus the computed ratio at the clip's rally-start boundary. Came out to 0.60 on this boundary: a real dip, but milder than the original 7–17% sample. Doesn't change anything — it's one more data point behind the existing conclusion (stillness is a loose leading indicator, not a precise boundary marker, per PIC-53) — but worth having since it came from a third video almost for free.

**Clarified for the record:** a low stillness ratio is *not* a rule that defines a rally start. It's correlational (dips tend to precede real starts, 88% on the one video tested), doesn't localize the boundary precisely, and — critically — has never been validated against real dead time, since every dead-time example this project had turned out on playback review to be real plays (ADR-057). "Low ratio → rally start" is an overclaim the data doesn't support yet.
