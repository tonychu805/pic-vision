# 09.20 progress overview

## A crash that reported nothing, and what got built because of it

1.5.1 crashes when you click Retry on a recording — and unlike the day before, it says nothing at all. No dialog, no message: the window simply goes away.

**The bug itself is still unexplained.** That's the honest status. I read the whole retry path and ruled out the obvious candidates — the work that happens on Retry all sits inside a handler that turns failures into a message in the row rather than a crash, and both of the background tasks I changed yesterday have error handlers on them. Nothing in the app installs a handler that would suppress the error dialog you'd normally get. So the app is either crashing below the JavaScript level or being told to quit, and from the outside those look the same.

**What's fixed is the silence.** Two crashes in two days, and the only real difference between them was what they reported. The first one named a file and a line, and was found and fixed in minutes. The second reported nothing, and cost a round trip asking for more information that may not be reproducible on demand.

So the app now records every way it can go away — into the Log tab, into a plain text file next to it, and onto the terminal if it was started from one. More usefully, it tells apart five things that all look like "the window vanished":

- an error in the app's main process
- a background failure nobody caught — the one that can kill the app with no dialog at all
- the window's own process dying
- a helper process dying
- nothing crashing; something simply asked the app to quit

That last one earns its place. "It crashed" and "it was told to quit" are indistinguishable when all you see is a window disappearing, and they send you looking in completely different places.

**One thing it deliberately can't catch:** a crash in the deepest layer of the app, where no code of ours runs afterwards. macOS writes those to its own crash reports folder — so *nothing being recorded* becomes useful information rather than a dead end.

**Tested the way yesterday taught us to.** Yesterday's crash lived in a function no test had ever run, sitting next to nine passing tests of the piece beside it. So these tests actually run the new code and fire each kind of failure at it, rather than only checking the wording. One of them covers the reporter breaking during a crash — it runs while the app is already falling over, and something that throws in there turns one lost explanation into two. 151 tests.

**Where this leaves the release train.** 1.4.0 is still the last build with no known crash. 1.5.0 is withdrawn (crashed on launch). 1.5.1 launches fine but crashes on Retry. The instrumentation above only helps once it's in a build actually being run.

**Still the real priority, and still blocked behind this:** the cloud pipeline has never completed a run on real hardware. Five stages have never executed successfully, and the next attempt starts with a "Send to cloud" from this app.

## Found it: nothing was crashing at all

The Retry "crash" turned out not to be a crash. Two observations settled it, both from running the app from a terminal: when the window vanished the terminal **did not** come back to a prompt, and the only line it ever printed was the one logged hours later when the app was quit deliberately. So the app was alive the whole time. It just had no window.

**Three separate, individually correct decisions combined into this.** The window is deliberately transparent, so the app can draw its own rounded corners instead of the operating system painting a squared-off rectangle behind them. React, when an error escapes, removes the entire interface — that is its designed behaviour, and there was nothing in place to catch it. And on a Mac this app deliberately keeps running when its window closes, so the heartbeat to the cloud console doesn't stop.

Put together: any error anywhere in the interface removes everything being drawn, and a transparent window with nothing drawn on it is not a blank window — it is an invisible one. You see your desktop through it. The app is still there, still connected, still recording if it was recording. It simply cannot be seen.

**The instrumentation built this morning couldn't have caught it**, which is worth writing down on its own. That work covers the app's background half, and this happened in the interface half. Instrumentation pointed at the part you were already looking at proves nothing about the part you weren't.

**What's fixed.** The interface now catches its own errors and shows a readable screen — what broke, where, and a button to reload — instead of removing itself. That screen paints a solid background, which is the part that actually matters: on a transparent window, a crash screen without one would be exactly as invisible as the blank it replaces. Errors that a screen like that can't catch (a failure inside a click handler, or a background request nobody waited on) are now reported too. All of it lands in the same Log tab as everything else, tagged so that "the interface broke" and "the interface's process died" can't be mistaken for one another — they look identical from outside and send you looking in completely different places.

**What's still unknown: what actually goes wrong when you click Retry.** This doesn't fix that. It makes it visible. The next time it happens you'll get the error on screen instead of an empty desktop, and that's what we've been missing for two days.

**Tested by actually rendering it.** The crash screen is built and rendered in the test suite and checked for the things that matter — that it shows the error, and that it paints that background — plus the other half, that when nothing is wrong it renders the app and nothing else. A crash screen that swallowed the app would just be a new way to lose the interface. 160 tests.

**Same shape three days running.** Monday: logic no test ever ran. Tuesday: a process that could die without reporting. Today: an interface that could vanish without reporting. Every one of them was something that could fail silently, and every one was found by an operator rather than by us.

## The Retry crash, named at last — and it was mine

The error screen shipped this afternoon worked on its first real use. Instead of the app vanishing, it said:

> **cancelling is not defined**

That's a mistake I made two days ago, in the work that fixed Cancel. I added a piece of state to a file using a scripted edit that anchored on a line of text — and that text appears twice in the file. The declaration landed in the wrong component, several hundred lines above the code that uses it. The component that needed it referred to something that simply wasn't there.

It only showed up on Retry because the Cancel button is only drawn while a job is running. Nothing ever evaluated that name until a job started — and then, until this afternoon, the whole interface silently disappeared instead of saying so.

**The real problem is that this is the second one.** Three days, two releases, two crashes, both of them a reference to a variable that doesn't exist:

- Monday's build died on launch: a refactor deleted a value and left one use of it three lines below.
- Today's vanished on Retry: an edit put a declaration in the wrong place.

Neither is a subtle bug. Neither was catchable by anything we were running. The build step treats an unknown name as "some global that'll exist at runtime" and says nothing at all. The test suite only fails on code it actually runs, and neither line was run by any test. Both reached the operator.

**So a linter is now part of the test suite**, running before the tests, with essentially one rule: a name that doesn't exist is an error. Both of this week's crashes were re-introduced and checked against it — one produces four errors, the other two. Both releases would have been stopped before they were built.

It's deliberately minimal: one error, one warning, no formatting opinions, nothing that would produce a page of complaints about existing code. A gate that cries wolf gets ignored, and this one needs to be trusted.

**What I couldn't check here.** The fix is verified by scope analysis rather than by clicking the button, because this machine's app is sitting at a sign-in screen and getting to that page would mean signing in against the live system. For this particular kind of bug that's an honest answer rather than a dodge — "this name doesn't exist anywhere in scope" is exactly the question a linter answers completely, and running the app would confirm the same fact less directly.

## The Cloud page was answering a different question than the one being asked

"Connected" on the desktop's Cloud page never meant the machine was reporting. It meant a connection record existed on disk. Those come apart exactly when it matters most: after a venue's machine is revoked, the record is still there, so the page kept showing a green tick and the venue's name while every check-in was being rejected. The truth was in the Log tab, which nobody opens to answer a question the page appears to have already answered.

This was found on 2026-09-05 and has been sitting in the backlog since.

**Two things were wrong, and fixing either one alone would have left the bug in place.** The app already knew whether check-ins were succeeding — it just kept that to itself, and the page had no way to ask. And separately, the page read the answer once when it opened and never again, so even a correct answer would have gone stale while somebody was looking at it.

**The page now distinguishes three things that used to look like one.** Not checked in yet, checked in successfully, and was checking in but isn't any more. That last one says how long it has been, because "lost two minutes ago" and "has never once connected" send you to completely different places — a dropped network versus a wrong address or a revoked machine.

**A deliberate omission: the page still doesn't show *why*.** The reason a check-in failed stays in the Log tab, where it already goes. Handing that text to the page would mean printing whatever the server said, which is the thing two earlier tickets existed to stop.

**Tested the way this week keeps teaching.** The wording is a plain function with its own tests — but that alone is precisely what shipped two crashes in three days: a well-tested piece with nothing running the code around it. So the status line is also built and rendered in the test suite, and checked for what an operator would actually see, including that the word "Connected" is absent when check-ins are failing. 160 tests to 180.

Writing those tests turned up a genuine race in the tests themselves: connecting starts the check-in loop immediately, and stopping that loop doesn't recall a check-in already in flight. One landed in the middle of a test and overwrote a value it had just recorded. Worth knowing before writing the next test that drives this by hand.

**What isn't verified:** nobody has watched this happen on a running app with a genuinely revoked machine. Same reason as the rest of this week — the app on this machine sits at a sign-in screen, and getting to that page means signing in against the live system.

## Three security tickets: one fixed, two that turned out to be filed wrong

Picked up the three oldest open security items. One was a real fix. The other two were both filed with a wrong assumption at the centre, and finding that out was the actual work.

**The one that was fixed: a secret was being shouted where anyone could hear it.** The cloud job used to hand the storage password to the GPU machine by writing it into the command it ran. Anything else running on that machine could see the full command, password included, just by listing running processes — six times per job. It's now written to a locked-down file and read from there; a file's contents don't show up in a process listing.

Two things worth noting. The ticket said this exposed the password on the rented GPU machine; it also exposed it on **this** workstation, for the same reason, which nobody had spotted. And the ticket's recommendation was to delete the file entirely as dead code — but it isn't dead. The local dashboard still calls it, in two places. Deleting it would have broken that. So the leak is fixed where it is, and whether to retire that dashboard route is now a separate question rather than a silent side effect.

**The one that can't be done as written: the storage cleanup rule.** Nothing currently reclaims the footage of a job that fails, so the plan was a rule that deletes old uploads automatically. Checking the actual storage rather than the plan: **the rule as described would have matched nothing at all** — it was written against a folder name that isn't how the files are actually named. It would have been switched on, appeared to work, and quietly reclaimed nothing.

The real numbers from that check: two dead uploads are sitting there now, 543MB, just under half the bucket — exactly the leak the ticket describes, so the problem is real even though the fix isn't. The ticket also warns that a careless version of this rule would delete the shared pipeline files; it misses that it would also delete the 135MB detection model sitting in the same place. Three ways forward written up on the ticket. **Nothing was switched on** — this deletes real venue footage, and the retention period is a judgement call about how long a venue might wait for their reel.

**The one that shouldn't be done yet: the GPU machines hold master keys.** Every rented GPU machine is handed full-privilege credentials — enough to reach every venue's footage and to create more machines — rather than anything limited to the one job it's running. Still true, re-checked today.

Deliberately not fixed now, and the reason is about sequencing rather than difficulty: the pipeline has still never completed a single run end to end, and this fix rewrites the credential path of that same pipeline. Doing it first means the next attempt is debugging two unknowns at once. The design is written up on the ticket so it's ready to go once a run has actually succeeded — and it turns out fixing them in the right order makes two of the three problems disappear rather than needing three separate fixes.

## The cloud pipeline finished a real run, for the first time

The thing that's been blocked for a week actually worked. A recording went from the desktop app to the cloud and came back as finished highlights, with every stage that had never once succeeded succeeding: converting the footage, detecting the ball, cutting the reels, uploading them, and reporting back. Ten and a half minutes, start to finish.

**What came out:** 20 candidate rallies, a 3-minute highlight reel, a 30-second quick-hits reel, and the ten best rallies as individual clips. The share link works.

**Checked properly, not taken on trust.** The runner prints "finished" whether a job succeeded or failed — that's a lesson from a run last night — so none of the above is from that line. The job's own record says done with no error; all twelve videos are really in storage at sensible sizes; the full reel was inspected directly from the delivery URL and is genuine 1080p video of the right length; the share page loads; and — the one that costs money if it's wrong — **no GPU machines were left running**.

One more thing worth confirming: the failed job from last night deleted nothing, and this successful one cleaned up after itself. That's exactly the rule put in place yesterday, working in both directions on real data rather than only in tests.

**And the calibration bug from earlier today is confirmed fixed** — this run's calibration went through in three seconds.

## But the run couldn't tell us what it cost, so that's now fixed too

Ten and a half minutes — but how much of that was converting, how much was detection, how much was cutting? **Nothing recorded it.** The job tracks which stage it's on, but only the current one, so each stage's start time was erased by the next. The logs only note when the job started and stopped.

So the run proved the pipeline works and left the most important question exactly where it was: what does a session actually cost to process? Every decision about scaling to more venues rests on that number.

**That's the second time today a missing number mattered.** Earlier I built a whole cost argument on a detection-speed figure from 26 August, and the operator pointed out it was long out of date — better numbers were already sitting in the project's own records, roughly three times faster. A pipeline that doesn't measure itself leaves every plan resting on whatever figure somebody last wrote down.

**So every job now records when each of its stages began**, and durations come out of the gaps. A few deliberate details: the finishing moment is recorded too, otherwise the last stage would never have an end; repeated reports of the same stage don't count as new ones, or a nine-minute detection step would log a hundred identical entries; and the history is capped so a misbehaving reporter can't bloat the record.

The database change went in *before* the code, on purpose — the other order would have broken every job update in production for the minute between the two.

**Not verified yet:** no job has run since, so nothing has actually been written to it. The next run confirms it — and will be the first one able to report its own cost.

## Two fixes the operator asked for: getting signed out, and storage that never empties

**Being signed out.** Reported as "the remember credential box doesn't work". The box turned out to be decoration — it came in with the original design mockup and was never connected to anything, permanently greyed out with its only explanation in a tooltip nobody hovers. Fair to call that broken.

But the complaint underneath it was real, and it was a genuine bug. The app renews your login quietly in the background about once an hour. If that renewal failed *for any reason at all* — a moment of bad wifi, the login service having a hiccup, being told to slow down — the app threw your saved login away entirely and made you type your password again. It couldn't tell "your login is genuinely dead" from "couldn't reach the server just then".

Now only an actual rejection ends a session. Everything else keeps it and simply fails that one attempt; the next one retries. **This is the same lesson as the pipeline fix from the night before** — a check that failed is not a check that came back negative. There it was a flaky connection killing a healthy GPU job; here it was a flaky connection killing a healthy login.

The box itself is removed rather than wired up, because what it promised is just what the app does once the renewal works. Worth building properly only if venues start sharing a machine, where "don't save my login here" becomes a real request.

Tested both directions, and checked the important way round: with the fix taken back out, three tests fail; with it in, all pass.

**Storage that never empties.** When a cloud job fails, the venue's uploaded footage is deliberately kept — deleting it would force them to re-upload a whole session to retry. But nothing ever cleaned it up afterwards, so failed sessions piled up forever. Right now that's 543MB, about half the bucket.

The plan on file was a rule to auto-delete anything in the "uploads" folder after a while. **Checking it against the real storage showed it would have matched nothing at all** — the files aren't named that way. They start with the venue's own id, and these rules only match names from the beginning with no wildcards. It would have been switched on, looked entirely correct, and reclaimed nothing indefinitely.

So instead: one rule per venue, deleting failed uploads after two weeks. That's actually what the naming was designed for — putting the venue first was a deliberate choice specifically to allow per-venue retention. Two weeks errs long on purpose, because getting it too short costs a venue their footage while too long just costs a little storage.

**The thing that could have gone badly wrong** is a rule written too broadly. The same storage also holds the shared files every job downloads — the ball-detection model and the video tools, about 620MB. A careless version would have deleted those and broken every future job. Most of the tests written here exist purely to pin down what must *not* be deleted.

Verified on the real storage rather than only in tests: a throwaway file written under a venue's uploads came back stamped with a deletion date two weeks out and the right venue's rule; identical files written next to the shared model and next to a venue's finished reels came back with no deletion date at all. All the throwaways were removed afterwards.

**One bug found only by actually running it.** The tool that checks whether the rules are correct compared them as raw text, and the storage service hands the fields back in a different order than we write them — so an identical, correct setup always reported as wrong. It would have flagged a problem on every single run, and a warning that's always on is a warning nobody reads.
