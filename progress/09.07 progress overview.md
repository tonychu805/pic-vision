# 2026-09-07

**Bumped the desktop app off its end-of-life framework, which was the second of the two things blocking a packaged installer (PIC-98).** It was eleven major versions behind — on a release that stopped getting security patches a long time ago, which is survivable for a tool running on one known machine and not for an installer going onto hardware at venues. Now on the current release.

**Checked what the jump would break before making it, rather than after.** The app only uses a small, conservative set of the framework's features, and none of them changed across those eleven versions. It has no compiled native components, so nothing needed rebuilding. Two things did come out of the review and both matter to packaging:

- **The current version no longer runs on macOS 12 (Monterey); it needs macOS 13 (Ventura) or newer.** That's a real constraint on what venue hardware can be supported — worth confirming against the machines pilot venues actually have. Staying one version back would buy Monterey support at the cost of a shorter runway before the next end-of-life. Apple itself stopped patching Monterey in 2024, so the recommendation is to hold at Ventura-and-newer, but it is a business call, not a technical one.
- Frameless windows on Linux now draw their own rounded corners. Cosmetic, and the target is macOS.

**Then actually ran the app, which had been owed for a while.** Everything built over the previous two days — the interface redesign, the light/dark theme, the whole design-token rework — had been verified by compiling and by automated tests, and never once opened. It runs: the interface loads, no errors beyond the framework's standard development-mode notice, and both themes render correctly, including the logo swap that keeps the brand mark visible on a light background. Screenshots taken of both.

Worth recording how, because it removes an excuse: the app was driven through its own remote-debugging port using a WebSocket client built into Node, with no browser-automation tooling installed. Real screenshots and real console output, on demand. There is now no reason for interface work here to go unverified.

**Also confirmed the packaging step itself still works** on the new version, producing a complete unpacked application with the video tools correctly bundled outside the compressed archive (which the cloud pipeline depends on). Filled in the missing author field the packager had been warning about.

**Then packaged the desktop app for real, and it took four attempts to get an installer that actually works.** The build itself passed first time — but "the build passed" and "the app runs" turned out to be very different claims, and the gap is the story of the afternoon.

**First: the installer was twice the size it should be.** Nearly 500MB. Almost all of the excess was one library that ships its video-inspection tool for every operating system and processor type in a single bundle — Windows, Linux, both kinds of Mac — of which exactly one is ever used. Roughly 260MB of every download was binaries for machines it would never run on. Now trimmed to just the one needed, during packaging, so nothing else changes. **186MB**, which is normal for this kind of app.

**Second, found while checking that trim: every build was quietly building both Mac types, and one of them was broken.** The build is deliberately split into two runs, one per processor type, because the video tools only download the version they were installed for. But a setting elsewhere told the packager to build both regardless — so the Apple-silicon run was packing Apple-silicon video tools into the *Intel* installer. That installer would have failed the first time anyone pressed record, and since both runs produced identically-named files, whichever finished last is what would have been published. Nothing about it looked wrong; the build went green both times.

**Operator's call: drop Intel Macs entirely.** Every Mac sold since late 2020 is Apple silicon, and a venue capture box is bought for the job rather than inherited. This also removes the ambiguity that caused the bug. Recorded what it rules out, since there are two separate exclusions with different fixes: a venue on an Intel Mac needs the second build restored; a venue on an older macOS (12, Monterey) would need the app's framework pinned one version back.

**Then the installer was tested on a real Mac, and the app opened to nothing at all.** No window — but the process running, icon in the dock, looking for all the world like it had opened and drawn an empty screen. Cause: one line setting the dock icon during startup, pointing at an image file that isn't included in the packaged app. It failed before the window was ever created. Its own comment already said it was only needed when running from source; it was just guarded on the wrong condition.

Two things made this invisible until a real install. The window is deliberately frameless and see-through (for rounded corners), so "no window" and "window that drew nothing" look identical. And running from source works fine, because the missing file is right there. Added a test that checks every file the app reaches for at startup is actually included in the package — and confirmed it catches this exact bug by re-breaking it deliberately.

**Then a second visible one: doubled window buttons.** The corner showed roughly four overlapping traffic lights. macOS was drawing its own set, and the app was drawing three more on top. The app's version was written when the window had no native buttons at all; a later change re-enabled them and nobody re-read the comment in the other file explaining why the hand-drawn ones existed. Removed ours — the native ones have the hover symbols, the full-screen menu, correct spacing and accessibility, none of which hand-drawn circles reproduce.

**With those fixed, it works: installs, opens, signs in, and finds cameras.** That last one matters most — it's the only check that exercises the video tools inside the packaged app, which is exactly what the size trim had touched.

**So there is now a real release.** Version 1.0.0, published, downloadable, built from a tagged commit. The app's own "check for updates" now points at a small service on our own domain rather than at the code-hosting site directly — so where downloads live can change later without stranding anyone who already installed. That address is baked into every copy handed out and can never change, which is the one decision here that's genuinely hard to undo.

**Also today, on the cloud console side:** billing built end to end on ECPay, because Stripe does not serve Taiwan-registered businesses at all. Currently hidden behind a switch and unable to charge anyone — the price is deliberately unset and the merchant application is still awaiting approval. Venues can also upload their own logo now, which appears on the highlight pages they share with members. Both written up as decisions.

**Post-release real-Mac follow-up: three desktop/cloud issues found and resolved.** The first external DMG test exposed a missing macOS local-network usage description, so the OS had no clear permission prompt for camera discovery; the packaged app now declares the camera-discovery purpose. The UI was also calling a partially successful scan an error whenever either of its two independent methods (WS-Discovery multicast or RTSP sweep) failed. It now reports a scan problem only when both fail.

**Closing the window now has visible, truthful background-agent presence.** The tray implementation and its template assets existed locally but had never been committed or connected to `main.js`, so a packaged app could not show the intended macOS menu-bar icon. They are now bundled and created after app startup; its menu reports local recording and connection state, reopens the window, and quits cleanly. The Apple-silicon DMG workflow completed successfully with this fix, and the operator confirmed the status-bar icon appears on the real Mac.

**Cloud-console registration is now verified working in production.** The desktop already serialized an automatic registration and a simultaneous button retry, but the console endpoint still needed to reclaim a globally unique `device_id`. A first server-side attempt used PostgREST's `onConflict`, which the deployed database rejected because its live uniqueness rule is not an exposed conflict target. Replaced it with a service-role lookup, insert, and duplicate-race re-read/update path. Production deployment completed and the operator confirmed **Connect to the cloud console** succeeds. These are resolved release issues; signing/notarization remains the outstanding packaging work.

## Open for next session

The installer works but is unsigned, so macOS warns on first launch and the person installing has to allow it through System Settings once. Fine for operator-led pilot installs; needed before a venue installs it themselves from a link, or before updates should land without a visit. Costs an Apple Developer membership.
- **The isolation test still hasn't happened**: install the release, sign up as a *separate* venue account, and confirm that venue cannot see the first one's cameras or reels.

- The recording folders are still keyed by camera *label* rather than its id, so renaming a camera orphans its history and two cameras sharing a name collide. This already caused one real bug and is still unfixed.
