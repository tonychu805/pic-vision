# 2026-08-28

**720p cloud-upload proxy checked against real detection accuracy, closing `ADR-069`'s last open item.** `ADR-069` (2026-08-27) shrank the cloud pipeline's upload from full-res to a 720p proxy to fit RunPod's payload limits, and verified the coordinate math was correct but explicitly left "does detection still work at 720p" unmeasured. Ran the real k14 detector on both a native-resolution (1920×1080) and a 720p-downscaled copy of a labeled video (`pb_draft_cup_30fps`, 34 hand labels) and scored both against the labels. **Result: no accuracy loss.** 720p actually came out slightly ahead on raw precision/recall (0.773/0.500 vs. native's 0.714/0.441); the one rally that looked like a 720p-only miss on the `quality:1` (highlight-worthy) metric turned out to be a boundary-threshold artifact — both runs detected the same rally with the same crossings, 720p's cluster just came out a hair wider and its IoU against the label landed at 0.491, just under the 0.5 cutoff. Full writeup in `EXPERIMENTS.md`. Caveat: one video only, and this session also turned up real run-to-run non-determinism in `pod_infer.py` (not previously known) that a single comparison can't fully rule out as a contributor — good enough to keep trusting the shipped 720p proxy, not exhaustive enough to close the resolution question forever.

**Along the way: caught a real mistake before it corrupted the result, not after.** First inference pass used a stale weights file left at the repo root (`TNV2_old_weights.h5`) instead of the actual production k14 model (`/mnt/fast_scratch/tracknet_weights/weights_k14_epoch19`) — caught by sanity-checking against an existing cached prediction file before trusting the numbers, not discovered later. Re-ran clean with the correct weights.
