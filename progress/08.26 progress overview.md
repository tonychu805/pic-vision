## TrackNetV3 (PIC-47) validation continued: IMG_7744 finally scored, InpaintNet confirmed harmful on low-detectability footage

Continuation of 2026-08-25's TrackNetV3 correction work (see that day's file for the adversarial-review outcome and the `pb_draft_cup` InpaintNet-config-mismatch finding). Ran `IMG_7744` through TrackNetV3 with InpaintNet on, matching the brickwall config — the one video that can separate format (doubles) from venue (brickwall), and the one whose 2026-08-21 run had silently failed and never been redone.

**Result: another loss, and a more informative one.** Raw recall looks like a TV3 win (24/75 matched vs. k14's 14/75), but every extra match is a `quality:2` rally. On the metric that actually matters (`quality:1` recall — the 3 genuinely highlight-worthy rallies on this video), TV3 goes **0/3** while k14 gets **2/3**. Precision is also worse (0.462 vs. 0.583).

**Pattern now consistent across two non-brickwall videos:** wherever TrackNetV3's raw (non-inpainted) detection rate is mediocre, InpaintNet fabricates the missing trajectory, and that fabricated trajectory generates net crossings that don't correspond to real rallies — inflating raw recall while actively hurting the recall that matters. Brickwall's near-100% raw detection rate is the one condition where this doesn't happen. Recorded in `EXPERIMENTS.md`.

**Conclusion: no format-based pattern, and TrackNetV3-with-InpaintNet is not a detector to ship on this evidence.** What's still an open, narrower question — not yet tested — is whether TrackNetV3's raw TrackNet component (without InpaintNet) beats k14; that's a different, smaller claim than PIC-47 originally set out to evaluate. Recommended closing PIC-47 as "evaluated, not adopted" in Linear.

## Correction to the correction, same day: R2 isn't the fix — RunPod's own Network Volume is

Operator said "proceed" on confirming R2/RunPod compatibility. Checked RunPod's actual S3-API docs page directly (`docs.runpod.io/storage/s3-api`) rather than trust the earlier community-sourced search summary the last note was based on. **The earlier note was wrong: RunPod's S3-compatible gateway is one-way and self-contained** — it lets S3 tools read/write RunPod's *own* Network Volume storage, using RunPod-issued credentials. It is not a mechanism for a worker to pull from an external bucket; RunPod's docs confirm no integration with any external S3-compatible provider, Cloudflare R2 included.

**Practical upshot: no third-party storage is needed to get a chunk into RunPod at all.** The real path is capture device → upload proxy chunk directly into a RunPod Network Volume via RunPod's own gateway (sidesteps the `/run`/`/runsync` payload limit entirely) → worker reads it from `/runpod-volume`. Cloudflare may still matter later, on the *output/delivery* side to end users, but has no role in getting a chunk into RunPod.

Corrected in `DECISIONS.md` (ADR-043 update, edited in place same day) and `TECH_SPEC.md` §5, and the memory saved from the last note was rewritten rather than left standing.

**Actually testing this is blocked on credentials that don't exist in this environment** — checked `.env` (only `GOOGLE_API_KEY`) and the shell environment for RunPod/Cloudflare keys, found none. Next concrete step needs the operator to provide a RunPod API key and set up (or authorize creating) a Network Volume before a real chunk-upload test can run.

## Correction #3, same thread: the operator pushed back with a real counter-argument, and it was right

Operator supplied a detailed answer (apparently from another source) arguing RunPod *is* compatible with R2 — not through a platform integration, but because code running inside a RunPod Pod/Serverless worker can call R2 directly as external S3-compatible storage via `boto3`/`rclone`/etc., independent of any RunPod-side feature. Checked this against Cloudflare's own R2 API docs directly (`developers.cloudflare.com/r2/api/s3/api/`) rather than take the pasted answer at face value: confirmed real — R2's endpoint format (`https://<ACCOUNT_ID>.r2.cloudflarestorage.com`) and `region_name="auto"` are genuine, standard, and work from any server with outbound internet, no platform-specific requirement.

**This was a real gap in the prior correction, not just a nuance.** The mistake was scoping verification too narrowly: checking "does RunPod's platform integrate with R2" (answer: no, confirmed) instead of the actually relevant question, "can code running on RunPod reach R2 at all" (answer: obviously yes, it's just outbound networking, no integration needed). Both facts are true and don't contradict each other — RunPod's own S3 gateway really is Network-Volume-only, and R2 really is usable, just via a different mechanism (the worker's own code making an HTTP call) than the one being checked.

**Corrected `DECISIONS.md`, `TECH_SPEC.md`, and the memory a second time** — now presenting RunPod Network Volume and R2-via-boto3 as two real, viable options rather than "R2 doesn't work." Judged R2 the more attractive of the two for this project specifically, since the same account/pricing can also cover highlight delivery to end users, which a RunPod Network Volume can't do at all — unifying input and output storage into one account instead of splitting across RunPod's Network Volume and a separate delivery bucket.

Still blocked on the same thing: no RunPod or Cloudflare credentials exist in this environment to actually build and test either path.

## R2 connectivity tested and confirmed working end-to-end

Operator provided a RunPod API key and Cloudflare R2 credentials, saved to `.env` (gitignored). RunPod key confirmed immediately (`GET /v1/pods` returned real account data). R2 took longer: the initial Access Key ID/Secret Access Key pair hit a TLS handshake failure at the S3 endpoint — reachable (DNS resolved to real Cloudflare IPs) but rejected before any credential exchange. Ruled out client-side causes directly rather than guess: general HTTPS worked fine from this environment (`google.com`, `developers.cloudflare.com`), and the failure was identical across TLS 1.2/1.3, with/without ALPN, and in raw `openssl s_client` — pointing at something account-side, not network or tooling.

Used the R2 token (not usable for the S3 API itself, but usable against Cloudflare's regular REST API) to check directly rather than keep guessing: confirmed the account ID was correct and R2 was active, but the account had **zero buckets**. Attempted to create one via the REST API — blocked again, this time by a real token-permission gap (the token could list but not create, a 403 "Authentication error"). Tried the official Cloudflare MCP plugin for Claude Code as a cleaner path (`cloudflare/skills` marketplace) — installed correctly but its remote MCP servers don't hot-load mid-session, so fell back to having the operator create the bucket directly in the dashboard (one click, fastest path, session restart deferred to next time this comes up).

**Once the bucket existed, everything worked immediately** — confirming the real root cause of the whole detour: **Cloudflare doesn't provision the account's S3-compatible endpoint until at least one bucket exists**, so a fresh account with zero buckets looks exactly like a broken credential or network problem. Verified end-to-end with `boto3`: `list_buckets`, `put_object`, and `get_object` all succeeded against a real bucket (`test-ingest-runpod`). Recorded in `DECISIONS.md` (ADR-043 update) and memory.

**Not yet done:** the other half of the real path — confirming a RunPod pod/worker can pull from R2 the same way (only tested from the local dev machine so far). That's the natural next step, and the only piece of the input-side POC still unverified.
