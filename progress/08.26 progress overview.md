## TrackNetV3 (PIC-47) validation continued: IMG_7744 finally scored, InpaintNet confirmed harmful on low-detectability footage

Continuation of 2026-08-25's TrackNetV3 correction work (see that day's file for the adversarial-review outcome and the `pb_draft_cup` InpaintNet-config-mismatch finding). Ran `IMG_7744` through TrackNetV3 with InpaintNet on, matching the brickwall config — the one video that can separate format (doubles) from venue (brickwall), and the one whose 2026-08-21 run had silently failed and never been redone.

**Result: another loss, and a more informative one.** Raw recall looks like a TV3 win (24/75 matched vs. k14's 14/75), but every extra match is a `quality:2` rally. On the metric that actually matters (`quality:1` recall — the 3 genuinely highlight-worthy rallies on this video), TV3 goes **0/3** while k14 gets **2/3**. Precision is also worse (0.462 vs. 0.583).

**Pattern now consistent across two non-brickwall videos:** wherever TrackNetV3's raw (non-inpainted) detection rate is mediocre, InpaintNet fabricates the missing trajectory, and that fabricated trajectory generates net crossings that don't correspond to real rallies — inflating raw recall while actively hurting the recall that matters. Brickwall's near-100% raw detection rate is the one condition where this doesn't happen. Recorded in `EXPERIMENTS.md`.

**Conclusion: no format-based pattern, and TrackNetV3-with-InpaintNet is not a detector to ship on this evidence.** What's still an open, narrower question — not yet tested — is whether TrackNetV3's raw TrackNet component (without InpaintNet) beats k14; that's a different, smaller claim than PIC-47 originally set out to evaluate. Recommended closing PIC-47 as "evaluated, not adopted" in Linear.

## Correction to the correction, same day: R2 isn't the fix — RunPod's own Network Volume is

Operator said "proceed" on confirming R2/RunPod compatibility. Checked RunPod's actual S3-API docs page directly (`docs.runpod.io/storage/s3-api`) rather than trust the earlier community-sourced search summary the last note was based on. **The earlier note was wrong: RunPod's S3-compatible gateway is one-way and self-contained** — it lets S3 tools read/write RunPod's *own* Network Volume storage, using RunPod-issued credentials. It is not a mechanism for a worker to pull from an external bucket; RunPod's docs confirm no integration with any external S3-compatible provider, Cloudflare R2 included.

**Practical upshot: no third-party storage is needed to get a chunk into RunPod at all.** The real path is capture device → upload proxy chunk directly into a RunPod Network Volume via RunPod's own gateway (sidesteps the `/run`/`/runsync` payload limit entirely) → worker reads it from `/runpod-volume`. Cloudflare may still matter later, on the *output/delivery* side to end users, but has no role in getting a chunk into RunPod.

Corrected in `DECISIONS.md` (ADR-043 update, edited in place same day) and `TECH_SPEC.md` §5, and the memory saved from the last note was rewritten rather than left standing.

**Actually testing this is blocked on credentials that don't exist in this environment** — checked `.env` (only `GOOGLE_API_KEY`) and the shell environment for RunPod/Cloudflare keys, found none. Next concrete step needs the operator to provide a RunPod API key and set up (or authorize creating) a Network Volume before a real chunk-upload test can run.

## Root-caused the 29.4fps pod-vs-local gap, same day

Operator flagged the unexplained fps gap directly ("i have a bit of concern about the runpod's processing speed"). Rather than re-guess, built a stage-by-stage profiler (`scripts/profile_pod_infer.py`) that times decode / preprocess / GPU-infer / postprocess separately, ran it once locally and once on a real freshly-created pod against the identical clip, calibration, and weights.

**Result: the earlier "likely network/disk I/O" note in `ADR-043` was wrong.** Decode is a small share of the loop on both sides. GPU inference time is essentially identical pod vs. local (37.76ms vs. 38.28ms/trio) — confirms the GPU-pin guarantee actually holds, not just in theory. The entire gap is in single-threaded CPU preprocessing (`cv2.resize` + numpy reshape): 53.29ms/trio on the pod vs. 37.25ms/trio locally, ~43% slower, despite the pod having 3x the vCPUs (48 vs. local's 16) — vCPU count is irrelevant to a single-threaded stage; what's different is per-core throughput on RunPod's shared/virtualized host vs. a dedicated local workstation.

The finding identified a real, cheap-looking lever (overlap `prep3()`'s CPU work with GPU inference, since both currently sit idle waiting on the other) — see the two follow-up entries below for what came of it.

## Fixed the CPU/GPU overlap; found a bigger lever underneath it

Walked through the fix live with the operator before building it: the loop was fully serial (decode → resize → GPU infer → postprocess), so the ~53ms/trio CPU stage and ~38ms/trio GPU stage stacked (91ms/trio) even though each sits idle while the other runs. Also examined, at the operator's request, three shapes for pod lifetime in the `ADR-066` rolling-10-min-chunk production architecture — pod-per-job (today), pod-per-session, pod-per-day — since the real ~86s-per-job pod-setup tax (mostly `pip install tensorflow[and-cuda]`, 66.5s of it) turned out to matter as much as the CPU/GPU overlap question once actually run through the 10-minute chunk budget. Recommended pod-per-session over pod-per-day (real booking gaps make per-day pay for idle GPU-hours with no benefit) and a pre-baked pod image over either (keeps per-job isolation, cuts the tax without new session-lifecycle/watchdog code this project has never built) — not yet built, needs Docker + a registry, unconfirmed as available here.

**Built the CPU/GPU overlap fix in `scripts/pod_infer.py`:** a background thread now decodes+preprocesses the next trio into a small queue while the main thread runs GPU inference on the current one — a scheduling change only, not a numerical one. **Verified byte-identical CSV output** against the pre-change version, both locally and on a real freshly-created pod, on a 730-frame clip deliberately not a multiple of 3 (exercises the tail-frame edge case `pod_infer.py`'s corruption check depends on).

**Real measured result, same pod, same clip: 29.4fps → 74.8fps**, a 2.5× win — bigger than the ~56fps ceiling the profiler's separately-timed stages had projected (likely a mix of the profiler's own per-call timing overhead and ordinary host-to-host hardware variance on RunPod's shared fleet). Local also improved, 36.4→66.8fps. A real 10-minute/18,000-frame chunk now takes ~4 min of inference instead of ~10.2 min — comfortably inside the 600s chunk budget on its own, even before the still-open pod-setup-tax question is addressed. Recorded in `DECISIONS.md` ADR-043's final update, `cloud_pipeline/README.md`'s status section.

**Then built and tested the pre-baked pod image idea from earlier — and it lost, measured, not assumed.** Docker Desktop wasn't running locally; started it, confirmed a stored Docker Hub credential already existed.
