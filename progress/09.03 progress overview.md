## Desktop client: live-camera calibration flow (PIC-75, supersedes PIC-68's file picker)

Session picked up from 2026-09-02's PIC-68 work (desktop wired to
`cloud_pipeline`, all uncommitted). Operator pushback on the "Cloud
pipeline" panel's calibration control: "I dont like the 'pick calibration
file', you should actually do the same for the test pipeline, take a
snapshot and ask users to calibrate, then save the calibration file (then
probably save it to the designated folder of the camera)." PIC-68's own
description had explicitly flagged this as out of scope ("not 'build
calibration in the client' -- separate issue if that's wanted"), so this
got its own tracking issue, `PIC-75`.

**Built:**

- `capture.js`'s new `grabSnapshot(camera)` -- one still frame from the
  camera's *live* stream (`ffmpeg -frames:v 1`), not a past recording,
  since the point is calibrating against what the camera sees right now.
  10s connect timeout, SIGKILL-safe (unlike `stopRecording`'s required
  SIGINT -- a single-frame grab has no in-progress container to corrupt).
- `cloud_pipeline/save_calibration.py` (new) -- reuses `calibrate.py`'s
  `solve_assignment`/`compute_calibration` (the same homography-fit math
  `webapp/app.py`'s browser calibration route already calls) rather than
  porting it to JS, per ADR-071's "invoke the existing Python as a
  subprocess" directive. Takes 14 clicked points as JSON on stdin, reads
  the actual snapshot's dimensions via `cv2` rather than trusting a
  caller-reported resolution, writes `calib.json`.
- `electron/calibration.js` (new) -- wires the above together: takes a
  snapshot, spawns `save_calibration.py` with the renderer's clicks, saves
  to `~/pic-vision-recordings/<camera>/calib.json` (a sibling of that
  camera's timestamped recording folders, not nested in one -- a
  calibration outlives any single session, invalidated only by the camera
  physically moving, ADR-049), records the path via `store.js`'s existing
  `setCalibPath`.
- `CameraDetailPage.jsx` -- `CalibrationControl` + `CalibrationModal`:
  takes a snapshot, renders it with an SVG click overlay (same 12 court +
  2 net-tape points, same order/labels as `calibrate.py`'s `POINTS`/
  `NET_PROMPTS` and `webapp/templates/calibrate.html`'s browser UI, ported
  into React rather than reimplemented from scratch), Undo/Reset/Retake,
  Save (reports reprojection RMSE, warns above 0.5 ft same threshold
  `calibrate.py`/`webapp` already use). The old native file picker
  (`system.js`'s `pickCalibFile`) stays as a secondary "Import file…"
  option -- a calibration produced elsewhere
  (`cloud_pipeline/setup_venue_calibration.py`, or another camera's
  already-clicked calibration for a reused mount) shouldn't force
  re-clicking 14 points against this camera's own stream.

**Verified:** `save_calibration.py`'s homography fit against a real,
already-scored calibration (`calib/IMG_7743_calib.json`) -- feeding its
recorded `image_points`/`net_image_points` back through the new script
reproduced its exact `reprojection_rmse_ft` (0.845 ft) and `point_names`,
confirming the port introduced no drift from `calibrate.py`'s own math.

## Sample-clip camera source (PIC-76) -- directly closes the privacy trap above

Right after the incident above, operator: "under the add manually, can you
able to add a drop down menu with (camera, sample clip) as selection,
where the 'sample clip' option simply allows users to upload a sample
clip to test calibration and pipeline processing." Direct, practical
response to the exact problem just hit -- testing calibration/the
pipeline shouldn't require a real, court-facing camera at all when one
isn't reliably available.

**Built:** `ManualAddDialog`'s "Add" flow now has a dropdown -- "a live
camera" (unchanged) or "a sample clip." Choosing the latter swaps to a
simple upload form (name + a native file picker for a video file), which
calls `store.js`'s new `addCameraFromSampleClip`: copies the file into
that camera's own `~/pic-vision-recordings/<camera>/` folder, creates a
camera with `connectionType: "sampleClip"` and no hostname/credentials --
just a `sampleClipPath`. From there it plugs into the existing UI with
surprisingly little special-casing, because the calibration/cloud-pipeline
work from earlier today was already cleanly separated from "how do we get
a frame/video":

- `capture.js`'s `listRecordings` returns the one uploaded file as a
  single synthetic "recording," so the existing "Send to cloud" row needed
  no changes. `pipeline.js` gained one thing -- a `videoPath` override that
  skips `concatSegments` (there are no segments for a single uploaded
  file).
- Calibration's snapshot now has two sources: `grabSnapshot` (live RTSP,
  unchanged) or the new `probeDuration`/`grabFrameFromFile` (`ffmpeg -ss`
  seek into the file), chosen by `calibration.js` based on
  `connectionType`. Defaults to 10% into the clip -- same heuristic
  `webapp/app.py`'s own frame-grab already uses, so an intro/black frame
  at t=0 isn't what gets clicked -- with a "frame at __ seconds / Reload
  frame" control in the modal for picking a clearer moment.
- Recording control is hidden for a sample-clip camera (nothing to
  start/stop); the camera grid's status text says "File ready" instead of
  "Streaming."
- Real latent bug caught while wiring this, not after: `CamerasPage.jsx`'s
  per-camera connection-status polling was keyed by `camera.hostname`. A
  sample-clip camera has no hostname, so two of them would have collided
  on the same `undefined` key and shown each other's status. Fixed by
  switching that keying (and `buildCards`'s matching lookup) to
  `camera.id` throughout -- more correct in general, not just for this
  case.

**A second, related privacy gap found while verifying this (not by
testing this feature directly, but by testing capture.js's file-seeking
functions against a real synthetic clip and finding stray files in
`/tmp`):** a leftover snapshot from the real "Court 1" camera -- the same
camera from this morning's incident -- was sitting undiscarded in `/tmp`,
almost certainly from the operator restarting the app (per this session's
own earlier instruction) and clicking "Calibrate" on Court 1 before
repositioning it, then closing the modal or the app without Save or
Cancel ever running. Deleted immediately without opening it, the same way
as this morning. This is a real, structural gap, not a one-off: nothing
before this ever cleaned up a calibration snapshot except the modal's own
Save/Cancel buttons, so any abandoned flow -- app quit, navigating away
mid-calibration -- left the file behind indefinitely. Fixed two ways:
`capture.js` now tracks every outstanding snapshot in a module-level set
and sweeps them up from `main.js`'s `before-quit` (alongside the existing
`stopAllRecordings`), and `CalibrationModal` itself now discards its
current snapshot on unmount via a cleanup effect, not only through its own
buttons. Both are safe to call on an already-deleted file (a no-op), so
this doesn't risk double-delete errors on the normal Save/Cancel paths.

**Verified:** `listRecordings`, `probeDuration`, and `grabFrameFromFile`
against a real *synthetic* test video (`ffmpeg -f lavfi testsrc`, color
bars -- not footage of any real place or person, learning directly from
this morning's mistake) -- correct duration, a correct frame at an
arbitrary seek point, and a correct, informative error seeking past the
end of the file. `vite build` clean. **Not verified:**
`addCameraFromSampleClip` itself couldn't be exercised the same way --
`electron-store` requires a real Electron environment to construct (its
`Conf` dependency demands a `projectName` option Electron normally
supplies automatically), which a bare Node script doesn't provide -- so
that function is reviewed carefully, not runtime-tested. Same for the
calibration click-modal UI end-to-end: the mechanism is now safe to test
with a sample clip, but nobody has actually clicked through it in the
running app yet.

source" section, "Known gaps" updated) updated in the same change. Linear:
new issue `PIC-76` tracks this build.

## "Cannot save calibration" -- wrong python3 resolved (bug in this session's own PIC-75 code)

Operator: "cannot save calibration." Reproduced directly (no need for a
live camera or the running app -- a synthetic snapshot plus a fake 14-point
JSON payload piped straight into `cloud_pipeline/save_calibration.py`, the
same way `calibration.js` invokes it): `ModuleNotFoundError: No module
named 'cv2'`. `calibration.js` (and `pipeline.js`, same pattern, same
session) spawn a bare `"python3"`, which resolves on the *Electron
process's* `PATH` -- the system interpreter (3.14, no `cv2`/`numpy`/
`boto3`) when the app isn't launched from a shell that activated the
repo's `.venv`, not the repo's own `.venv/bin/python3` that actually has
those packages. Works fine when a dev happens to test `save_calibration.py`
by hand from an activated shell, silently breaks from the packaged/
launched app -- exactly why this shipped without being caught.

**Fixed:** new `desktop/electron/pythonBin.js` resolves `.venv/bin/python3`
if present, falling back to bare `python3` otherwise (a dev machine with
deps installed globally); both `calibration.js` and `pipeline.js` (the
cloud-job runner has the identical latent bug, unreported but same class)
now spawn that instead of a bare string. Verified by rerunning the same
repro through the fixed path -- exits 0, produces a valid `calib.json`.
`pytest -q --ignore=archive/tests` still 132 passed (pre-existing
`archive/`-module collection error unrelated, confirmed present on `main`
before this change too).
