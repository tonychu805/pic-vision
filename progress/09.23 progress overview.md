# 09.23 progress overview

## Venues can put their logo on their reel videos (ADR-124)

A new switch in the console's Settings, "Show logo on reel videos", off by default. When a venue turns it on, its uploaded logo appears in the lower-right corner of every video made for it from then on: the full reel, the burst reel, and each top-rally clip. Reels already made stay as they are.

The logo scales with the video (8% of the frame width, with rounded corners), so a 720p camera looks the same as a 1080p one. If the logo can't be downloaded during a job, the reel is still made, just without the logo. SVG logos can't be used yet; Settings says so and asks for a PNG, JPEG or WebP.

**Where it stands:** built and tested (pipeline 229 tests, console 174), **Live and confirmed.** Turned on for PGC and run on a real Court 5 job: all 12 videos came back, and the full and burst reels both show the logo in the lower-right corner, rounded, at 1080p. PGC's uploaded logo is small (94×101), so it's slightly soft when enlarged; a bigger upload would be sharper.

## The console now agrees with itself about which venue machines are offline

Two problems, found while looking at a stuck upload:

- **Screens disagreed.** When venue machines started checking in every 60 seconds instead of 30 (09.20), only the Overview page's cutoff was raised to 3 minutes. The warning banner, the sidebar count and the Cameras page stayed at 90 seconds, so one late check-in could put "stopped reporting" at the top of a page whose table said online. All four now share one rule: offline after 3 minutes (three missed check-ins).
- **The database's status said "online" forever.** That field was really "is this machine paired", but it stored the word "online" and nothing ever changed it back. Office and Zhonghe Store had been silent 30+ hours and still read "online" to anyone querying the table. The screens were never fooled (they use the last check-in time), but any future report or alert would have been. It now stores "paired".

Live and confirmed: the database update was run after the deploy, and the next check-in kept `paired` instead of writing `online` back.

## The outside health check wasn't running every 15 minutes

It's meant to run every 15 minutes; GitHub actually ran it 8 times in the last day, with gaps up to 5.4 hours. A Cloudflare timer we already run for bookings now starts it every 15 minutes instead, and alerts still arrive as GitHub emails. **Built and committed, not live**: it needs a GitHub token saved to that timer and a deploy, both operator steps.

The five alerts it did send yesterday were all one real problem, already fixed this morning: an Office upload was sent twice, and the first copy sat "uploading" for 19 hours.

**No alert for a venue machine being off, on purpose:** Office and Zhonghe Store being off is normal right now (operator, 09.23), so an "off" alert would only be noise. Revisit if venue machines are ever expected to stay on.

## Plan decided: moving the job runner off the workstation (ADR-125, PIC-123)

The workstation is the last piece of the pipeline that has to be on for reels to get made. The plan moves each of its duties to the cloud:

- **Picking up jobs and supervising GPU machines** becomes a Cloudflare Workflow, one per job. It survives Cloudflare restarts and costs nothing while waiting.
- **Packing the pipeline code** moves to GitHub, on every push, so jobs only ever run committed code.
- **Deleting finished footage and making the code download link** move into the console.
- **Calibration fits** get rewritten in the console itself, so the Calibrate click answers instantly. They're checked against all 15 past calibrations before switching.

Venues see no change. Nothing is built yet. The build goes step by step, with the Workflow deployed switched off, then a one-job cutover test that can be rolled back by restarting the workstation runner.

## The cloud replacement for the job runner is built (ADR-125, step 4)

The Cloudflare version of the job runner is written and tested, but **not switched on**. It does everything the workstation does for reel jobs: rents the GPU machine, retries when RunPod is full or a machine gets stuck, honours Stop, and shuts machines down at the 3-hour limit. 30 tests cover each of those cases, and some tests read the workstation runner's own code so the two can't quietly drift apart. It only takes reel jobs; calibrations stay on the workstation until that part is rewritten.

Next is the cutover test: deploy it, give it two secrets, tell the workstation to keep only calibrations, switch the cloud version on, and run one real job. Rolling back means switching it off again.

## Calibration no longer needs the workstation (ADR-125, step 6)

Court calibration used to be sent to this workstation to do the math. The math now runs inside the console, so a venue's calibration needs only its own computer (to take the snapshot) and the console. It also answers straight away instead of waiting up to a minute.

Checked against every real calibration done so far (15): the new version gives the same answer as the old one, to within 0.008 mm on the court. Needs one real calibration after deploy to confirm end to end.

With this, the only thing still tied to the workstation is making reels, which the Cloudflare version (built, not yet switched on) takes over at cutover.

## Reels no longer need the workstation (ADR-125, cutover done)

The job runner moved from this workstation to Cloudflare today, and it passed a real test: a venue recording (Court 6) went from upload to finished reels, with the PGC logo, in 14 minutes, handled entirely by the cloud. Afterwards the uploaded footage was cleaned up and the GPU machine shut itself down. A real calibration through the console also passed, matching the old method to a millionth of a foot.

**The live system no longer depends on this workstation.** Its runner is switched off. If something goes wrong, rolling back is one setting in Cloudflare plus one command here.

Scaling to more venues is logged in the backlog (PIC-165 to PIC-169), none urgent.

## Security check: two real holes fixed

A security review of today's changes and the live database found two problems. Both are fixed and verified.

- **Anyone on the internet could start or stop a venue's recordings** through a database function that was left public. It's now server-only, and an outsider's attempt is refused.
- **Venue owners could edit hidden fields on their own venue record** from the browser, including the new "keep footage for training" consent flag. They could also, in a roundabout way, delete another venue's logo or reel. They can now change only what the Settings page offers; everything else is server-only.

Also found: **scheduled recordings have never started automatically.** The scheduling timer's password was saved under the wrong name, so the console has rejected it every minute since it was set up. Recording had only worked through the manual Start button. **Fixed the same evening:** the password was replaced and saved correctly in both places, and the timer is now accepted every minute. The next scheduled booking will be the first to start by itself.
