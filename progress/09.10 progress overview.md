# 2026-09-10

## Locked in the N100 SKU, and built the machine-capability check ADR-101 called for

Follow-on from yesterday's ADR-101 (venue devices have no GPU by default; the fallback for a bandwidth-constrained venue is a small physical box, not a weaker software encoder). Two threads: a business decision, and the piece of code that decision depends on.

**The decision: the standard fallback box is specifically an Intel N100, not the wider "N100/N150" family the research floated.** `DECISIONS.md`'s ADR-101 updated to say so, and a comment added on the Linear ticket (PIC-133) noting the title still says "N100/N150" as shorthand for the class of hardware researched, but N100 is the actual standard.

**The code: `desktop/electron/encoderCapability.js`, built and verified for real.** This answers "can this machine's ffmpeg actually encode fast enough to be its own bandwidth fallback, or does it need the physical box?" Built to avoid two mistakes already made once this project: trusting `ffmpeg -encoders` listing a name as proof it works (a name there means the codec was compiled in, not that a driver exists or a VM has GPU passthrough — so every candidate is benchmarked with a real synthetic encode, not just detected), and hardcoding one vendor's quality knob (NVENC's `-cq` inflated a 2.70 Mbps camera stream into a 4.67 Mbps "proxy" earlier this session — every candidate here targets a bitrate instead, the one flag portable across VideoToolbox/QSV/NVENC/AMF/libx264). Confirmed for real on this workstation: correctly found no hardware H.264 encoder in the bundled ffmpeg build, fell back to `libx264`, measured 3.5x realtime. Paired tests added (`encoderCapability.test.js`) — the "no hardware, honest fallback" path is verified for real; the hardware-present path (VideoToolbox/QSV/NVENC/AMF) is not, since none of that hardware exists in this session.

**Where it doesn't go: PIC-118's existing Diagnostics tab.** Caught this before writing the wrong code — asked where this fits, started planning to wire it into the Diagnostics tab, and got corrected: that tab answers "is a configured camera's stream healthy," a question that needs a camera to already exist. This new check is a machine-level property, answerable before any camera is added. Different moment, different surface. Instead, proposed (via a comment on PIC-128, the first-run setup wizard, still Backlog) a new step 2 — "Check this machine" — sitting between naming the machine and finding cameras, ahead of the existing per-camera check. Nothing wired into any UI yet; this is queued behind PIC-128 actually getting built.

## Chased yesterday's "get the operator's own machine out of the reel pipeline" thread (ADR-093) into a real, live-tested dead end — and a real lesson about why

Walked through what's still stuck on the operator's own workstation for no good reason: converting the video and creating the upload proxy both run there on the local NVIDIA card, before the cloud even sees the session, and the whole cloud step is driven by SSH commands issued from that same machine — meaning nothing works if that machine isn't on. Yesterday's ADR-093 already decided the fix (move the conversion onto the rented cloud GPU machine, have it run itself instead of being SSH'd command-by-command), but hadn't been built yet, and one specific worry was never resolved: does a machine image, cached once, actually stay fast to start days or hours later, or only right after it was just used? That was never tested past a 15-minute window.

Tried a shortcut to sidestep the whole question: a different way of renting cloud GPU time (RunPod's "Serverless" product) that's specifically built to keep a machine ready-to-go without the caching guesswork. Built it for real, deployed it, fired a real job at it — **it never finished starting up in over 18 minutes**, versus under 2 minutes the old way. Torn down immediately, nothing left running or billed for.

Dug into why, and found something worth knowing regardless of which path wins: the machine "image" behind all of this (everything the rented GPU machine needs installed) was **17.7 GB**, and about 10 GB of that turned out to be things this project doesn't even use — a whole second video-processing library (PyTorch, alongside the TensorFlow this project actually runs), developer tools for *compiling* GPU code (not needed to just *run* it), and an interactive web-notebook stack, all inherited from picking a "comes with everything" starting image rather than a purpose-built one. Rebuilt a lean version with just what's needed — **7.25 GB, real bug found and fixed along the way** (removing the extra libraries had silently pulled in a newer version of a shared dependency that broke the video library entirely; pinned it back and confirmed everything loads correctly).

Tested the lean image the same way, expecting it to start faster since it's less than half the size. **It was worse — consistently.** Six real tests: one slow, five that flat-out never finished starting within 3-4 minutes each. The reason makes sense once you see it: the *original*, bulkier image is built on a starting point that a huge number of other people renting from the same GPU provider also use — so the provider's machines tend to already have most of it sitting around from serving someone else, whether or not they've ever served *this* project specifically. The lean image's starting point is a perfectly good, well-known library on its own, but not one this particular GPU provider's machines happen to already be holding onto — so every single test had to fetch the whole thing fresh, and being smaller didn't help enough to make up for starting from zero.

**Net decision: keep the original, bulkier machine image.** The size wasn't actually the problem — near-universal familiarity with the base was doing the real work, and there's no way to get that benefit from a leaner, less-common starting point without a fundamentally different plan (deliberately warming the cache ourselves ahead of time, not attempted here). The lean image and its Dockerfile are kept in the repo as a documented, real, tested dead end rather than deleted. Attention goes back to yesterday's already-decided fix — getting the pipeline to run itself on the rented machine instead of being remote-controlled by SSH commands from the operator's own computer — which doesn't depend on winning the image-size question at all.

## Built the "get the operator's machine out of the pipeline" fix itself

With the image question settled (keep the original), built the actual thing: a script that runs entirely on the rented cloud machine and drives itself, instead of being told what to do one remote-control command at a time from the operator's own computer.

It pulls the venue's own recording straight from cloud storage (skipping the operator's computer for the video entirely — under the old design that footage made an unnecessary round trip through the operator's own internet connection), does the same video-shrinking and quality checks that used to require the operator's own graphics card, runs the same detection and reel-cutting steps as before (unchanged, nothing about how a highlight gets picked or cut was touched), uploads the finished reel, and reports its own progress back over the same plain web connection the rest of this system already uses — no remote-control session needed at all.

Checked this for real rather than trusting it would just work: built the actual machine image with everything baked in, and — inside that real image, not just on this laptop — confirmed every piece of code it needs to import actually loads correctly, and that the detection step still runs exactly as before inside the new setup. Also added a real automated test for the one part of this that's both testable and genuinely risky to get wrong: the "please stop" signal. A rented GPU machine bills by the minute, so a stop request that gets ignored wastes real money, and — just as bad — a brief network hiccup being mistaken for a stop request would kill a job that was working fine. Both directions are now checked automatically, against a real (if fake, local) version of the reporting system, not a guess.

**What this doesn't do yet: actually get used.** The live system still runs every real session the old way, remote-controlling a rented machine step by step from the operator's computer. Nothing has been switched over, and this new approach hasn't been tried end-to-end on a real session yet. Given today already produced two separate surprises from real live tests, that end-to-end try is being held for a deliberate go-ahead rather than run automatically.

## The self-driving machine's first real try — a long fight, and a real finish

Given the go-ahead, wired the live system to actually use the new approach and tried it for real. It went wrong, repeatedly, in a way that turned into the day's hardest and most valuable debugging session.

**The first sign of trouble looked like more of the same bad-luck-with-rented-machines story from earlier today.** The rented machine got created, then just... sat there. No progress, no error, nothing — for over 30 minutes on the first try, before it was killed by hand. Trying again landed on a different physical machine and failed the exact same silent way. A third try, a fourth — each one either sitting silent for many minutes or, once the machine's own low-level activity log was checked, showing it stuck trying to start over and over without ever actually getting anywhere, on machine after machine. One real bug got found and fixed along the way regardless — a rented machine that disappears for *any* reason, not just finishing properly, now always gets its job correctly marked as failed, instead of being left to look like it's still running forever (confirmed for real, several times, once the problem started recurring).

**Ruled things out one at a time, for real, instead of guessing.** Checked whether the whole rental service was just having a bad day — it wasn't; the *old*, already-proven way of renting a machine worked perfectly, in under 20 seconds, on the very same account, moments apart. Checked whether it was one bad physical machine — it wasn't; the failure followed the custom-built machine image itself, not any specific host, confirmed by testing the exact same unmodified starting image (which worked fine, repeatedly) against a machine image with anything at all added to it (which reliably failed, every time, no matter how small the addition). No single explanation was ever pinned down for *why* — after real, careful testing across nine rented machines, the honest answer was "something about building a custom image specifically breaks starting up on this rental service, and no amount of poking found out what."

**So the approach changed, not the persistence.** Instead of trying to figure out why a custom-built machine image kept failing, stopped building one at all. Went back to the exact same unmodified starting image already proven to work reliably, and instead had the machine fetch its own instructions and code from cloud storage the moment it boots, rather than having anything baked in ahead of time. This sidesteps the unexplained problem entirely instead of solving it.

**That worked — immediately, and completely differently.** The very next real try got much further than any of the previous nine: it actually downloaded the real recording, and only then hit a real, ordinary bug — a video-conversion command failed with no explanation given. That itself was a small bug (the failure reason wasn't even being captured), fixed in a couple of minutes. The reason underneath, once visible, was simple and made complete sense: the rented machine's own basic toolkit understands slightly older command syntax than the operator's own well-equipped computer, and this exact conversion step had simply never run on the rented machine's own basic toolkit before today — under the old design, that step always happened on the operator's own machine first.

**Fixed that, tried again — and it worked, completely, for the first time.** A real recording went in; the rented machine downloaded it, shrank it, detected the rallies, cut a highlight reel and a shorter "quick hits" version, uploaded both, and reported itself finished — all without the operator's computer touching a single video frame or running a single remote-control command. Checked thoroughly, not just taken on faith: both finished video files were confirmed to genuinely exist in storage, at real, sensible file sizes, correctly linked to the right camera and account.

**Where this actually leaves things:** the core mechanism — a rented machine that fetches its own work, does everything itself, and reports back over a plain web connection — is now proven, for real, end to end. What's still true: the live system doesn't automatically use this yet for real venue sessions; every test today was a manually inserted, manually run trial, never a real booking going through the real queue on its own. That's the natural next step, not attempted today.
